# 첫 학생 흐름 구현·검증

2026-09-09 · 기준 커밋 `f17cbe4` · 구현 가지 `codex/student-first-flow`

기존 클로드 발주서의 과제·수집·교정 통로는 이미 구현돼 있었다. 이번에는 그 실물을 재사용해 **녹음 제출의 재시도 동일성과 제출 뒤 답장 갱신**을 완성했다. 작업 범위는 `발주_첫학생흐름.md`다.

## 실제 변경

- 업로드 성공 주소를 기기에 먼저 기록하고 같은 발화의 재전송에 재사용한다. 기기 기록 실패 시 사건을 보내지 않는다.
- 동시 업로드 참조 저장을 순서대로 처리한다. 저장 중 새 로그가 생기면 최신 로그에 합쳐 다시 쓴다.
- 화면 재진입 뒤의 오래된 로그 쓰기도 저장된 동일 항목의 참조를 보존한다. 참조 불일치는 교체하지 않고 오류로 돌려준다.
- 전송 직전 저장본의 참조를 다시 읽는다. 공유 요청의 성공·오류 결과에도 저장된 참조를 실어 모든 호출자가 유지한다.
- 제출이 서버에 닿은 뒤 기존 교정 API를 조회한다. 지연 도착은 제한된 재조회로 확인하며, 백그라운드에서 중지하고 앱 복귀 시 다시 읽는다. 이전 계정의 늦은 응답은 적용하지 않는다.

## 남은 범위

- 원격 DB 검증 실패를 먼저 확인한다. [실패 실행 34288203256](https://github.com/unmet23-lab/SYNK-talk/actions/runs/34288203256), `tools/검증_마이그레이션.sh`의 첫 검사, `supabase/확인_적용후상태.sql`이 출발점이다. 로컬 코드 시험 통과를 이 DB 시험 통과로 해석하지 않는다.
- 실제 휴대전화의 녹음·기기 종료·재시작 시험 및 운영 앱 배포는 아직 하지 않았다. 네이티브 저장 어댑터는 실제 코드를 합성 파일 모듈로 실행해 확인했다. 웹 저장은 기존 규약대로 메모리다.
- 최신 전체 앱 설계의 내 방·마을·옷장과 c17 어휘/엔진 소비자는 이번 범위가 아니다. 실제 학생의 학습 효과도 측정하지 않았다.
- 다음 과제의 선택 규칙과 서버 교정 모델은 바꾸지 않았다. 기존 관련 회귀를 통과했다는 뜻이지 새 모델의 품질을 검증했다는 뜻은 아니다.
- 계약 c16, 원본 음성 보존, 기존 미커밋 변경은 유지했다. 새 결제·원격 AI 호출·운영 DB 변경 없음.
- 배포 대조에서 양쪽 모두 다른 함수는 `companion`, `deliver`, `deliver-one`, `progress`, `tasks`, `teach`다. 이 차이가 이번 구현에서 생겼다고 판정하지 않았다. 다음 운영 반영 전에 해당 차이와 `sunday-bundle` 부재를 함께 확인해야 한다. ⛔배포 0 — 이번 요청은 커밋 후 중단이며, DB 검증과 실기기 확인도 남아 있다.
