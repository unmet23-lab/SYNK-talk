## 0. 계약 코드 — 혼선 정리

| 코드 | 무엇 | 정본 위치 | 확정 주체 |
|---|---|---|---|
| **P0** | 제품 계약 — 사용자 시나리오·완료 조건·S1 선정 | `docs/개발_분업.md` §2 | **유호님** |
| **F0** | 개발 기반 1회 — CI·환경 분리·Mock | 〃 | 상호 검수 |
| **C0** | **API 계약** — 앱↔서버 인터페이스·타입·예시 payload·오류 규격·버전 정책 | 〃 | Codex 소비자 승인 후 동결 |
| **L0** | **DB 스키마** — Postgres DDL·권한(RLS) | **이 문서** | 클로드 레인 |
| **M0** | 마일스톤 — 계약 동결 3종(N1+엔진 조항+N2) | SYNK-appsscript `docs/앱기능_역할별_전수분석.md` | — |

⚠ **C0와 L0는 다르다**: C0는 *앱이 서버에 무엇을 보내고 받는가*, L0는 *그것이 DB에 어떤 모양으로 앉는가*. 둘이 1:1이면 **DB 구조가 API로 새서 나중에 못 바꾼다** — 잇는 자리는 서버 함수 한 층이다.

## 1. 설계 기준선

> **원본 증거는 지금, 파생 상태는 나중.** 원본이 있으면 파생은 언제든 다시 계산되지만, 원본이 없으면 파생을 **영원히 못 만든다**(코어엔진 §10).

**지금 만든다 (6개)**: `learners` · `learning_events` · `submissions` · `corrections` · `skills` · `consents`

**지금 안 만든다**: `learner_skill_state`·`learner_misconceptions`·`memory_items`·`interventions`·`outcomes`·`learner_profile` — 전부 위 6개에서 계산되는 **파생**. 🚫V3식 선행 구축 + E0 「엔진 전용 코드 0줄」 유지.

**「지금 아니면 못 얻는 것」 4가지** — 이것만 예외로 지금 넣는다:
1. **`intervention_id` + 개입 내용** — AI가 무엇을 했는지. ID만으로는 성과를 못 읽는다(§3-2 · v1.1 보강).
2. **`task_snapshot`** — 그때 학생이 본 문제. 문항이 수정되면 영원히 복원 불가(§3-3 · v1.1 신설).
3. **`level_snapshot`** — 그때의 급수.
4. **선택 로그** — 무엇이 제시됐고 무엇을 추천했나.

## 2. 공통 규약

| 규약 | 내용 | 근거 |
|---|---|---|
| `schema_ver` | 모든 행이 **몇 번 규격으로 적혔는지** 스스로 들고 있다. 계약 파일 `버전`(현 `c3`)을 저장 시 자동 기입 | A-8 · **유호님 확정 "넣어"** |
| 시각 2종 | `occurred_at`(발생) ≠ `ingested_at`(서버 수신) | c3 봉투 |
| `idempotency_key` | **`(learner_id, key)` 복합 유일** — 전역 유일이면 두 학생이 같은 키를 만드는 날 뒤에 온 제출이 조용히 거부된다(중복 방지 장치가 데이터 손실 장치가 된다) | v1.1 수정 |
| `correlation_id` | 한 수업·한 세션의 흐름 | c3 봉투 |
| **append-only** | `learning_events`는 갱신·삭제하지 않는다. 잘못된 사건은 **정정 이벤트를 새로 쌓는다** | v1.1 원칙 |
| 원문 불변 | 학생 원문은 고치지 않는다(오류가 곧 데이터). 교정은 항상 별도 행 | 제품방향 불변식 2 |
| 어휘 통제 | `task_type`·`event_type`·`error_tags`·`learner_response`·`verdict`는 **계약 파일 값목록만** 허용. DB `CHECK` + **CI가 계약 JSON과 대조** | v1.1 (중요-1) |

```sql
create schema if not exists engine;

create type engine.actor_kind  as enum ('learner','ai','teacher','system');
create type engine.source_kind as enum ('explicit', …);  -- 전체 값목록 = 계약/수집_교정_계약.json · 실행 DDL 정본 = supabase/L0_스키마.sql (여기 나열하면 낡는다)
```

> ⚠ **`privacy_class` enum은 두지 않는다** — §6-2 참조. v1에 있던 3등급 enum을 v1.1에서 **제거**했다.

## 3. 테이블 정의

### 3-1. `engine.learners`

```sql
create table engine.learners (
  learner_id      uuid primary key default gen_random_uuid(),
  auth_user_id    uuid unique references auth.users(id),  -- Supabase 인증과 직접 연결
  student_code    text unique not null,      -- SYNK-001 · 사람이 부르는 이름표 (⚠비밀 아님 · §4-1)
  display_name    text,
  contact         text,
  birth_year      int,
  level_current   text,
  created_at      timestamptz not null default now(),
  schema_ver      text not null
);
```

> **`auth_user_id`를 두는 이유**(v1.1): 권한을 JWT의 커스텀 클레임(`student_code`)에 걸면 토큰이 오래되거나 재발급될 때 불일치가 난다. `auth.uid()`에 직접 걸면 그 위험이 사라진다(§4).
>
> ⚠ **식별자는 여기 「구조화된 형태로만」 산다.** 학생이 작문·음성에서 자기 이름·전화번호·회사·주소를 말할 수 있으므로 **`submissions`와 오디오에도 우발적 식별정보가 들어온다** — 외부 모델 호출 전 비식별 검사를 거치고 그 결과를 기록한다(§3-3 `redaction_ver`). v1의 "식별자가 사는 유일한 곳" 문구는 부정확해서 고쳤다.

### 3-2. `engine.learning_events` — 모든 학습 행동 (N1)

```sql
create table engine.learning_events (
  event_id         uuid primary key default gen_random_uuid(),
  learner_id       uuid not null references engine.learners(learner_id) on delete cascade,
  event_type       text not null,     -- 계약 값목록 (CHECK · 판은 계약 파일이 정본)
  task_type        text,              -- 계약 값목록 — 어느 과업 통로인가 (v1.1 합류)
  actor_kind       engine.actor_kind not null default 'learner',
  occurred_at      timestamptz not null,
  ingested_at      timestamptz not null default now(),
  correlation_id   uuid,
  idempotency_key  text not null,
  session_id       uuid,
  content_id       uuid,
  skill_ids        text[] not null default '{}',
  level_snapshot   text,
  intervention_id  uuid,
  model            text,
  prompt_ver       text,
  policy_ver       text,              -- 어느 개인화 정책이 이 개입을 골랐나 (v1.1)
  consent_ver      text not null,
  degraded         boolean not null default false,
  payload          jsonb not null default '{}',
  schema_ver       text not null,
  unique (learner_id, idempotency_key)
);

create index on engine.learning_events (learner_id, occurred_at desc);
create index on engine.learning_events (event_type, occurred_at desc);
create index on engine.learning_events (intervention_id) where intervention_id is not null;
create index on engine.learning_events using gin (skill_ids);
```

**`event_type`·`task_type` 값목록** — **개수도 전체 나열도 여기 적지 않는다.** 정본은 계약 파일(`계약/수집_교정_계약.json` → `learning_events.값목록`)이고, 예시 한둘(`submission.created`·숙제제출 같은)만 무방하다. ⚠이 자리의 사본은 두 번 낡았다 — c4판 9종에 멈춘 것을 2026-08-06 외부 검토가, c6판 12종에 멈춘 것(`content.viewed` 누락)을 2026-08-09 유호님 실측이 잡았다. 「산문에 값을 복사하면 반드시 낡는다」고 스스로 적어 둔 줄이 그랬다 — 그래서 프로즈가 아니라 회귀가 막는다(`tests/C0계약.test.js` 통째복사·판개수 가드 · §5 표 「여기 복제하지 않는다」와 같은 원칙).

> **왜 둘 다 필요한가**(c3 판정 승계): `event_type`은 *무슨 일이 일어났나*, `task_type`은 *어느 과업이었나*. 합치면 숙제 제출과 다시쓰기가 똑같이 `submission.created`가 되어 구분이 사라진다.

#### `intervention.delivered` — AI가 무엇을 했는지 (v1.1 신설 · P0-2)

v1은 `intervention_id`만 남기면 된다고 했으나 **절반만 맞다.** ID는 조인 고리일 뿐이고, **그 ID가 가리키는 개입 내용이 없으면 나중에 「무엇이 효과 있었나」를 물을 수 없다.** 새 테이블은 필요 없고 이벤트 하나면 된다:

```json
{
  "intervention_id": "uuid",
  "strategy_code": "hint_only",
  "output_ref": "…",
  "target_skill_ids": ["skill-ko-grammar-particle-topic"],
  "difficulty": 2,
  "rationale": "직전 3턴 조사 오류 연속 · 설명 길이 선호=짧게",
  "cited_refs": ["note-particle-eun-neun@2026-07-30"]
}
```

> 🔑 **`cited_refs` = c4 추가**(코어엔진 §9 ⑤ 호출·인용 로그): 그 답에 **실제로 실린** 지식 노트다. `model`·`prompt_ver`(컬럼)은 어느 엔진이 말했나이고 이쪽은 **무엇을 읽고 말했나**다. 없으면 지식 노트가 틀린 것을 알아도 **이미 나간 답**을 못 찾아 미래분만 고친다(A-5 회수의 전제). ⏳ 채우기는 **RAG 도입일 첫날부터 강제** — 나중에 붙이면 그 사이 답들은 영원히 출처 미상이다.

성과 이벤트는 **같은 `intervention_id`를 가리킨다.** 그래야 상태→개입→반응→성과가 이어진다(코어엔진 §10 성과 배선).

> 🔴 **v1의 오류 정정**: talk의 **일반 AI 답변을 `corrections`에 넣기로 했던 것은 틀렸다.** 대화 응답과 오류 교정은 다른 개념이다 — 일반 답변은 `intervention.delivered`, **실제 오류 교정만** `corrections`로 간다.

#### `payload` 규격 — `choice.selected`

```json
{ "choice_dimension": "correction_style",
  "options_shown": [{"option_id":"cs1","label":"즉시 자세히 설명"},
                    {"option_id":"cs2","label":"힌트만 제공"},
                    {"option_id":"cs3","label":"수업 후 정리"}],
  "position": 2, "recommended_option": "cs1",
  "selected_option": "cs2", "changed_selection": false,
  "latency_ms": 4200, "skipped": false,
  "selection_reason": "설명이 길면 수업 흐름이 끊겨서", "rejected_all": false }
```

> 🔑 **`recommended_option`과 `position`이 없으면 학생의 진짜 선호와 「우리가 밀어준 것」이 영원히 구분되지 않는다** — 편향된 데이터로 개인화를 학습하게 된다.

> 🔴 **선택지는 `{option_id, label}`로 싣는다**(c6 · C0 §156 · 절단문서 ①-8 · 2026-08-07 정정). `option_id`는 안 바뀌는 조인 키고 `label`은 그때 표시된 문구의 **스냅샷**이다. `recommended_option`·`selected_option`이 가리키는 것도 문구가 아니라 그 **id**다. 이 예시는 c6까지 문구 문자열 배열이었고 — 계약 본문(C0 §156)이 이미 객체형을 못박은 뒤에도 — 검증기·회귀가 문구형을 정상으로 통과시켰다. 문구를 개정하는 날 판을 가로지르는 집계가 끊기고, 그 전에 쌓인 행은 어느 선택지였는지 되짚을 길이 없다(소급 불가). 이제 `lib/이벤트검증.js`가 **필드 이름 기준으로** 강제한다 — `choice.selected`뿐 아니라 같은 필드를 `submission.created` payload로 보내는 통로(G2 · `발주_게임모듈.md` §362)까지 같은 자로 잰다.

> 🔑 **c4 추가 2**(코어엔진 §9 ③ 실물 대조 · 2026-08-06): `selection_reason`은 **그 순간에만 있는 것**이다 — 나중에 물으면 회상 편향으로 다른 답이 나온다. 매번 묻지 않는다(질문 총량 상한). `rejected_all`은 **`skipped`와 다른 사건**이다: 건너뜀은 무반응이고 전량 거절은 「우리 안이 다 틀렸다」다. 합치면 개인화가 「관심 없음」과 「전부 아님」을 같은 신호로 배운다. 전량 거절이면 `selected_option`은 null이고 이때 `selection_reason`이 가장 값지다.

#### payload 검증 — 봉투와 내용을 두 층으로 (v1.1 · P0-5)

`payload jsonb default '{}'`만으로는 `event_type='choice.selected'` + `payload={}` 같은 **빈 껍데기 이벤트가 그대로 저장된다.** 그래서:

- **공통 봉투** = 모든 이벤트 필수 (컬럼으로 DB가 강제)
- **이벤트별 payload** = 해당 이벤트에만 필수 (**서버 함수에서 Zod/JSON Schema 검증** — 검증 통과분만 DB로)
- payload 모양의 버전은 **`payload.ver` 필드**로 싣는다 — 🔴 **이벤트 이름에 붙이지 않는다**(`choice.selected.v1` 표기는 C0 §4-1로 정정 · 2026-08-06). 이름에 박으면 `event_type` 값목록이 판마다 늘어나 CHECK와 집계 축이 함께 깨진다. 모양이 바뀌면 `ver`만 오르고 과거 행은 옛 `ver`로 남는다.

**테이블은 늘지 않는다.** 검증은 Edge Function 한 곳(A-2 서버측 강제와 같은 자리).

### 3-3. `engine.submissions` — 학생 산출물 원문

```sql
create table engine.submissions (
  submission_id   uuid primary key default gen_random_uuid(),
  event_id        uuid not null references engine.learning_events(event_id) on delete restrict,
  task_type       text not null,
  task_ref        text,              -- 원본 콘텐츠 ID
  task_snapshot   jsonb,             -- 🔴 그때 학생이 본 것 (질문·보기·정답·지시문)
  task_schema_ver text,              -- 스냅샷 모양의 버전
  body_original   text,              -- ⚠ 원문 — 절대 갱신하지 않는다
  audio_ref       text,              -- 음성 원본 (보존 무제한 · 유호님 확정 08-04)
  transcript      text,
  transcript_state text,
  redaction_ver   text,              -- 외부 모델로 나가기 전 비식별 검사 버전
  redaction_result jsonb,            -- 무엇이 가려졌나
  due_at          timestamptz,       -- 🔴 c10 그 배정의 마감 순간 (배정 행에만)
  due_ver         text,              -- 🔴 c10 그 마감을 낸 규칙의 판 (`due.v1` = 배정일의 끝)
  occurred_at     timestamptz not null,
  schema_ver      text not null
);
```

> 🔴 **`due_at`·`due_ver`가 c10의 전부다**(유호님 승인 2026-08-08 · 소급 불가). 습관 축(리듬)의 원신호는 「몇 시에 냈나」가 아니라 **「마감까지 몇 분 남기고 냈나」**다 — 같은 21시 제출이라도 마감이 22시면 벼락치기고 다음날 정오면 여유인데, 둘을 같은 행동으로 학습하면 이탈 예측이 통째로 어긋난다. 마감은 **수업표에서 파생된 값**이라 수업표가 바뀌면 그때 그 학생의 마감을 다시 계산할 근거가 사라진다 → **배정 순간에 박고 자물쇠로 잠근다**(§10-2 자물쇠 목록에 두 칸 합류).
>
> **`due.v1` = 배정일의 끝**(배정일 다음날 00:00 · `Asia/Ulaanbaatar`). 값은 `(배정일::date + 1)::timestamp at time zone <시간대>`로 **DB가 낸다** — 오프셋 상수를 코드에 적지 않는다(C0 §4-1·절단문서 ①-14). 규칙이 바뀌면 **새 판 이름**을 쓰고 옛 행은 옛 이름을 그대로 든다. 🚫 **읽는 쪽이 그때그때 다시 계산하는 안은 기각** — 그게 곧 「수업표가 바뀌면 과거가 바뀐다」라 이 열의 존재 이유를 스스로 깨뜨린다.
>
> **배정 행에만 채운다.** 학생 제출 행(`submission.created`)에 복사하지 않는다 — 복사하는 순간 「이 배정의 마감」의 정본이 둘이 되고, 어긋나는 날 어느 쪽이 참인지 아무도 못 정한다(바로 아래 `learner_id`를 안 둔 것과 같은 이유). 제출은 그날 배정을 조인해 읽는다. 짝 CHECK `submissions_due_paired_c10`이 반쪽(시각만·판본만)을 막고, 확인 카운터 `마감없는배정`이 **c10 이후 배정에 마감이 빠지는 것**을 드러낸다. ⛔ 옛 배정은 **소급 채우지 않는다** — 규칙을 소급 적용하는 것은 복원이 아니라 날조다.

> 🔴 **`task_snapshot`이 v1.1의 최대 신설**(P0-3). v1은 `숙제ID·숙제문항 → task_ref`를 1:1이라 썼는데 **틀렸다** — `task_ref`는 참조고 `숙제문항`은 스냅샷이다. **2년 뒤 문제가 수정되면 그때 학생이 무엇을 보고 답했는지 영원히 알 수 없다.** 계약이 문항 스냅샷을 필수로 요구하는 이유가 이것이고, 파생이 아니라 **그 순간에만 얻을 수 있는 원본 증거**다. **c4에서 계약 파일에도 합류**했고(c3에는 이 필드가 없어 `task_ref`가 둘을 겸하고 있었다) 라이브 대응은 `task_ref: [숙제ID]` / `task_snapshot: [숙제문항, 문제]`로 갈랐다.
>
> **필수 4 + 버전**: 질문 · **보기(오답 선택지 포함)** · 정답 · 지시문, 그리고 문항 버전(`task_schema_ver`는 스냅샷 *모양*의 버전이므로, 문항 자체의 판은 스냅샷 안에 넣는다). 🔴 **보기를 빠뜨리면 「왜 그 오답을 골랐나」를 영원히 못 묻는다** — 오답 선택지는 개념 진단의 재료 그 자체다(코어엔진 §9 ② 개념 매핑을 나중에 해도 되는 유일한 근거가 이 스냅샷의 완전성이다).
>
> ⚠ **실측(2026-08-06)**: 라이브 `quiz_log`는 `문제`·`정답`은 남기지만 **보기와 문항 버전을 안 남긴다**(`퀴즈ID`·`유형`·`문제`·`고른답`·`정답`·`정답여부`·`확신도`). 새 앱은 위 규격대로 채우고, **라이브 열 보강은 별건**이다 — ~~개원(2027-02) 전에는 닫아야 소급 불가 손실이 안 생긴다~~ → ✅**재실측·판정(2026-08-12)**: 라이브 quiz 100행 중 **27행은 보기가 문제 문자열 «안»에** 있고(①② 마커 2지선다) `quiz_log`가 응답 행마다 문제 «원문»을 저장하므로 **소급 파싱 가능** · 73행은 보기가 원리상 없는 주관식(누락이 아니라 출제 형식) — **라이브 열 보강은 하지 않는다.** 이 규격(보기·문항 버전)은 새 앱 `task_snapshot`과 라디오24 TOPIK 문항 팩(`296e14c`)이 채운다. 정본 = appsscript `docs/코어엔진_설계.md` §6 08-12 실측 줄.
>
> **`learner_id`를 두지 않는다**(v1.1 · 중요-6): v1은 `event_id`와 `learner_id`를 함께 뒀는데 **둘이 같은 학생인지 강제되지 않아** A학생 이벤트에 B학생 제출물이 붙을 수 있었다. 학생은 `event_id`를 통해 조회한다.
>
> 원문을 이벤트 payload에 넣지 않는 이유: ①원문은 불변, 이벤트는 계속 늘어난다 ②본문 검색·용량 특성이 다르다 ③철회 시 **원문만 지우고 통계는 남기는** 처리가 가능해진다(A-6).

### 3-4. `engine.corrections` — 교정 (생성 후 불변)

```sql
create table engine.corrections (
  correction_id    uuid primary key default gen_random_uuid(),
  submission_id    uuid not null references engine.submissions(submission_id) on delete restrict,
  reviewed_correction_id uuid references engine.corrections(correction_id),  -- 강사가 평가한 AI 교정
  actor_kind       engine.actor_kind not null,      -- 'ai' | 'teacher'
  corrected_text   text,
  error_tags       text[] not null default '{}',    -- 계약 오류태그 값목록(개수는 계약 파일이 정본) — 검증은 서버 (아래 정정)
  explanation      text,
  model            text,
  prompt_ver       text,
  reviewer         text,
  verdict          text,                            -- 계약 골든 판정 3값 (CHECK)
  verdict_reason   text,
  reviewer_confidence numeric(3,2) check (reviewer_confidence between 0 and 1),
  created_at       timestamptz not null default now(),
  schema_ver       text not null
);
```

> **가변 필드를 전부 뺐다**(v1.1 · P0-4). v1은 여기에 `seen_at`·`learner_response`·`responded_at`을 뒀는데, `learning_events`에도 `correction.responded`가 있어 **정본이 두 군데**가 됐다 — 앱이 한쪽만 쓰거나 서로 다른 값을 쓸 수 있다. 이제:
> - `corrections` = 교정 **결과 자체**, 생성 후 불변
> - `correction.viewed` 이벤트 = 학생이 **본** 사건
> - `correction.responded` 이벤트 = 학생 반응 사건(`learner_response` — 값목록은 계약 파일 · 예: 채택)
> - 「현재 상태」가 필요하면 나중에 이벤트에서 계산(파생)
>
> 🔴 **`error_tags`에 DB CHECK를 걸지 않는다**(v1.2 정정 — v1.1은 `(CHECK)`라 적었다). 배열 CHECK는 태그 리터럴 전부를 DDL에 복제해 **계약 파일과 이중 정본**을 만든다. 스칼라 값목록(`event_type`·`task_type`·`verdict`)은 c3에 동결돼 바뀌면 c4라는 명시적 개정을 거치므로 CHECK로 박았지만, **오류 태그 23종은 아직 다듬어지는 어휘**라 DB 제약으로 굳히면 마이그레이션만 잦아진다. → 태그 검증은 서버(계약 파일이 정본). ⚠ 그래서 **박아둔 3개가 계약과 갈라지는 것**은 회귀가 막는다(`tests/계약.test.js` · 변이 5/5 실측).
>
> **`reviewed_correction_id` 신설**: 여러 모델이 같은 제출물을 교정하면 **강사 판정이 어느 교정에 대한 것인지 모호해진다** — 골든셋의 분모가 흐려지는 자리라 지금 못 박는다.
>
> **`confidence` 세 뜻 분리**(중요-2): 학생 확신도 = `learning_events.payload.confidence`(라이브 `quiz_log` 확신도 · 1~5) / 추정 신뢰도 = `estimator_confidence`(c3 명명 · 0~1) / 검수자 확신 = `reviewer_confidence`(여기 · 0~1). **한 이름으로 두면 「AI가 얼마나 확신하나」와 「학생이 얼마나 확신하나」가 한 칸에서 섞인다.**
>
> **`actor_kind`와 `source_kind`를 나눈 이유**(중요-3): `source_kind`는 *어떻게 알게 됐나*(추정 메타)이고, 교정에 필요한 건 *누가 했나*다. v1은 `source_kind=inferred`를 "AI가 교정했다"는 뜻으로 써서 두 의미가 섞였다.

#### 3-4-1. 검수 확정이 담길 칸 넷 (`20260809090000_engine_c10` · 2026-08-09)

> ⚠ **위 DDL 블록은 설명용 발췌지 정본이 아니다** — 실측 2026-08-09: 이미 `l1_source_phrase`·`rubric_scores`·`review_listened_ms` 셋이 빠져 있다. **물리 정본은 `supabase/L0_스키마.sql`(합본) 하나**다. 아래 넷도 그 블록에 베껴 넣지 않았다 — 베끼면 낡는 칸이 하나 더 느는 것뿐이다.

발주 §3 이 승인·폐기 경로의 계약을 **일부러 비워 두고** 적은 문장이 이 절의 발단이다 — *"담을 물리 칸이 없어 c11 선행이다. 열 없이 적으면 구현 불가능한 계약이 정본이 된다."* 그 칸 넷을 냈다. **계약(요청·응답·오류코드)은 여전히 c11 몫이고, 여기는 자리만 판다.**

| 칸 | 무엇 | 없으면 영영 못 하는 것 |
|---|---|---|
| `corrections.supersedes` | 이 행이 대신하는 **이전 teacher 교정**(재검수 `Z`) | 두 판정 중 어느 것이 정본인지 아무 데도 없어 **서로 다른 라벨이 둘 다** 개인화·훈련으로 흘러간다. 🔑 `reviewed_correction_id` 는 **AI 행**을 가리키는 다른 축이라 이 자리를 못 덮는다 |
| `corrections.promotion_intent` | 확정에서 사람이 **훈련 승격을 함께 눌렀나**(`Shift+Enter`) | 승격 사건이 산출물 저장 **뒤**에 나므로, 그 사이 비식별·저장이 실패하면 **사람이 누른 의사가 증발**한다(그 항목은 이미 큐에서 나갔다 — 다시 물을 방법이 없다) |
| `corrections.transcript_at_review` | 그 행이 **판정한 시점의 전사** | 나중에 `submissions.transcript_verified` 가 고쳐지면 과거 라벨이 조용히 **다른 원문**에 붙는다 |
| `pipeline_jobs.discard_reason` | 폐기 사유(**닫힌 어휘 6**) | 「강건성 재료」와 「오염 데이터」를 나중에 구별할 수 없다 — 남긴 이유가 사라지면 남긴 의미도 사라진다 |

- 🔑 **`promotion_intent` 만 `not null default false`** 다. `request_hash`(앞 조각)는 *행에 대한 사실*이라 기본값이 「없는 지문이 있는 척」이 되지만, 승격 의사는 반대다 — 아무도 누른 적 없으면 그것이 곧 `false` 이고, null 로 두면 사슬이 「모름」을 참으로 접을 여지가 생긴다. **실패해도 승격이 안 되는 쪽**이 기본값이어야 한다.
- 🚫 **teacher 행의 «존재»를 승격 의사로 읽지 않는다** — 그것이 곧 발주서가 금지한 자동 발행이다. 갈리는 것은 **이 열의 값**이다.
- 🔑 폐기 사유 **값목록의 정본은 CHECK `pipeline_jobs_discard_reason_c*`**(접미는 현행 계약판 — c16 이 다시 이름째 갈았다)이다(계약 JSON 에 넣지 않는다 — 그 파일은 앱·수집층이 공유하는 어휘이고 폐기 사유는 검수자 통로 밖으로 안 나간다). 산문 사본 둘(`발주_수집파이프라인.md` §3 · `검수_내부계약.md` 표)은 **지우지 않고** `tests/폐기사유.test.js` 가 그 CHECK 와 순서까지 대조한다.
- ⚠ **CHECK 는 「폐기인데 사유가 없다」를 안 막는다** — 조각 이전에 이미 `discarded` 인 행이 있으면 조각 자체가 안 부어진다(따를 수 없는 처방 · F103). 그 자리는 확인 쿼리의 카운터 `폐기사유없는폐기` 가 지고, c10 `마감없는배정` 과 같은 모양으로 **조각이 선 뒤에 갱신된 job 만** 센다.
- 🚫 **데이터셋 멤버십 표(`dataset_item`·`group_id`)는 이 조각에 없다.** 발주서가 넷째 자리로 함께 적었지만 **새 표를 만드는 것은 ㉮ 가 미뤄 둔 C 계층 그 자체**다(`엔진도달_설계.md` §6 표 3행). 위 넷은 *이미 있는 표의 열*이라 그 결정을 안 건드리고, 멤버십은 소급 불가가 아니다(조립 시점에 위 넷을 읽어 계산한다). ▶ c11 이 그 표를 낼 때 **`(dataset_ver, group_id) → 목적` 을 PK 로** 잡아 훈련셋⟂평가셋 혼입을 *표현 불가능하게* 만드는 것이 권고다 — 트리거로 막으면 꺼질 수 있다.
- 🔴 **넷 다 채우는 코드가 0줄이다.** 검수 Edge Function(⑥ · `supabase/functions/review`)의 approve·discard 경로가 서야 값이 들어온다. **열이 섰다는 것을 「배선이 섰다」로 읽지 않는다**(`daily_activity.expected`·`model`·`prompt_ver` 가 그렇게 열만 선 채 남아 있다).

### 3-6. `engine.consents` — 동의 (간략 · 유호님 확정)

```sql
create table engine.consents (
  consent_id    uuid primary key default gen_random_uuid(),
  learner_id    uuid not null references engine.learners(learner_id) on delete cascade,
  consent_ver   text not null,
  doc_hash      text,                      -- 동의 문서 원본 해시 (나중에 내용이 바뀌지 않게)
  agreed_at     timestamptz not null,
  revoked_at    timestamptz,
  schema_ver    text not null
);
```

**서버가 이벤트 저장 전 반드시 확인한다**(v1.1 · 중요-5) — `consent_ver`가 단순 문자열이면 **동의한 적 없는 버전으로도 저장된다**:

```
agreed_at <= occurred_at
  AND (revoked_at IS NULL OR occurred_at < revoked_at)
  AND event.consent_ver = 그 학생의 유효한 consent 버전
```

> ⚠ **의도적으로 여기서 멈춘다.** 외부 검토문의 동의 4종 분리는 **유호님이 「동의는 전 버전 그대로 최대한 간략하게」로 확정**(코어엔진 §6)해 기각됐다. 별도 `consent_ledger`도 만들지 않는다.
> ⚠ **음성 「보존 무제한」은 「철회 면제」가 아니다** — 보존 기간을 두지 않는다는 뜻이고, 철회 시 파기(A-6)는 별개 사유로 그대로 적용된다.
> ⚠ 만 14세 미만 법정대리인 동의는 이 구조와 **별도**로 필요하다(법적 검토 대기 · v18.9 트랙).

## 4. 인증·권한 (v1.2 확정 — 유호님 "학원 발급 코드로 가자" 2026-08-05)

**DDL 실물 = `supabase/L0_스키마.sql`**(이 절의 실행 가능한 형태). 아래는 그 근거다.

### 4-1. 아이디 = `student_code` · 비밀번호는 학생이 정한다 (✅유호 확정 2026-08-06)

**이 설계의 목표는 전달물 0이다.** 학생이 이미 아는 것(자기 학생번호·자기 전화번호)만으로 첫 로그인이 되고, 그 뒤로는 학생이 정한 비밀번호를 쓴다. **카드·QR·문자·메일 어느 것도 만들지 않는다.**

| | 아이디 | 비밀번호 |
|---|---|---|
| 값 | `SYNK-042` (`student_code`) | 학생이 첫 로그인에서 **직접 정한다** |
| 성격 | **비밀 아님** — 남이 알아도 된다 | 비밀 |
| 어디 사나 | `engine.learners.student_code` | **`auth.users`만** — 평문은 우리 표에 없다 |
| 바뀌나 | 안 바뀐다 | 학생이 언제든 변경 · 잊으면 원장이 초기화(§4-2-2) |

> 🔑 **이것은 「순번을 로그인에 쓰지 말라」던 앞 판정과 충돌하지 않는다.** 그때 막은 것은 순번을 **비밀번호로** 쓰는 안이었다 — `SYNK-043`을 넣는 것만으로 남의 계정에 들어가기 때문이다. **아이디는 공개여도 되고 비밀은 그 옆에 따로 있다.** 🚫 `student_code` 고엔트로피화는 여전히 기각이다(출석·포인트·리포트가 이미 물려 있고 매일 부르는 문자열 · memory `student-id-autoissue-2026-08-04`).
>
> 🚫 **크루카드 번호는 아이디로 쓰지 않는다** — 그건 **제출 번호**라 재제출·태블릿/링크 이중 제출이면 **한 학생에게 여러 개**가 생긴다(같은 memory ②). 사람당 하나인 것은 `student_code` 뿐이다.

**정규형**: 하이픈·공백 제거 + 대문자 → `SYNK042`. 합성 이메일은 이를 소문자화한 **`synk042@synk.invalid`**. ⚠ **자릿수는 발급기가 낸 그대로 쓴다** — `SYNK-42`와 `SYNK-042`를 같은 것으로 접지 않는다(접는 순간 두 학생이 한 계정을 가리킬 수 있다).

#### 4-1-1. 첫 로그인 게이트 — 학생번호만으로는 열지 않는다

학생번호는 순번이라 **다음 번호가 예측된다.** 그것만으로 계정을 열면 `SYNK-043`을 **먼저 선점해 남의 계정을 뺏는다.** 그래서 첫 1회에만 **본인 전화번호 뒤 4자리**를 함께 요구한다(상담 때 이미 받은 `contact` · 전달물 0).

🔴 **뒤 4자리는 1만 가지뿐이라 그 자체로는 약하다. 지키는 것은 자릿수가 아니라 다음 셋이다.**

1. **시도 제한** — `learners.signup_attempts`가 **5**에 이르면 그 학생의 첫 등록 경로가 잠긴다. 해제는 원장만 한다. (제한이 없으면 1만 번 대입으로 반드시 뚫린다.)
2. **한 번만 열린다** — 첫 등록은 `auth_user_id is null`일 때만 돈다. 성공하는 순간 이 경로는 그 학생에게 **영원히 닫힌다**.
3. **실패는 어느 칸이 틀렸는지 알려주지 않는다** — 「없는 학생번호」와 「뒷자리 불일치」를 가르면 **학생번호의 존재 여부가 새어 나가** 명단을 훑을 수 있다. 메시지는 하나뿐이다.

**전화번호 대조는 숫자만 남겨서 한다** — `contact`에 `+976`·공백·하이픈이 섞여 들어오므로 양쪽에서 숫자만 뽑아 뒤 4자리를 비교한다. 숫자가 4개 미만인 행은 **대조 불가로 잠근다**(빈 값이 통과하면 그 학생은 아무나 가져간다).

⚠ **이 게이트가 막는 것은 「모르는 사람의 선점」이지 「아는 사람의 도용」이 아니다.** 같은 반 친구는 서로 번호를 알 수 있다. 그쪽은 ②의 1회성과 원장 초기화 기록(§4-2-2)이 담당한다.

### 4-2. Supabase Auth 매핑 — 인증 서버를 따로 짓지 않는다

번호+비밀번호 로그인을 위해 **커스텀 JWT 발급기를 만들지 않는다.** Supabase 내장 이메일/비번 provider에 **합성 이메일**로 얹으면 `auth.uid()`가 그대로 나오고 §4-3 정책이 손대지 않고 작동한다.

| | 값 (학생번호가 `SYNK-042`일 때) | 비고 |
|---|---|---|
| email | `synk042@synk.invalid` | 정규형을 **소문자화** — Supabase가 이메일을 소문자로 저장하므로 |
| password | **학생이 정한 것** | 우리는 모른다. **6자 이상만** 요구하고 복잡도 규칙은 두지 않는다 — 몽골 10대가 매일 치는 값이고, 이 앱이 지키는 것은 금융 자산이 아니라 학습 기록이다 |
| 앱 호출 | `signInWithPassword` 1회 | `signUp`은 앱에서 **절대 부르지 않는다** — 계정 생성은 Edge Function(service_role)만 |

> 🔑 **아이디는 소문자화하지만 비밀번호는 손대지 않는다.** 앞 판(코드 방식)에서 실전에 깨지던 두 줄이 여기서도 그대로 산다 — 다만 이제 비밀번호는 **학생이 친 문자열 그대로** 넘긴다(대소문자·공백 어느 것도 우리가 고치지 않는다. 고치면 학생이 정한 값과 달라져 「분명히 맞게 쳤는데 안 된다」가 된다).

> 🔑 이 두 줄(소문자 이메일 / 대문자 비밀번호)이 실전에서 깨지는 자리다. **앱과 발급 도구가 같은 함수 하나를 공유한다** — 두 곳에 적으면 갈라지고, 갈라지면 증상은 「로그인이 안 된다」뿐이라 원인이 안 보인다.
>
> ✅ **`@synk.invalid` 수용 실측 완료 (2026-08-06)** — 문서가 정한 판정 방법 그대로 **계정 1개를 실제로 만들어** 쟀고, 만든 뒤 지웠다(`auth.users` 0 확인). 대체안 `@code.synk.mn`은 **필요 없어졌다.**
>
> | 잰 것 | 결과 |
> |---|---|
> | `admin.createUser` 로 `@synk.invalid` 생성 | ✅ HTTP 200 · 저장된 email 이 소문자 그대로 |
> | `email_confirm: true` | ✅ `email_confirmed_at` 즉시 채워짐 — **대시보드 「이메일 확인 OFF」에 의존하지 않는다** |
> | 소문자 이메일 + **대문자** 비번 로그인 | ✅ 성공(access_token 발급) |
> | 소문자 이메일 + **소문자** 비번 로그인 | ✅ **실패** — 비밀번호 대소문자 구분이 실측으로 확인됐다(§4-2 표의 전제) |
> | 표기형(하이픈 포함) 그대로 로그인 | ✅ **실패** — 앱이 정규형으로 바꿔야 하는 이유가 이것이다 |
>
> 🔑 **`email_confirm: true` 가 통했다는 것이 뜻하는 바** — 관리자 생성 경로는 `mailer_autoconfirm` 설정과 **무관하게** 확인된 계정을 만든다. 그래서 §4-2 가 요구하던 대시보드 설정 둘 중 **「이메일 확인 OFF」는 우리 경로에 필요 없다**(설정을 바꾸는 대신 안 건드리는 쪽이 싸다). **「공개 가입 OFF」는 여전히 필요하다** — 그건 우리 경로가 아니라 **남의 경로**를 닫는 것이다.

**계정은 첫 로그인 때 만든다 — 미리 만들지 않는다.** 미리 만들면 그 순간 **전달해야 할 초기 비밀번호가 생기고, 전달물 0이 깨진다.** Edge Function이 §4-1-1 게이트를 통과시킨 뒤 `auth.admin.createUser({ email, password: 학생이_정한_값, email_confirm: true })`(service_role)로 만들고 `learners.auth_user_id`를 잇는다. 대시보드 **공개 가입 OFF**는 그대로 필요하다 — 그건 우리 경로가 아니라 **남의 경로**를 닫는 것이다. 명단에 없는 학생번호로는 계정이 생기지 않으므로 **열거 공격의 입구는 여전히 닫혀 있다**.

#### 4-2-1. 복구 정보 — **저장하되 발송하지 않는다** (✅유호 확정)

첫 로그인에서 비밀번호를 정할 때 **복구 이메일**(`recovery_email`)과 **복구 전화번호**(`recovery_phone`)를 함께 받아 `learners`에 저장한다. 🔴 **거기로 메일·문자를 보내지 않는다** — 보내려면 SMTP·SMS 공급자가 필요하고, 그 비용·설정을 안 들이는 것이 이 설계의 전제다(§4-5 ①과 같은 판단).

그럼 왜 받나 — **본인 확인 대조용**이다. 학생이 비밀번호를 잊으면 원장이 화면에서 그 값을 보고 묻는다(「등록한 이메일 앞 세 글자?」). 그리고 **지금 안 받으면 나중에 소급이 안 된다** — 발송을 붙이고 싶어지는 날 정보는 이미 쌓여 있다.

⚠ 복구 이메일·전화는 개인정보다. **원장과 본인만** 본다 — 검수자·강사에게는 열지 않는다(§4-5 ②의 「필요 없는 것은 열지 않는다」와 같은 축).

#### 4-2-2. 잊었을 때 = 원장의 「비밀번호 초기화」 (✅유호 확정 — 🚫공용 비밀번호 기각)

원장이 학생을 찾아 **버튼 1번** → 화면에 **6자리 임시번호**가 뜬다 → 말로 알려준다 → 학생이 그것으로 들어오면 **즉시 새 비밀번호 설정 화면**으로 간다.

> ✅ **물리 확정 2026-08-07 (유호님 "해시로 들고 있는 방식으로 가자") — 임시번호는 `auth.users`에 넣지 않는다.**
> 🔴 **넣었으면 「30분 만료」가 장식이었다.** GoTrue에는 비밀번호 만료 개념이 없어, 임시번호를 그냥 비밀번호로 세우면 30분이 지나도 **영원히 유효**하고 `temp_password_expires_at`은 아무도 보지 않는 칸이 된다 — 그건 그 계정에 **영구히 발급된 두 번째 비밀번호**이고, 이 절이 「공용 비밀번호」를 기각한 이유(학생이 그 값을 알고 친구 계정에 들어간다)를 그대로 되살린다.
> **대신 우리가 해시로 든다**: `learners.temp_password_hash`(pgcrypto `crypt`+`gen_salt('bf')` · 대조도 DB 안에서 `hash = crypt(입력, hash)`) + `temp_password_expires_at`. 학생은 `POST /v1/auth/temp-login`으로 들어오고 **그 자리에서 자기 비밀번호를 정한다.** 우리 코드가 반드시 로그인 길목에 있으므로 **만료가 참**이 된다. 🔑 원장 화면 흐름은 한 글자도 안 바뀐다.
> 🔴 **초기화는 옛 비밀번호도 죽인다** — GoTrue 비밀번호를 **아무도 모르는 난수**로 갈아끼운다. 초기화가 필요한 현실적 사고 중 하나가 「누가 내 비번을 안다」인데, 옛 값을 살려 두면 그 경우 초기화가 아무것도 안 한 것이 된다.
> 🔴 **평문은 어디에도 남기지 않는다** — DB에도(해시뿐), 감사표에도(번호를 안 적는다). 원장 화면이 1회 보여주고 끝이다.
> **시도 제한은 새 칸 0** — `signup_attempts`를 그대로 쓴다(둘 다 「이 계정을 여는 시도」이고 푸는 것도 같은 버튼 하나다). 6자리는 100만 가지지만 지키는 것은 자릿수가 아니라 **30분 + 5회**다.
> 조각 = `supabase/migrations/20260807024500_temp_password_c7.sql`(칸 1 + CHECK 1 · 표 0). CHECK `learners_temp_password_paired_c7` = **해시가 있는데 만료가 없으면 거절** — 그 상태가 곧 이 판이 없애려던 「영구 두 번째 비밀번호」라 문서가 아니라 DB가 막는다.

- 임시번호는 **그 학생 것만**, **1회용**(쓰는 즉시 해시·만료를 지운다), `learners.temp_password_expires_at`으로 **30분** 뒤 만료.
- 초기화 기록이 남는다(누가·언제·어느 learner). `learner_id`·`auth_user_id`는 안 바뀌므로 **과거 학습 데이터가 끊기지 않는다.**
- `signup_attempts`도 여기서 0으로 푼다(첫 등록이 잠긴 학생의 해제 경로가 이 버튼 하나다).

> 🚫 **「고유 공용 비밀번호」(마스터 비번으로 아무 학생 계정에나 로그인)는 기각한다.** 하나가 새면 **전 학생 계정이 통째로** 열리고, 새면 전원 비밀번호를 바꿔야 하며, 그동안 누가 무엇을 봤는지 알 수 없다. 학원에서 가장 현실적인 사고는 **학생이 그 값을 알고 친구 계정에 들어가는 것**이다. 초기화 버튼은 **더 안전하면서 손이 더 적다 — 외울 것이 없다.**
>
> 🔑 마스터키는 「학생 계정을 여는 열쇠」가 아니라 **「초기화 권한」**이어야 하고, 그 권한은 **원장 로그인 자체가 이미 갖고 있다**(§4-5 `director`). 그래서 따로 만들 비밀번호가 없다.

#### 4-2-3. 비밀번호 변경 — 학생이 언제든

앱에서 **현재 비밀번호를 확인한 뒤** `updateUser({ password })`. 서버 로직 0(Supabase 기본). 변경해도 `learner_id`는 그대로다.

**초기화가 유일한 복구 경로다**(§4-2-2 · 분실 공통): ①본인 확인(원장 — 대면 + `recovery_email`·`recovery_phone` 대조) → ②-ⓐ **GoTrue 를 먼저** — `auth.admin.updateUserById` 로 비밀번호를 **아무도 모르는 난수**로 갈아끼운다(그 호출의 목적은 임시번호를 심는 것이 아니라 **옛 비밀번호를 죽이는 것**이다) → ②-ⓑ **DB 를 나중에** — 임시번호는 우리가 `learners.temp_password_hash`(bcrypt) + `temp_password_expires_at` 로 든다(§4-2-2) → ③**전 세션 폐기**(완료조건은 아래 — 비밀번호 교체만으로는 이미 로그인된 기기가 죽지 않는다) → ④**감사 기록**(누가·언제·어느 learner·사유 · **임시번호 평문은 기록 금지**).

> 🔴 **②는 2026-08-07 까지 「`auth.admin.updateUserById`로 임시 비밀번호 설정」이라고 적혀 있었다** — 바로 위 §4-2-2 가 명시로 기각하고 물리(`supabase/functions/auth/index.ts`)가 이미 반대로 선 것을, 이 절만 옛 판으로 들고 있었다. 그대로 구현하면 §4-2-2 가 없애려던 **「영구히 발급된 두 번째 비밀번호」**가 되살아나고 `temp_password_expires_at` 은 아무도 보지 않는 칸이 된다. ⓐ→ⓑ **순서**도 같이 못 박는다(②-18 · 순서가 곧 「반쯤 실패했을 때 남는 상태」다).

> 🔴 **③은 특정 API 호출이 아니라 보안 완료조건이다**(2026-08-06 정정 — 이전 판의 `auth.admin.signOut(user_id)` 표기는 오류: 실제 `admin.signOut`은 user_id가 아니라 그 사용자의 **유효한 JWT**를 받고, 세션·refresh token을 폐기해도 **이미 발급된 access token은 만료 시각까지 유효하다**). 완료조건: **재발급 즉시 옛 refresh token의 재사용이 차단되고, 만료 전인 옛 access token도 보호 데이터에 접근하지 못한다.** ✅ **ⓑ로 확정·물리까지 섰다**(2026-08-06 · §4-5 ③과 같은 판정 함수 `engine.session_alive()`): `learners.active`·`learners.revoked_before`를 두고 정책이 **매 요청 토큰의 `iat`와 비교**한다. ⓐ(짧은 TTL)는 창이 0이 아니라 기각.

- ✅ **실측**: 옛 access token의 학생 데이터 접근 → **0행**(`supabase/검증_직원정책.sql` ⑤ · 폐기 전 1행 / 폐기 후 0행). 학생·직원 **두 축이 같은 함수 하나**를 부르므로 갈라질 자리가 없다.
- ⛔ **아직 아닌 것**: 옛 refresh token 갱신 실패 · 새 비밀번호 로그인 성공 · 다른 학생 세션 무영향 — 셋 다 **로그인 왕복이 필요**해서 첫 등록 Edge Function이 선 다음에 잰다.
- 🔴 위 보증은 **토큰 경로**의 것이다. `service_role`은 RLS를 우회하므로 Edge Function은 같은 판정을 자기 손으로 한 번 더 한다.

> ⛔ **「메일로 재설정」 UI는 두지 않는다** — `resetPasswordForEmail`은 `signUp`과 나란히 금지 목록이다(합성 주소로 발송돼 **배달 불가**하고, 증상은 「메일이 안 온다」뿐이라 원인이 안 보인다). `recovery_email`을 받는다고 이것이 열리는 것이 아니다 — 그 값은 **대조용**이지 발송 대상이 아니다(§4-2-1).
> **비밀번호 「변경」 UI는 있다**(§4-2-3) — 현재 비밀번호를 아는 상태에서만 도는 것이라 위 금지와 축이 다르다.
> 학생 화면에 **합성 이메일을 노출하지 않는다** — 로그인 UI는 「학생번호 + 비밀번호」 두 칸이다.

> ⚠ **임시번호를 시트·문서에 모아두지 않는다.** 원장 화면이 **1회 보여주고 끝**이며 30분 뒤 만료된다. 모아두는 순간 그 파일 하나가 다수 계정이 된다.

### 4-3. 정책 — 학생 토큰은 **읽기만**

쓰기는 전부 Edge Function(service_role)을 지난다 — payload 검증(§3-2)이 이미 거기 있어서 쓰기 통로를 둘로 만들 이유가 없다. 그래서 정책은 `select`만 존재한다.

```sql
-- 조인을 정책마다 다시 적으면 갈라진다 — 한 곳에서 파생시킨다
create or replace function engine.current_learner_id() returns uuid
  language sql stable security invoker set search_path = engine, public as
$$ select learner_id from engine.learners where auth_user_id = auth.uid() $$;

create policy learner_self_events on engine.learning_events for select to authenticated
  using (learner_id = engine.current_learner_id());
-- learners·submissions·corrections·consents 도 각각 (전문 = supabase/L0_스키마.sql §4)
```

**`engine` 스키마는 지금 API에 노출하지 않는다**(Settings → API → Exposed schemas 건드리지 않음). 앱은 Edge Function만 통하므로 노출이 필요 없고, 노출을 미루면 정책 실수의 영향 범위가 0이다. RLS는 **그래도 켠다** — 나중에 노출하는 날 잊어도 닫힌 채로 실패하게.

> **기본은 「아무도 못 본다」**이고 정책이 열어주는 것만 보인다 — 새 테이블에 정책을 잊으면 **닫힌 채로 실패**하지 열린 채로 새지 않는다.
>
> ⚠ **`service_role`은 RLS를 우회한다.** 서버 함수가 요청에 담긴 `learner_id`를 그대로 믿으면 RLS가 있어도 남의 데이터를 읽고 쓴다 — **서버는 항상 토큰에서 학생을 확정**한다.

### 4-4. 도전안 (기각 — 라벨 병기)

**Supabase Auth를 아예 안 쓰고** 앱이 코드를 서버에 보내면 서버가 자체 세션 토큰을 발급하는 안. Auth 설정 0이고 코드 형식도 자유롭다. **기각 근거**: RLS라는 마지막 방어선이 사라져 **서버 코드 버그 하나 = 전 학생 데이터 유출**이 되고, 세션 만료·갱신·폐기를 직접 짜야 한다. 지금 얻는 건 설정 몇 개고 잃는 건 「닫힌 채로 실패」라는 성질이다.

### 4-5. 직원(강사·검수자·원장) 인증 — **설계 확정** (P0 승격분 · 2026-08-06)

**S1 실행 범위는 여전히 학생 읽기 전용 토큰뿐이다.** 이 절은 그다음(N10 검수 탭)이 서기 위해 먼저 확정돼야 했던 설계다 — 발주서 §3이 `role='inspector'` 화면을 발주했는데 그 인증이 없어 **착수가 차단**돼 있었고(외부 검토 P0), 아래 ①~④가 그 차단자다.

**전제 (재론하지 않는다)**: 검수 대시보드 = **Expo 앱 안 역할 화면**(유호 확정 08-06 "expo로 해줘" · PC는 Expo web · 한 코드베이스 · 🚫「앱 밖 웹 도구」 재제안 금지). **한 앱에 역할이 넷 들어가고 나뉘는 것은 앱이 아니라 권한이다.** 그래서 차단 사유는 화면 형태가 아니라 **`service_role` 키**였다 — 그 키는 웹 빌드를 포함해 **앱에 어떤 경우에도 두지 않는다**(번들은 사용자 기기에 있고 거기 들어간 키는 회수 불가).

#### ① 인증 방식 — 학생 통로를 그대로 쓴다 (새 인증 서버 0)

직원도 **학원 발급 코드 + 합성 이메일**(§4-1·§4-2 그대로). 발급 도구·정규형 규칙·`@synk.invalid` 수용이 이미 실측으로 서 있어 새로 지을 것이 0이다.

- ✅ **SMTP는 여전히 불요** — 이 절이 재판정하라던 항목의 답이다. 직원 경로에도 메일이 0이면 SMTP 계정·도메인 인증·발송 실패 대응이 아예 안 생긴다. 분실 복구 = **원장 재발급**(대면)이 담당한다.
- ⚠ **직원 코드는 12자**(학생 8자와 다르다 · 32¹² ≈ 1.15×10¹⁸). 직원 계정 하나가 전 학생 제출물을 읽으므로 표적 가치가 다르다. 같은 생성기의 **길이 인자 하나**이지 새 코드 체계가 아니다.
- 🚫 **직원 실이메일+비밀번호 provider는 만들지 않는다** — 1~3명을 위해 SMTP·비번 재설정 UI·메일 배달 실패라는 새 실패 모드 셋을 들인다.

#### ② 역할·행 접근 범위 — 역할은 토큰이 아니라 **표**에 산다

새 표 `engine.staff`: `auth_user_id`(pk · `learners`와 같은 모양) · `staff_id`(감사에서 사람을 가리키는 안정 키) · `role`(`teacher`·`inspector`·`director`) · `display_name` · **`active`**(즉시 차단 스위치) · **`revoked_before`** · `created_at`. **이 절이 새로 내는 표는 이것과 ④의 `staff_access_log` 둘뿐이다.**

> ⚠ **`role` 값목록의 정본은 조각의 CHECK(`staff_role_c7`)다 — 계약 파일이 아니다**(2026-08-06 정정 · 초안은 「계약 파일에 c7 등재」라 적었다). `계약/수집_교정_계약.json`은 스스로를 **두 저장소가 같은 바이트로 나눠 갖는 학습 데이터 어휘**로 정의한다. 직원 역할은 학습 데이터가 아니고 Apps Script는 읽지 않는다 — 넣으면 **자기가 안 쓰는 값목록 때문에 저쪽 CI가 지게 된다**. 정본은 한 곳이면 되고, 그 한 곳이 값을 실제로 강제하는 자리다.

> 🔴 **역할을 JWT(`app_metadata`)에 넣지 않는 이유** — 토큰은 발급 시점에 굳는다. 해임·역할 강등이 **토큰 만료까지 반영되지 않는다.** 표에 두면 RLS와 Edge Function이 매 요청 **살아 있는 값**을 읽어 즉시 닫힌다.

| 역할 | 읽기 | 비고 |
|---|---|---|
| `inspector` | 검수 큐에 든 **`engine.review_queue`**(제출물 12열) · `corrections`(ai 행) | 🔴 **구조화된 신원은 안 연다**(`display_name`·`contact` · 화면은 `student_code`도 아닌 **제출물 ID**로 돈다). ⚠ 그러나 **익명이 아니다** — 아래 ②-1 |
| `teacher` | 담당 학생 | 담당 관계 표는 S1 밖(수업 운영) — **N10 착수 시 정의**하고 그전까지 이 역할은 발급하지 않는다 |
| `director` | 집계만 | 조회 전용 — 원장 화면은 사건을 만들지 않는다 |

🔴 **쓰기는 직원도 Edge Function만**이다. 검수 승인이 만드는 teacher `corrections` 행도 Edge Function이 쓴다 — **클라이언트는 자기 역할을 주장만 하고 서버가 `engine.staff`에서 확정한다**(§4-3 ⚠ "서버는 항상 토큰에서 학생을 확정"의 직원판 · `service_role`이 RLS를 우회하므로 이것이 유일한 방어선이다).

##### ②-1 검수자는 익명 데이터를 보지 않는다 — 정정 (2026-08-07 · 절단문서 ②-17)

v1의 이 절은 「학생 신원은 안 본다」로 끝났다. **그 문장은 이 설계가 지킬 수 없는 약속이다.** §3-1이 스스로 적어 둔 대로 **학생은 작문·음성에서 제 이름·전화·회사·주소를 말한다** — 검수 대상인 `audio_ref`와 `transcript`가 바로 그 내용물이다. `display_name`을 안 여는 것은 **가명화**이고 익명화가 아니다. 아래 셋을 갈라 적는다.

| 층 | 무엇 | 상태 |
|---|---|---|
| **안 연다** | `learners` 전부(`display_name`·`contact`·복구 이메일·전화) · 제출물 중 `body_original`·`redaction_result`·`redaction_ver`·`capture_meta`·`image_refs`·`task_ref`·`task_schema_ver`·`schema_ver` · **`task_snapshot` 전문**(계약이 거기 **정답**을 두기로 했다 §3-3 — 과제 맥락은 키 2개만 투영: `task_instruction`·`task_prompt`) | ✅ 물리 — `engine.review_queue` 허용 목록(20260807190000 · **20260809050000**이 판을 화면이 성립하는 집합까지 올렸다) · 반대방향 장부 `tests/검수큐.test.js` |
| **줄일 수 없다** | `audio_ref`·`transcript`·`corrections.corrected_text` — **검수 대상 그 자체**다. 열 목록으로는 못 푼다 | 🔴 남는다 |
| **그래서 남는 통제** | 동의(제3자 열람 고지) · 수탁 계약(NDA) · 조회 감사(`staff_access_log`) · 최소 수집 | ⏳ 앞의 둘은 유호님 판정 자리 |

🔴 **`redaction_result`가 특히 위험하다** — 그 칸은 *가려낸 식별자 자체*를 담는다. 비식별의 산출물을 검수자에게 주면 비식별을 안 한 것보다 나쁘다. 뷰에서 뺐다.

⚠ **쓰기·번역 검수 화면이 서는 날 `body_original`·`task_snapshot` 전문이 필요해진다.** 그때 뷰에 더한다 — 그 자리가 「사람이 원문을 읽는다」를 다시 판정할 지점이고, 지금 미리 열어 두면 그 판정이 영영 안 일어난다.

🔴 **`event_id`는 2026-08-09에 판으로 들어왔다 — c8의 제외 판정을 뒤집었다**(`20260809050000_review_c10`). c8의 사유는 「학생 사건 줄 전체로 가는 지렛대 — 화면은 `submission_id`로 돈다」였고 **화면만 보면 맞다.** 틀린 것은 그 판을 읽는 자가 화면만이 아니라는 것이다: 승격 사슬의 멱등키가 **원본 `event_id` 하나**라(발주 §3) 승인 Edge Function이 그 값을 얻어야 하는데, 판에 없으면 **직원 통로가 `engine.submissions` 원표를 직접 연다.** 그 통로가 한 번 열리면 `body_original`·`redaction_result`는 같은 쿼리 한 줄 거리다 — **지렛대를 판 안에 두는 쪽이 원표를 여는 쪽보다 좁다.** ⚠ 정직하게 남는 한계: 이 판은 「Edge Function이 브라우저로 무엇을 내보내는가」를 못 막는다. `event_id`는 그리는 값이 아니라 **서버가 승격에 쓰는 값**이고, 그 경계 검사는 Fn이 서는 날 그 자리에 붙는다(오늘 검수 Fn은 0개다).

#### ③ 세션 폐기 — §4-2 🔴가 남긴 선택지 둘 중 **ⓑ로 확정**

`active`·`revoked_before`를 헬퍼가 **매 요청** 읽는다(`learner_self`와 같은 모양의 `staff_self` 정책 1개가 자기 행 읽기를 연다):

```sql
create or replace function engine.current_staff() returns engine.staff
  language sql stable security invoker set search_path = engine, public as
$$ select s.* from engine.staff s
    where s.auth_user_id = auth.uid()
      and s.active
      and to_timestamp((auth.jwt()->>'iat')::bigint) >= coalesce(s.revoked_before, '-infinity') $$;
```

- 해임·유출 = `active=false` **한 줄** → 만료 안 된 access token도 다음 요청에서 죽는다. 재발급 = `revoked_before=now()` → 옛 토큰만 죽고 계정은 산다.
- **ⓐ(짧은 TTL)를 안 고른 이유**: 검수는 1시간 연속 작업이라 TTL이 짧으면 작업 중 재로그인이 반복되고, **그래도 그 TTL만큼 창이 남는다.** ⓑ는 창이 0이다.
- 🔑 **이 헬퍼가 학생 쪽 미확정(§4-2 🔴)도 함께 닫는다** — `learners`에 같은 두 칸을 둔다. 두 축에 다른 규칙을 두면 갈라진다.

#### ④ 감사 로그 — 새 표는 **1개뿐**(`staff_access_log`)

| 무엇 | 어디 | 상태 |

| 로그인·로그아웃·비번 변경 | `auth.audit_log_entries`(Supabase 내장) | ✅ 만들지 않는다 |

## 6. 판정이 필요한 2건

### 6-1. `intervention.delivered` 외 2종 = **✅ c4로 해소** (2026-08-06)

`event_type` 값목록의 정본은 계약 파일이다. 이 문서가 제안한 3종(`intervention.delivered`·`correction.viewed`·`data_use.granted`)은 **c4 개정으로 값목록에 들어갔다**(9종 · 값 추가는 하위호환 · C0 §6). 제약 이름도 `_c3`→`_c4`로 갈아끼웠고 회귀가 계약 버전에서 이름을 파생시킨다(`tests/L0스키마.test.js`). 🔴 **DB에 c3가 이미 적용된 상태라면 재실행으로는 안 바뀐다** — `supabase/L0_스키마.sql` 헤더 ⚠의 `alter` 3쌍으로 이행하고, 꼬리 확인 ④가 `_c3`를 드러낸다.

c4가 함께 낸 자리(코어엔진 §9 빈 곳 ①⑤ — S1 전 필요한 원본 고리): `task_snapshot`(계약에 없던 것 합류) · `selection_reason` · `rejected_all` · `cited_refs`. 물리 열은 §3-2·§3-3에 이미 있거나(위) payload 규격으로 간다.

### 6-2. `privacy_class` — **열을 만들지 않는 쪽으로 해소** (v1.1 판정)

c3는 이 열을 **「보류·유호님 확정 대기」**로 뒀다. 근거: A-10 ⑤의 3등급은 유호님 기각(*"동의·출처만 넣어. 「이 행을 훈련에 써도 되나」를 말하는 열은 넣지마"*)과 글자 그대로 부딪치고, A-10은 그 기각 **뒤에** 쓰인 AI 설계안이라 기각을 넘지 못한다. **그 지적이 맞다.**

**그런데 유호님께 다시 여쭐 필요가 없다 — 열 없이 같은 일을 할 수 있다:**

- **원본 이벤트는 언제나 개인용**이다. 신분을 나타내는 열 자체를 두지 않는다(= 기각과 충돌 0 · append-only와도 정합 — 원본 행을 나중에 `UPDATE`하지 않는다).
- **회사 통계**는 원본의 신분을 바꾸는 게 아니라 **별도의 비식별 집계 산출물**로 만든다.
- **훈련 데이터 승격**은 미래의 `data_use.granted` 이벤트 / `dataset_item`으로 — **행이 아니라 사건으로** 기록한다.

즉 **3관문은 유지하되 「원본 데이터의 신분을 바꾸는 방식」을 버린다.** v1의 `privacy_class` enum·컬럼은 이 문서에서 제거했다.

**승격 사건이 남겨야 할 것**(2026-08-06 보강 · 같은 날 정정 — `dataset_item` 최소 필드 · DDL은 E1/E3 착수 때 · 전부 미래 사건이라 소급 불가분 없음): 원본 `event_id` 목록 + **승격 시점의 비식별 정규화 결과를 별도의 불변 산출물로 보관**하고 `artifact_ref` + `content_hash` + `serializer_ver` 기록(🔴 해시는 「내용이 같은가」를 검증하는 지문일 뿐 **삭제·변경된 내용을 복원하지 못한다** — 원본은 철회 시 지워질 수 있으므로 해시만 남기는 안은 재현 불가다. 철회 대상은 산출물에서도 삭제·제외하되, 내용 대신 「어느 데이터셋·모델에서 제외됐는지」 **계보만** 남긴다) · `dataset_ver` · 목적 + 당시 `consent_ver` **+ 근거 `consent_id`·검사 시각**(`consent_ver`만으로는 어느 동의 행을 근거로 통과했는지 고정되지 않는다 — consents 테이블 PK 그대로) · 비식별·라벨링 규칙 버전(계약 파일 버전 축) · 라벨 출처(teacher_gold 등) · **승인자(사람)·승인 시각**(자동 승격 금지 — 사람 확정 고리) · 평가 결과 참조(A-7 평가셋) · **제외·철회·롤백도 사건으로**(A-6 철회 전파와 조인). 하나라도 빠지면 「무엇으로 학습했나」를 나중에 재현하지 못한다.

적용 순서:

1. Codex의 작업본이 독립 검수와 CI를 통과하고 정확한 커밋으로 고정된 뒤, 유호님이 대상 프로젝트와 적용을 승인한다.
2. 클로드가 `supabase/확인_적용전상태.sql`을 원격으로 실행해 상태를 다시 읽는다.
3. 아래 세 갈래 중 하나만 택한다. 판별되지 않으면 실행하지 않는다.

| 적용 전 상태 | 처리 |
|---|---|
| 완전히 빈 DB | 합본을 한 번 실행한다 |
| 지문이 정확히 일치하는 낮은 판 c3 또는 c4 | 합본 안의 해당 `ALTER` 경로를 실행한다 |
| 부분·혼합·불명 상태 | 중단하고 원인을 보고한다 |

현재 개발 DB의 **이력 없는 c6**는 네 번째 부트스트랩 갈래가 아니다. 유호님이 확정한 「지우고 다시 붓기」에 따라, 승인 뒤 클로드가 `drop schema engine cascade`를 실행하고 빈 상태를 재확인한 다음 이력 테이블을 포함한 합본을 한 번 적용한다. 이력 없는 c6를 그대로 발견했다면 부분·혼합·불명 상태로 중단한다.

4. 클로드가 저장소에 커밋된 정확한 합본만 `tools/원격SQL.js`로 실행한다. 편집창에서 즉석 수정하지 않는다.
5. 성공 응답, 오류, 시간 초과, 응답 유실 중 어느 결과라도 **곧바로 재실행하지 않는다.** 먼저 `supabase/확인_적용후상태.sql`로 실제 상태와 현재 version·checksum을 읽는다.
6. 사후 판정과 이력 행이 모두 맞을 때만 완료로 기록한다. 아니면 중단하고 트랜잭션 롤백 여부와 실제 상태를 확인한 뒤 전진 수정 또는 승인된 롤백을 택한다.
7. 적용 커밋·마이그레이션 version / 프로젝트·환경 / 실행 전 상태 / 실행 결과 / 적용 후 구조·RLS·현재 checksum / 롤백·전진 경로의 기록 6종을 남긴다.

| 사후 확인 결과 | 재실행 | 다음 행동 |
|---|---|---|
| 판정 통과 + 현행 version·checksum 일치 | 안 함 | 적용 완료 기록 |
| version 없음 + 사전·사후가 모두 완전히 빈 DB | 그 두 상태가 모두 일치할 때만 허용 | 같은 합본을 한 번 실행 |
| version 없음 + 사전·사후가 모두 정확한 c3 또는 c4 | 해당 판 지문이 다시 전부 일치할 때만 허용 | 같은 합본의 부트스트랩 경로를 한 번 실행 |
| version 없음 + 부분·혼합·불명 상태 | 금지 | 상태를 보존하고 중단·보고. 이력 없는 c6도 이 갈래다 |
| 다른 version 또는 같은 version의 checksum 불일치 | 금지 | 원인을 확정하고 새 전진 마이그레이션 작성 |
| SQL 오류·시간 초과·응답 유실·빈 응답 | 즉시 금지 | 사후 확인을 한 번 실행한 뒤 위 행으로 판별 |

| `learning_events` | **`retry_of_event_id`** | 교정 후 다시 낸 고리. 🔑지금 설계의 필드가 거의 전부 「입력·성향」인데 **결과 변수는 이것 하나뿐**이다 — 없으면 엔진이 상관만 배우고 처방을 못 배운다 |
| `corrections` | `l1_source_phrase`·`rubric_scores`·`review_listened_ms` | 몽골어 관용구 매핑 키 / 🔴강사만 매길 수 있는 첨삭 점수 / 검수자 1명 체제의 유일한 품질 계기판 |
| `learners` | `home_aimag`·`gender`·`goal_track` | 가입 **1회** 문항. 뒤에 붙이면 재적 전원에게 다시 물어야 한다. 🔑`gender`는 **화자 편향을 재는 유일한 계기판**이고 학습 라벨이 아니라 **분포 점검 전용**이다 |
| `submissions.task_snapshot` (기존 열) | `challenge_id`·`addressee_level`·`target_phonemes`·`prompt_seed` | 전부 **과제 설계 시점에만 아는 값** — 「그때 학생이 본 것」의 정의에 그대로 들어맞아 새 열이 필요 없다 |

**테이블 추가 2 — 둘 다 학습 내용을 한 글자도 담지 않는다**

- **`engine.pipeline_jobs`** — 큐. `learning_events`는 append-only이고 `submissions`의 원문은 불변인데 큐는 **본질적으로 가변**이다(집었다 놓았다 재시도한다). 불변 테이블에 가변 열을 섞으면 「원문을 갱신하지 않는다」가 지켜지는지 아무도 못 본다.
  - 신뢰성은 **3개면 실패 모드가 덮인다**: `for update skip locked` + `lease_until`(죽은 워커가 행을 영원히 잠그지 않게) + `attempt_id`(늦게 돌아온 유령 워커의 쓰기를 가른다). 🚫claim·heartbeat·DLQ·outbox 풀세트는 파일럿 10~20명·단일 워커에 과하다 — 규모가 오면 그때.
  - **배선(20260807120000)**: `submissions` insert 가 **같은 트랜잭션**에서 job 을 만든다(`submissions_enqueue_job` 트리거 + 기존 행 backfill · 사후 확인의 `잡없는제출=0`) — 「제출은 섰는데 처리 job 이 없는 영구 고아」(sol P0)가 물리적으로 안 생긴다.
  - ⚠ `status`는 **처리 상태이지 학습 사실이 아니다.** 「검수됐다」의 진실은 언제나 `corrections` 행이고 `'verified'`는 그 캐시다. 어긋나면 `corrections`가 맞다.
- **`engine.daily_activity`** — 접속 0인 날. 이벤트 테이블만 보면 **「안 왔다」와 「기록이 안 됐다」가 똑같이 생긴다** — 이탈 신호를 영영 못 배운다. 부재는 이벤트가 아니라서 append-only 통로로는 담기지 않는다.

### 9-3. 폐기 ≠ 철회 (동의문 위반 수리)

`docs/동의_문구_v1.md`는 철회 시 **「보관 중인 녹음을 모두 삭제」**를 약속한다. 발주서 v1은 `파일 삭제 정책 없음(폐기=소프트)` 한 줄로 그것을 덮어썼다 — **문구가 거짓말이 되는 자리**다. 두 사건을 갈랐다:

| | 폐기 `discarded` | 철회 `revoked` |
|---|---|---|
| 누가 | 검수자 (교육상 판정) | 학생·보호자 (권리 행사) |
| 통로 | `pipeline_jobs.status='discarded'` | `consents.revoked_at` + **`data_use.revoked` 이벤트**(c5 신설) |
| 파일 | **남긴다** — 노이즈도 강건성 학습 재료다 | **지운다** + `submissions.audio_deleted_at` 기록 |
| 행 | 남는다 | **남는다** — 통계·계보는 유지하고 내용만 없어진다 |
| 이미 학습된 것 | 해당 없음 | 되돌리지 않는다(동의문이 그대로 고지). 계보만 남긴다(§6-2 승격 사건) |

> 🔑 **승격이 사건이면 철회도 사건이어야 대칭이 맞는다** — 한 축으로 두면 「지웠어야 할 것이 남는다」가 조용히 성립하고, 증상이 없어서 첫 감사 때까지 아무도 모른다.
#### 9-3-1. Storage 경로 규칙 (확정 · 🔴소급 불가)

**`{voice|image}/{learner_id}/{uuid}.{ext}`** — 비공개 버킷 **`learner-media`** 1개 · **첫 칸 뒤가 반드시 `learner_id`**.

> 구현 정본 = `lib/업로드경로.js`(발급 `functions/uploads` 와 수납 `functions/events` 가 **같은 파일을 동봉**해서 쓴다 — 두 곳에 적으면 갈라지고, 갈라지는 방향은 언제나 「통과」다). 회귀 = `tests/업로드경로.test.js` 12건 · 리허설 실왕복 `tools/업로드왕복시험.js` 12/12(2026-08-06 · 실제 PUT 후 `storage.objects` 에서 경로 확인).

| 갈래 | 판정 |
|---|---|
| 날짜 분할 `voice/YYYY/MM/` | ✗ — 한 학생의 파일을 **모든 달 폴더에 흩는다.** 손 삭제가 불가능해지고 동의문 약속이 그 순간 거짓이 된다 |
| `learner_id` 프리픽스 | ✓ — **안 바뀐다.** 폴더 하나가 곧 한 학생의 전부라 삭제가 1회다 |
| `student_code`(SYNK-001) 프리픽스 | ✗ — 사람이 읽기 쉽지만 **재발급되면 옛 코드 밑 파일이 미아가 된다.** 삭제 보증이 깨진다 |

- 🔴 **소급 불가** — 첫 업로드가 이 규칙 밖으로 나가면 그 파일은 규칙을 고쳐도 **안 옮겨진다.** C0 §4-2 초안이 `voice/2026/08/uuid.wav`(날짜 분할)였고, 그대로 구현됐으면 **첫 철회 요청 날 동의문이 거짓말이 되는 것을 그때 알았을 것**이다. Edge Function 구현 **전에** 못박는 이유가 이것이다.
- **이미지도 같은 규칙을 쓴다**(`image_refs` = 손글씨 답안). 동의문의 철회 문장은 「녹음」만 말하지만, 지울 수 없는 형태로 쌓아둘 이유가 없다 — 규칙은 넓게, 약속은 문서가 정한 대로.
- ⚠ 천장: 행 표식 열 이름은 `audio_deleted_at` 하나다(계약 c5 동결). 이미지까지 지운 경우도 이 칸이 진다 — 이름이 좁은 것이지 뜻이 좁은 게 아니다.
- 회귀 = `tests/철회경로.test.js` — C0 §4-2와 이 절이 **같은 규칙을 말하는지**, 그리고 날짜 분할이 되살아나지 않는지.

#### 9-3-2. 철회 처리 절차 (유호님 손 = **폴더 삭제 1회** · 나머지는 원격)

> 순서를 바꾸지 않는다 — **파일을 먼저 지우고 표식을 남긴다.** 반대로 하면 「지웠다고 적혀 있는데 파일이 있는」 상태가 생기고, 그건 감사에서 가장 나쁜 모양이다.

> 🔑 **1·3·4는 `tools/원격SQL.js`로 AI가 돈다**(2026-08-06 통로 신설 · 3은 쓰기라 `--적용` + 유호님 명시 승인). **2번만 유호님 손에 남는다** — 그 도구는 Management API의 SQL 엔드포인트라 **Storage 파일은 못 지운다.** 아래는 원격이 막혔을 때도 그대로 성립하는 손 절차로 적는다(둘이 같은 문장이어야 갈라지지 않는다).

1. **누구인지 확정** — 나온 `learner_id`를 복사한다.
   ```sql
   select learner_id, student_code, display_name from engine.learners where student_code = '@@학생코드@@';
   ```
2. **파일 삭제 — 🙋유호님** Supabase 대시보드 → Storage → **버킷 `learner-media`** → `voice/` → 복사한 `learner_id` **폴더 삭제**. `image/` 도 같은 폴더 이름으로 한 번 더.
   - 🔑 버킷 이름을 적는 이유: 대시보드는 **버킷을 먼저 고르게** 한다. 이름이 없으면 이 줄은 철회 요청이 실제로 온 날 「어디를 열어야 하지」에서 멈춘다 — 그날은 알아볼 시간이 없다.
3. **표식·사건 기록** — **바꾸는 곳은 첫 줄 학생 코드 하나뿐이다.**
   ```sql
   with 대상 as (
     select learner_id from engine.learners where student_code = '@@학생코드@@'   -- ← 여기만 바꾼다
   ), 사건 as (
     insert into engine.learning_events
       (learner_id, event_type, occurred_at, idempotency_key, consent_ver, consent_id, schema_ver)
     select d.learner_id, 'data_use.revoked', now(), 'revoke:' || current_date,
            (select consent_ver from engine.consents c
              where c.learner_id = d.learner_id order by agreed_at desc limit 1),
            (select consent_id from engine.consents c
              where c.learner_id = d.learner_id order by agreed_at desc limit 1), 'c5'
       from 대상 d
     on conflict (learner_id, idempotency_key) do nothing
     returning event_id
   ), 동의 as (
     update engine.consents set revoked_at = now()
      where learner_id in (select learner_id from 대상) and revoked_at is null
     returning consent_id
   ), 파일 as (
     update engine.submissions set audio_deleted_at = now()
      where audio_deleted_at is null
        and event_id in (select event_id from engine.learning_events
                          where learner_id in (select learner_id from 대상))
     returning submission_id
   )
   select (select count(*) from 사건) as 철회사건,
          (select count(*) from 동의) as 동의철회,
          (select count(*) from 파일) as 파일표식;
   ```
   - **한 문장이라 전부 되거나 전부 안 된다** — `begin`/`commit`을 사람이 챙기지 않는다.
   - 두 번 Run해도 안전하다(`on conflict do nothing` + `is null` 조건) — 두 번째는 전부 `0`이 나온다.
   - 🔴 **`consent_ver`가 null이라 오류가 나면** 그 학생의 `consents` 행이 없다는 뜻이다. 그건 철회 절차 문제가 아니라 **동의 없이 수집된 행이 있다**는 더 큰 발견이다 — 덮지 말고 그 사실부터 본다.
   - 🔴 **`@@학생코드@@`는 실재할 수 없는 값이라야 한다.** 초판은 예시로 `'SYNK-001'`을 적었는데 그건 **1번 학생의 진짜 코드**다 — 치환을 잊고 그대로 돌리면 **엉뚱한 학생의 동의를 철회한다.** 지금 형태는 잊으면 0행이라 아무 일도 안 일어난다(실패가 안전한 쪽으로 떨어진다). 회귀 = `tests/철회경로.test.js`.
4. **확인** — 2번 폴더가 실제로 없는지 눈으로 1회, 3번 결과 숫자 3칸이 0이 아닌지 1회.

- **이미 학습에 들어간 것은 되돌리지 않는다** — 동의문이 그렇게 고지한다. 계보만 남는다(§6-2 승격 사건과 대칭).
- **원격 실행 시**: 3번은 위 블록의 `@@학생코드@@`를 치환한 사본을 임시 파일로 써서 `node tools/원격SQL.js <파일> --적용`. 🔴**저장소에 학생 코드가 박힌 .sql 파일을 커밋하지 않는다** — 다음 철회 때 낡은 코드로 도는 함정이 되고, 학생 식별자가 이력에 남는다.
- ⏳ 남은 자동화는 **2번(파일 삭제)뿐**이다 — 원격SQL은 DB만 닿는다. Storage까지 원격으로 하려면 `service_role` 키가 따로 필요하고, **첫 철회 요청 전까지는 유호님 클릭 1회로 충분하다**(D5 앱 내 삭제 버튼은 「오픈 전 필수 아님」 확정). 위 4단계는 원격이 없어도 그대로 성립한다.
- ⚠ **서명 꼬리**: 업로드 서명은 발급 후 **10분** 산다(`functions/uploads`) — 3번(철회 SQL)을 Run 한 시점에 이미 발급된 서명으로 파일이 늦게 도착할 수 있다. 2번 폴더 삭제를 3번 **10분 뒤에 한 번 더 확인**하면 꼬리까지 잡힌다. (행 쪽은 `functions/events`가 철회 뒤 수집을 시각 주장과 무관하게 거절한다 — 20260807120000. 절차 순서 자체의 경쟁 조건 수리는 sol P0 후속.)
- ⚠ 3번의 `insert`는 `learning_events`의 NOT NULL 열이 늘면 깨진다. **기준선 마이그레이션이 선 날 이 블록을 한 번 Run해 본다**(§8 절차 뒤).

### 9-4. 이미 c3·c4가 적용된 DB가 있다면 (ALTER 경로)

> ⏱ **시점 표식(2026-08-07 추가)**: 아래 문단은 **c5 당시**(어느 DB에도 안 섰던 때)의 판단 근거다.
> 지금은 운영(`Synk Core`)·리허설 둘 다 이력표를 들고 **`20260807060000`(계약 c8)**까지 서 있으므로,
> 여기서 말하는 「없다」는 현재 상태가 아니다. 현재 상태의 물증은 `supabase/확인_적용후상태.sql` 실행 결과다.

기준선은 **아직 어느 DB에도 적용되지 않았으므로**(당시) c5를 alter 체인이 아니라 기준선 파일에 흡수했다 — 행이 0인 스키마에 마이그레이션 이력을 쌓는 건 비용만 남는다. **다만 이미 선 DB가 있다면 재실행으로는 안 바뀐다**(`create table if not exists`가 문장을 통째로 건너뛴다). 그 경우 순서:

1. `alter type engine.job_status` 대신 **enum·새 테이블 2개를 먼저** 만든다(`create type` / `create table if not exists` 그대로 통과).
2. 열 추가 — `alter table … add column if not exists` (위 §9-2 표의 열 전부).
3. CHECK 3개 **이름째 교체**: `drop constraint …_c4` → `add constraint …_c5`(새 값목록) + `submissions_task_format_c5` 신설.
4. 꼬리 확인 ④가 `_c4`를 드러내면 3번이 안 돈 것이다.

### 9-5. 발주서 체크포인트 처분

- **[CHK-1] 해소** — `student_id` FK 대상 = `engine.learners(learner_id)`. 제출은 `learning_events.learner_id`로 붙는다. 재적 명단 소스 = `learners` 그 자체.
- **[CHK-2] 해소** — `error_types`는 새 축을 발명하지 않고 계약 `오류태그`를 쓴다. c5가 **`화용:공손성` 1개만** 추가했다(문화적 무례는 `높임:상대` 등급과 다른 실패다). 🚫`mishearing`은 태그로 만들지 않는다 → 전사 2칸의 diff가 그 자리다.
- **[CHK-3] 해소** — RLS = §4-3 그대로. **학생 직접 INSERT는 없다**(발주서 v1의 「학생: 자기 행 insert」는 L0 위반). 앱 → Edge Function(service_role) → DB.
- **[CHK-4] 해소** — 가입 3문항 = `learners` 3열(§9-2).
- **[CHK-5] 유지** — 동의 6항목 개정 완료 전 실학생 수집 금지(파일럿 시작 게이트 · 유호님 몫).

## 10. c6 — 문서에만 있던 불변을 DB가 지킨다 (2026-08-06 · 외부 이종 검토 2차)

> **발단**: 정본 6종(이 문서·`supabase/L0_스키마.sql`·계약 JSON·코어엔진 설계·C0·발주서)을 실제로 읽은 외부 검토가 P0 14·P1 2를 냈다. 1차 검토는 요약만 보고 나와 절반이 오독이었지만, **2차는 인용한 줄번호가 전부 실측과 맞았다.** 기각한 것은 1건뿐이다(개입·성과 파생 테이블 선행 구축 — §1이 이름을 지목해 금지한 항목 · 🚫재론).

### 10-1. 구조 결함 3건 — 전부 「조용히」 성립한다

### 10-2. 불변 트리거 3 — 두 문서가 다른 말을 하면 기계가 판정한다

- `submissions` — **이미 값이 있는 원본 칸만** 차단. 20260807120000 조각이 선언(「최대 소급 불가」)과 자물쇠의 범위를 일치시켰다(sol P0): `body_original`·`transcript`·`task_snapshot`·`audio_ref`·`image_refs`·`capture_meta`·`transcript_verified`, `occurred_at`은 전면. **c10에서 `due_at`·`due_ver` 두 칸이 합류했다** — 마감을 사후에 늘릴 수 있으면 「놓쳤다」가 조용히 지워지고, 그 순간 그 열이 지키려던 것을 그 열이 깨뜨린다. 통째로 막지 않는 이유는 그대로다 — 철회의 `audio_deleted_at`(§9-3-2)과 뒤에 채워지는 전사·검수 결과(null→값 첫 채움)가 함께 죽는다.

## 11. c7 — 병렬 코퍼스(몽골어↔한국어)가 설 자리 (2026-08-06 · 유호님 지시)

**발단** — 유호님 질의 「수집할 때 코퍼스 시스템은 만들어놨나」. 실측해보니 셋 중 둘은 **이름만 「코퍼스」가 아닐 뿐 이미 서 있었고**, 하나는 판정된 적 없이 빠져 있었다.

| 코퍼스 | c6까지 | 어디에 |
|---|---|---|
| 학습자 | ✅ 통로 있음 | `submissions.body_original` → `corrections.corrected_text` + `error_tags[]` + `explanation` + `skills`(태그 체계) |
| 음성 | ✅ 통로 있음 | `audio_ref`·`audio_duration_sec`·**`transcript`/`transcript_verified` 2칸**·`stt_segments`·`stt_confidence` + `learners`(화자 메타) |
| **병렬(몽↔한)** | ❌ **없음** | — 「코퍼스」라는 말이 이 저장소 전체에 0건이었다. 기각된 게 아니라 **논의가 없었다** |

### 11-1. 새 테이블은 만들지 않는다 (F124를 두 번 겪지 않는다)

`task_snapshot`(그날 학생이 본 몽골어 제시문) · `body_original`(학생의 한국어 답) · `corrected_text`(검수 확정 한국어) — **정렬 3원쌍이 이미 있었다.** 없던 것은 「이 행을 병렬 쌍으로 읽어도 되는가」를 가르는 축 하나뿐이다.

- `task_format` +1 **`번역`**. 축이 없으면 자유발화 답안과 번역 답안이 한 칸에 섞이고, 섞이면 「몽골어 원문이 있는 답」과 「없는 답」을 나중에 못 가른다 — c5가 낭독/자유발화를 가른 것과 **같은 계열**이다.
- 🔴 `l1_source_phrase`(corrections)는 이 자리를 대신하지 못한다: **검수자가 사후에 추정해 적는 칸**이라 학생 본인의 L1 의도가 아니고, 몽골어 제시문이 없는 과제에도 붙는다.

### 11-2. 축만으론 코퍼스가 안 선다 — 왼쪽을 DB가 요구한다

값만 늘리면 「번역인데 몽골어 원문이 없는 행」이 통과한다. 그건 코퍼스가 아니라 그냥 한국어 문장이고, **제시문은 그 순간에만 남길 수 있다**(문항이 수정되면 학생이 무엇을 보고 답했는지 사라진다 — c4가 `task_ref`/`task_snapshot`을 가른 바로 그 이유).

```sql
add constraint submissions_translation_source_c7 check (
  task_format is distinct from '번역'
  or nullif(btrim(task_snapshot->>'mn'), '') is not null
)
```

- **몽골어 제시문의 자리 = `task_snapshot.mn`**(비어 있지 않은 문자열). 이 키가 규약이다 — 다른 이름으로 넣으면 행이 거절된다.
- 한국어 정답이 함께 제시된 과제라면 `task_snapshot.ko`에 둔다(선택 · CHECK 밖).
- 🔑 검증기(`lib/이벤트검증.js`)는 아직 이 조건을 모른다 — 값목록만 계약에서 파생한다. Edge Function이 서는 날 **친절한 오류**를 그쪽에 붙인다(지금은 DB가 최후 방어선으로 막고, 앱은 23514를 본다).

### 11-3. CHECK는 이름째 `_c6` → `_c7`

값이 바뀐 것은 `task_format` 하나지만 접미는 판 전체를 통일한다 — 같은 이름이 두 값목록을 가리키면 확인 ④가 어느 판인지 못 가른다. 새 제약 `submissions_translation_source_c7`이 하나 늘었고, 확인 ④ 기대 목록도 함께 늘었다(**개수의 정본은 기준선 파일 꼬리다** — 여기 숫자를 적지 않는다).

### 11-4. 체인의 첫 「두 번째 조각」 — 합본을 보던 검사 3개가 낡아 있었다

`supabase/L0_스키마.sql`은 `migrations/` 조각을 **이어붙인 생성물**인데, 회귀들이 「합본 전체」를 보고 있었다. 조각이 하나일 땐 합본=조각이라 구별할 이유가 없었지만, 두 번째 조각이 붙자 옛 조각의 **죽은 제약**과 **낡은 확인 블록**이 현행으로 읽혔다.

- 「CHECK 이름이 계약 버전을 단다」 → 뒤 조각이 `drop`한 이름은 뺀다. 탐지력은 그대로다 — drop을 빠뜨리면 그 이름이 살아 남아 잡힌다.
- 「확인 ④ 기대 줄」·「사후 확인 사본」 → **마지막** 조각의 블록이 현행이다(첫 블록을 보면 사후 확인 파일을 갱신해도 영원히 「갈라졌다」가 나온다).
- 「단일 명시 트랜잭션」 → **조각마다** 1개로. 앞 조각이 커밋된 상태는 이력상 정합하고(뒤 조각만 고쳐 다시 부으면 된다), 조각 단위로 보면 **감싸지지 않은 조각 하나**를 잡아내 검사가 오히려 강해진다.
- 신설: 「파일명 ↔ `migration_version` ↔ 앞 조각의 `base_version`이 한 줄로 이어진다」 — 어긋나면 로컬은 초록인데 **원격에서만** 「이력에 그 판이 없다」로 중단된다.

변이 6/6 잡음(원본 거짓양성 0).

### 11-5. 남은 것

## 12. c8 — 교정을 가리킬 이름 `correction_id` (2026-08-07 · P0 §10-A-11 해소)

### 12-1. 무엇이 비어 있었나

`correction.viewed`·`correction.responded`는 c4부터 값목록에 있었는데 **어느 교정에 대한 것인지 지목할 필드가 없었다.** `retry_of_event_id`는 사건→사건(재제출) 고리라 그 자리를 대신하지 못한다. 그래서 검증기(`lib/이벤트검증.js`)가 `correction.viewed: []`로 **비워 둔 채** 서 있었다 — 없는 이름을 필수로 걸면 앱은 못 보내는데 검증은 전건 거부하기 때문이다.

🔴 이건 미룰 수 있는 종류가 아니다. S1-8(교정 열람·응답)은 §6이 「학습이 일어났다」의 **유일한 직접 신호**로 지목한 자리이고, 고리 없이 쌓인 열람 사건은 나중에 어느 교정이었는지 **복원되지 않는다**(그때만 얻을 수 있는 값 — c4가 `task_snapshot`을 가른 것과 같은 계열).

### 12-2. 🔴 새 테이블 0 · **새 정본 0**

「이 교정은 누구 것인가」의 답은 이미 DB 안에 하나 있다 — RLS 정책 `learner_self_corrections`가 `corrections → submissions → learning_events → learner_id`로 걷는 그 사슬이다.

그래서 `corrections`·`submissions`에 `learner_id`를 **복제하지 않았다.** 복제하면 「누구 것인가」의 정본이 둘이 되고, 어긋나는 날 RLS와 FK가 서로 다른 답을 낸다 — §3-3이 `seen_at`·`responded_at`에서 이미 겪은 「정본이 두 군데」다.

그 결과 교차 학생 연결(§10 · c6)은 복합 FK가 **아니라** 같은 사슬을 걷는 트리거로 막는다:

| | 복합 FK 경로 | 트리거 경로(채택) |
|---|---|---|
| 필요한 것 | `unique (learner_id, correction_id)` → `corrections.learner_id` 신설 | 없음 |
| 대가 | 「누구 것인가」 정본이 둘 | `disable trigger`로 꺼질 수 있다 |
| 판정 | ❌ 복제를 **강제**한다 | ✅ 꺼짐·사라짐은 확인 블록의 기대트리거가 드러낸다 |

### 12-3. 자리를 비워 두지 않는다

CHECK `learning_events_correction_target_c8` = 두 사건에는 **반드시 있고**, 나머지에는 **반드시 없다**. 「있어도 되고 없어도 되는」 칸이면 S1은 여전히 교정 단위로 판정할 수 없고, 엉뚱한 사건에 붙은 값은 나중에 집계에서 조용히 섞인다.

⚠ 이 CHECK는 기존 행을 검사한다 — 위반 행이 있으면 조각이 그 자리에서 **실패한다**(의도한 실패다. 「운영 0행일 것이다」에 기대지 않는다).

🔑 같은 판정이 **SQL과 JS 두 곳**에 적힌다(한쪽은 CHECK, 한쪽은 검증기). 목록을 하나에서 파생시킬 수 없는 자리라, 갈라지면 빨개지는 회귀를 뒀다(`tests/L0스키마.test.js`) — 갈라진 상태의 증상은 「저장이 안 된다」뿐이라 원인이 안 보인다.

### 12-4. CHECK는 이름째 `_c7` → `_c8` (살아 있는 8개 전부)

초안은 반대로 갔다: 「c8은 어떤 값목록도 바꾸지 않으니 이름을 갈 이유가 없고, 갈면 `learners`·`staff`의 c7 제약까지 건드리게 된다」. 그럴듯했지만 틀렸고 `tests/L0스키마.test.js`가 그 자리에서 빨개졌다. 그 가드가 지키는 것은 값목록의 최신성이 아니라 **판이 조용히 미적용되는 것**이다 — `create table if not exists`는 테이블이 있으면 문장을 통째로 건너뛰므로, 이름이 그대로면 「c8 계약 + c7 물리」가 초록으로 보인다. 값은 한 글자도 안 바꾸고 이름만 갈았다.

### 12-5. 체인은 판 이름이 아니라 **바로 앞 조각**에 건다

초안의 `base_version`은 `20260806210000`(engine_c7)이었는데, 그 뒤로 `auth_c7`·`staff_c7`·`temp_code_c7` 세 조각이 더 붙어 있었다. 그대로면 c8이 그 셋을 건너뛴 DB 위에서도 서고, 이 조각이 `staff`·`learners` 제약을 갈므로 그건 실패가 아니라 **오염**이다. 같은 실수를 확인 블록에서도 했다 — c7 조각의 기대열을 베껴 뒤 세 조각이 낸 **13열이 통째로 빠졌다**(합본 생성기의 diff가 잡았다). 두 번 다 원인이 하나다: **베낄 곳은 「그 판의 첫 조각」이 아니라 「바로 앞 조각」이다.**

### 12-6. 남은 것

- **원격 적용은 아직이다** — 유호님 승인 사안이고, 절차는 §11-5와 같다(`supabase/확인_적용후상태.sql` 사후 확인 · 기대 `11·11·7·0·0·3·1·0·0·1` — 2026-08-07 `20260807190000_review_c8` 뒤 · 그전 조각까지만 부었다면 `11·11·8·0·0·3·1·0`).

- 교정을 **실제로 보여주고 되돌려 받는** 화면은 S1 몫이다. 지금 선 것은 **받을 자리**다.

## 14. 시즌 회고 ③④ — 라벨과 그 근거 (2026-08-12 · 조각 `20260812170000_season_review_c11`)

> 정본 = SYNK-appsscript `docs/시즌회고_설계.md` v3 §3-2·§4·§5·§7.
> §13 이 **왼쪽**(학생이 선언한 것)을 세웠고, 이 절은 **오른쪽과 라벨**을 세운다.

### 14-1. 🔴 왜 이것이 엔진에 중요한가 — 8축은 «부호»를 모른다

`학습자상태.v6` 은 「지금 어떤가」만 안다. 리듬이 빨라졌는지, 끈기 값이 0.7 인지는 세지만
**「그게 이 학생에게 좋은 방향이었나」는 어떤 축도 모른다.** 그 부호(sign)를 아는 것은 사람뿐이고,
사람이 그것을 말하는 자리는 회고 하나뿐이다 — 그래서 이 표가 **엔진의 유일한 라벨 생산자**다.

그러므로 특징(`record_snapshot`)과 라벨(`verdict`)이 **같은 행**에 있어야 한다. 갈라 두면 나중에
짝을 못 맞추고 — 창이 밀리므로 **원리상** 못 맞춘다(아래 14-3) — 그릇은 화면으로 끝나고 엔진엔
한 방울도 안 닿는다.

### 14-2. `engine.season_review` — 학생×시즌 1행

| 칸 | 무엇 |
|---|---|
| `record_snapshot` | 회고를 **연 순간** 굳힌 오른쪽 전부 — `axes_전반`·`axes_후반`·`season_totals` + `추정판` + 창 경계 |
| `verdict` | 강사 판정 **3갈래** `closer`/`same`/`redirected` · `note` = 한 줄 사유 · `decided_by`·`decided_at` |
| `verdict_by_self` | **학생 자신의** 같은 3갈래(✅유호님 채택 08-12) · `null` = 안 눌렀다 |
| `opened_by`·`opened_at` | 누가 언제 열었나(= 굳힌 시각) |

🔴 **판정이 3갈래인 이유**: 2갈래로 접으면 목적 변경이 「멀어짐」이 되고 엔진은
**「학생이 목적을 바꾸는 것 = 나쁜 신호」**를 배운다 — 철학 Ⅱ-4(목적 변경은 정상 경로)를
정면으로 뒤집는 학습이 조용히 일어난다.

🔴 **판정칸이 둘인 이유**: 강사만 판정하면 회고는 성적표가 되고, 학생만 판정하면 근거가 없다.
**둘이 갈리는 행이 가장 값진 신호**다(`자기인식축`의 유일한 대조군). `null`(안 눌렀다)과
「눌렀는데 강사와 같다」는 **다른 값**이다 — 접으면 그 대조군의 분모가 거짓이 된다.

### 14-3. 🔴 왜 «굳히나» — 창 30일이 판정을 배신한다

축은 창 30일인데 시즌은 2달이다. 회고 시점에 그냥 조회하면 8축이 덮는 것은 시즌의 **뒤 절반**뿐이고,
한 달 뒤 다시 조회하면 창이 밀려 **다른 숫자**가 나온다. 「가까워졌다」고 적힌 행 옆에 나중에
조회한 숫자를 붙이면, 그 숫자는 **그 판정을 낸 사람이 본 적 없는 숫자**다.

처방은 창을 «늘리는» 것이 아니라 **구간을 달리해 두 번 부르는** 것이다(설계 §4-2):

| 층 | 어떻게 | 무엇을 답하나 |
|---|---|---|
| `axes_전반` | `as_of`=시즌 중간 · `창`=앞 절반 | 앞 한 달에 어땠나 |
| `axes_후반` | `as_of`=시즌 끝 · `창`=뒤 절반 | 뒤 한 달에 어땠나 |
| `season_totals` | 시즌 구간 전체(제출·배정·교정/열람·급수·`exam.result`) | 시즌 전체 규모 |

창 60일 한 번은 이 문제를 **못 푼다**(평균으로 접혀 「잘하다 말았다」와 「못하다 살아났다」가 같은
값이 된다 — 회고가 판정할 것이 정확히 그 **방향**이다). 그리고 창 30 은 과제 배정·답장 맥락이
**매일** 쓴다. 🚫 두 층 평균 · 🚫 `학습자상태` 기본 `창일수` 변경 · 🚫 회고 전용 축 함수 신설.

⚠ 구간은 **`season` 행의 날짜에서 계산**한다(창 30 고정 금지 — 시즌 2달이 정확히 60일이 아니다).
⚠ `교정열람률` 의 분모는 그 시즌에 «난» 교정이라 끝자락 교정을 다음 시즌에 보면 낮게 나온다 —
분자·분모를 **둘 다** 굳혀 나중에 다시 잴 수 있게 뒀다(비율만 담으면 그 왜곡이 영영 안 보인다).

### 14-4. 물리로 못박은 것 넷

1. **`season_review_once_c11`** — `unique (learner_id, season_id)`.
2. **`season_review_verdict_c11`·`season_review_self_c11`** — 3갈래 값목록. 정본은 `lib/회고.js` 의
   `판정목록` 이고, 없앨 수 없는 사본이라 **회귀가 둘을 대조**한다(`tests/회고.test.js`).
3. **`season_review_decided_c11`** — 판정·사유·주체·시각이 **한 벌로** 선다(빈 사유 포함 거절).
   갈라지면 「판정은 있는데 누가 언제 했는지 모르는 행」이 서고, 그 행은 라벨로 못 쓴다.
4. **트리거 둘** — `season_review_freeze`(굳힌 근거·대상·연 시각 **불변** + `verdict` 가 있는 행의
   `verdict_by_self` 개서 금지 = 메아리 차단) · `season_review_protect`(**삭제 금지**).
   ⚠ `verdict`·`note` **개서는 허용**한다 — 잘못 누른 강사에게 남는 통로가 「지우고 다시」뿐이면
   그 우회가 정상 통로가 되는데 삭제는 막혀 있어 길이 아예 없다. 고친 사실은 `decided_at` 갱신과
   `staff_access_log` 한 줄로 남는다.

### 14-5. 통로 셋 (`functions/teach`) — 순서가 규격이다

| 경로 | 누가 | 무엇 |
|---|---|---|
| `GET retro/open` | 강사 | 시즌을 **서버가 고르고**(나침반이 있는데 회고가 아직 확정 안 된 **가장 오래된** 시즌) 근거를 **굳힌다**. 이미 굳혔으면 **재계산 0** |
| `POST retro/self` | 학생 | 3갈래 클릭 1. 강사 판정 **뒤**면 409 `SELF_AFTER_JUDGE` |
| `POST retro/judge` | 강사 | 3갈래 + 한 줄. `verdict_by_self` 는 **안 건드린다** |

🔑 통로가 갈라져 있는 것이 곧 「학생이 먼저」다 — 하나로 합치면 순서가 화면 규약으로만 남는다.
🔑 굳힌 근거는 **응답에서 `evidence_refs` 를 벗겨** 내보낸다(행에는 남는다 · `event_id` 를 브라우저로
보내지 않는 `gold/queue` 와 같은 축).
거절: `RETRO_NOT_DUE`(회고할 시즌 없음) · `RETRO_NOT_OPENED`(열지 않고 판정) · `SELF_AFTER_JUDGE` — 셋 다 409.

### 14-6. 계약판을 **안 올린다** (c11 유지)

새 값목록 0(`verdict` 3갈래는 이 표 안에만 산다) · `learning_events` 0 · 새 `event_type` 0 ·
기존 engine 표 변경 0. 🚫 회고를 사건 층에 넣기 — 시즌당 1회·사람이 읽는 자료라 `쓰는사건`·검증기·
CHECK·8축을 다 건드리면서 **엔진은 그 값을 못 센다**(세는 축이 없다).
