> **자리**: M0 마일스톤의 「계약 동결 3종」 중 **N1(learning_events)의 물리 스키마**.
> **담당** = 클로드 레인(L0) · **동결 조건** = 아래 §7 · **DDL 실물** = `supabase/L0_스키마.sql` · **적용 절차** = §8.
> **v1.3(2026-08-06)** — **수집 파이프라인이 이 스키마 위에 앉는다(§9 신설 · 계약 c4→c5).** 파이프라인 발주서가 신설했던 3테이블은 전부 여기 있던 것의 재발명이었다(GPT 이종 검수 `failed_p0` · F124). 테이블을 늘리는 대신 **없던 축만** 냈다: 전사 2칸 · 큐 · 접속 0 · 가입 3문항 · 철회 이행 표식.
> **v1.2(2026-08-05)** — 유호님 답 2건으로 §7의 남은 전제가 둘 다 풀렸다: Supabase 프로젝트 ✅생성 · 학생 로그인 = **학원 발급 코드** → §4 확정.
> **필드 정본은 이 문서가 아니다** — 「무엇이 필수인가」의 정본은 `계약/수집_교정_계약.json` **c3 `learning_events` 절**, 라이브 구현 필드의 정본은 SYNK-appsscript `docs/학습데이터_스키마감사.md`. **이 문서는 물리 스키마(테이블·타입·인덱스·RLS)만 정한다**(코어엔진 부록 A-0 · c3 `정본_경계`).
>
> **v1.1 개정 (2026-08-05)** — 외부 적대 검토(P0 5건·중요 6건) + **c3 계약 정합**. v1은 c2 기준으로 쓰였고, 그 사이 다른 세션(`local_8f792d12`)이 c3를 커밋하며 이름을 L0 컬럼명으로 통일했다. **c3가 상위 계약이므로 이 문서가 맞춘다.**

## 0. 계약 코드 — 혼선 정리

| 코드 | 무엇 | 정본 위치 | 확정 주체 |
|---|---|---|---|
| **P0** | 제품 계약 — 사용자 시나리오·완료 조건·S1 선정 | `docs/개발_분업.md` §2 | **유호님** |
| **F0** | 개발 기반 1회 — CI·환경 분리·Mock | 〃 | 상호 검수 |
| **C0** | **API 계약** — 앱↔서버 인터페이스·타입·예시 payload·오류 규격·버전 정책 | 〃 | Codex 소비자 승인 후 동결 |
| **L0** | **DB 스키마** — Postgres DDL·권한(RLS) | **이 문서** | 클로드 레인 |
| **M0** | 마일스톤 — 계약 동결 3종(N1+엔진 조항+N2) | SYNK-appsscript `docs/앱기능_역할별_전수분석.md` | — |

⚠ **C0와 L0는 다르다**: C0는 *앱이 서버에 무엇을 보내고 받는가*, L0는 *그것이 DB에 어떤 모양으로 앉는가*. 둘이 1:1이면 **DB 구조가 API로 새서 나중에 못 바꾼다** — 잇는 자리는 서버 함수 한 층이다.

## 1. 설계 기준선

> **원본 증거는 지금, 파생 상태는 나중.** 원본이 있으면 파생은 언제든 다시 계산되지만, 원본이 없으면 파생을 **영원히 못 만든다**(코어엔진 §10).

**지금 만든다 (6개)**: `learners` · `learning_events` · `submissions` · `corrections` · `skills` · `consents`

**지금 안 만든다**: `learner_skill_state`·`learner_misconceptions`·`memory_items`·`interventions`·`outcomes`·`learner_profile` — 전부 위 6개에서 계산되는 **파생**. 🚫V3식 선행 구축 + E0 「엔진 전용 코드 0줄」 유지.

**「지금 아니면 못 얻는 것」 4가지** — 이것만 예외로 지금 넣는다:
1. **`intervention_id` + 개입 내용** — AI가 무엇을 했는지. ID만으로는 성과를 못 읽는다(§3-2 · v1.1 보강).
2. **`task_snapshot`** — 그때 학생이 본 문제. 문항이 수정되면 영원히 복원 불가(§3-3 · v1.1 신설).
3. **`level_snapshot`** — 그때의 급수.
4. **선택 로그** — 무엇이 제시됐고 무엇을 추천했나.

## 2. 공통 규약

| 규약 | 내용 | 근거 |
|---|---|---|
| `schema_ver` | 모든 행이 **몇 번 규격으로 적혔는지** 스스로 들고 있다. 계약 파일 `버전`(현 `c3`)을 저장 시 자동 기입 | A-8 · **유호님 확정 "넣어"** |
| 시각 2종 | `occurred_at`(발생) ≠ `ingested_at`(서버 수신) | c3 봉투 |
| `idempotency_key` | **`(learner_id, key)` 복합 유일** — 전역 유일이면 두 학생이 같은 키를 만드는 날 뒤에 온 제출이 조용히 거부된다(중복 방지 장치가 데이터 손실 장치가 된다) | v1.1 수정 |
| `correlation_id` | 한 수업·한 세션의 흐름 | c3 봉투 |
| **append-only** | `learning_events`는 갱신·삭제하지 않는다. 잘못된 사건은 **정정 이벤트를 새로 쌓는다** | v1.1 원칙 |
| 원문 불변 | 학생 원문은 고치지 않는다(오류가 곧 데이터). 교정은 항상 별도 행 | 제품방향 불변식 2 |
| 어휘 통제 | `task_type`·`event_type`·`error_tags`·`learner_response`·`verdict`는 **계약 파일 값목록만** 허용. DB `CHECK` + **CI가 계약 JSON과 대조** | v1.1 (중요-1) |

```sql
create schema if not exists engine;

create type engine.actor_kind  as enum ('learner','ai','teacher','system');
create type engine.source_kind as enum ('explicit','teacher','observed','inferred');
```

> ⚠ **`privacy_class` enum은 두지 않는다** — §6-2 참조. v1에 있던 3등급 enum을 v1.1에서 **제거**했다.

## 3. 테이블 정의

### 3-1. `engine.learners`

```sql
create table engine.learners (
  learner_id      uuid primary key default gen_random_uuid(),
  auth_user_id    uuid unique references auth.users(id),  -- Supabase 인증과 직접 연결
  student_code    text unique not null,      -- SYNK-001 · 사람이 부르는 이름표 (⚠비밀 아님 · §4-1)
  display_name    text,
  contact         text,
  birth_year      int,
  level_current   text,
  created_at      timestamptz not null default now(),
  schema_ver      text not null
);
```

> **`auth_user_id`를 두는 이유**(v1.1): 권한을 JWT의 커스텀 클레임(`student_code`)에 걸면 토큰이 오래되거나 재발급될 때 불일치가 난다. `auth.uid()`에 직접 걸면 그 위험이 사라진다(§4).
>
> ⚠ **식별자는 여기 「구조화된 형태로만」 산다.** 학생이 작문·음성에서 자기 이름·전화번호·회사·주소를 말할 수 있으므로 **`submissions`와 오디오에도 우발적 식별정보가 들어온다** — 외부 모델 호출 전 비식별 검사를 거치고 그 결과를 기록한다(§3-3 `redaction_ver`). v1의 "식별자가 사는 유일한 곳" 문구는 부정확해서 고쳤다.

### 3-2. `engine.learning_events` — 모든 학습 행동 (N1)

```sql
create table engine.learning_events (
  event_id         uuid primary key default gen_random_uuid(),
  learner_id       uuid not null references engine.learners(learner_id) on delete cascade,
  event_type       text not null,     -- 계약 c3 값목록 (CHECK)
  task_type        text,              -- 계약 c3 값목록 — 어느 과업 통로인가 (v1.1 합류)
  actor_kind       engine.actor_kind not null default 'learner',
  occurred_at      timestamptz not null,
  ingested_at      timestamptz not null default now(),
  correlation_id   uuid,
  idempotency_key  text not null,
  session_id       uuid,
  content_id       uuid,
  skill_ids        text[] not null default '{}',
  level_snapshot   text,
  intervention_id  uuid,
  model            text,
  prompt_ver       text,
  policy_ver       text,              -- 어느 개인화 정책이 이 개입을 골랐나 (v1.1)
  consent_ver      text not null,
  degraded         boolean not null default false,
  payload          jsonb not null default '{}',
  schema_ver       text not null,
  unique (learner_id, idempotency_key)
);

create index on engine.learning_events (learner_id, occurred_at desc);
create index on engine.learning_events (event_type, occurred_at desc);
create index on engine.learning_events (intervention_id) where intervention_id is not null;
create index on engine.learning_events using gin (skill_ids);
```

**`event_type` 값목록** — **계약 c4 9종**(2026-08-06 개정 · §6-1 해소 · 정본은 계약 파일이고 여기는 파생):
`submission.created` · `quiz.answered` · `choice.selected` · `correction.responded` · `correction.viewed` · `preference.stated` · `session.abandoned` · `intervention.delivered` · `data_use.granted`

**`task_type` 값목록**(c3): 숙제제출 · 다시쓰기 · 퀴즈응답 · 대화턴 · 발화녹음 · 출석발화

> **왜 둘 다 필요한가**(c3 판정 승계): `event_type`은 *무슨 일이 일어났나*, `task_type`은 *어느 과업이었나*. 합치면 숙제 제출과 다시쓰기가 똑같이 `submission.created`가 되어 구분이 사라진다.

#### `intervention.delivered` — AI가 무엇을 했는지 (v1.1 신설 · P0-2)

v1은 `intervention_id`만 남기면 된다고 했으나 **절반만 맞다.** ID는 조인 고리일 뿐이고, **그 ID가 가리키는 개입 내용이 없으면 나중에 「무엇이 효과 있었나」를 물을 수 없다.** 새 테이블은 필요 없고 이벤트 하나면 된다:

```json
{
  "intervention_id": "uuid",
  "strategy_code": "hint_only",
  "output_ref": "…",
  "target_skill_ids": ["skill-ko-grammar-particle-topic"],
  "difficulty": 2,
  "rationale": "직전 3턴 조사 오류 연속 · 설명 길이 선호=짧게",
  "cited_refs": ["note-particle-eun-neun@2026-07-30"]
}
```

> 🔑 **`cited_refs` = c4 추가**(코어엔진 §9 ⑤ 호출·인용 로그): 그 답에 **실제로 실린** 지식 노트다. `model`·`prompt_ver`(컬럼)은 어느 엔진이 말했나이고 이쪽은 **무엇을 읽고 말했나**다. 없으면 지식 노트가 틀린 것을 알아도 **이미 나간 답**을 못 찾아 미래분만 고친다(A-5 회수의 전제). ⏳ 채우기는 **RAG 도입일 첫날부터 강제** — 나중에 붙이면 그 사이 답들은 영원히 출처 미상이다.

성과 이벤트는 **같은 `intervention_id`를 가리킨다.** 그래야 상태→개입→반응→성과가 이어진다(코어엔진 §10 성과 배선).

> 🔴 **v1의 오류 정정**: talk의 **일반 AI 답변을 `corrections`에 넣기로 했던 것은 틀렸다.** 대화 응답과 오류 교정은 다른 개념이다 — 일반 답변은 `intervention.delivered`, **실제 오류 교정만** `corrections`로 간다.

#### `payload` 규격 — `choice.selected`

```json
{ "choice_dimension": "correction_style",
  "options_shown": ["즉시 자세히 설명","힌트만 제공","수업 후 정리"],
  "position": 2, "recommended_option": "즉시 자세히 설명",
  "selected_option": "힌트만 제공", "changed_selection": false,
  "latency_ms": 4200, "skipped": false,
  "selection_reason": "설명이 길면 수업 흐름이 끊겨서", "rejected_all": false }
```

> 🔑 **`recommended_option`과 `position`이 없으면 학생의 진짜 선호와 「우리가 밀어준 것」이 영원히 구분되지 않는다** — 편향된 데이터로 개인화를 학습하게 된다.

> 🔑 **c4 추가 2**(코어엔진 §9 ③ 실물 대조 · 2026-08-06): `selection_reason`은 **그 순간에만 있는 것**이다 — 나중에 물으면 회상 편향으로 다른 답이 나온다. 매번 묻지 않는다(질문 총량 상한). `rejected_all`은 **`skipped`와 다른 사건**이다: 건너뜀은 무반응이고 전량 거절은 「우리 안이 다 틀렸다」다. 합치면 개인화가 「관심 없음」과 「전부 아님」을 같은 신호로 배운다. 전량 거절이면 `selected_option`은 null이고 이때 `selection_reason`이 가장 값지다.

#### payload 검증 — 봉투와 내용을 두 층으로 (v1.1 · P0-5)

`payload jsonb default '{}'`만으로는 `event_type='choice.selected'` + `payload={}` 같은 **빈 껍데기 이벤트가 그대로 저장된다.** 그래서:

- **공통 봉투** = 모든 이벤트 필수 (컬럼으로 DB가 강제)
- **이벤트별 payload** = 해당 이벤트에만 필수 (**서버 함수에서 Zod/JSON Schema 검증** — 검증 통과분만 DB로)
- payload 모양의 버전은 **`payload.ver` 필드**로 싣는다 — 🔴 **이벤트 이름에 붙이지 않는다**(`choice.selected.v1` 표기는 C0 §4-1로 정정 · 2026-08-06). 이름에 박으면 `event_type` 값목록이 판마다 늘어나 CHECK와 집계 축이 함께 깨진다. 모양이 바뀌면 `ver`만 오르고 과거 행은 옛 `ver`로 남는다.

**테이블은 늘지 않는다.** 검증은 Edge Function 한 곳(A-2 서버측 강제와 같은 자리).

### 3-3. `engine.submissions` — 학생 산출물 원문

```sql
create table engine.submissions (
  submission_id   uuid primary key default gen_random_uuid(),
  event_id        uuid not null references engine.learning_events(event_id) on delete restrict,
  task_type       text not null,
  task_ref        text,              -- 원본 콘텐츠 ID
  task_snapshot   jsonb,             -- 🔴 그때 학생이 본 것 (질문·보기·정답·지시문)
  task_schema_ver text,              -- 스냅샷 모양의 버전
  body_original   text,              -- ⚠ 원문 — 절대 갱신하지 않는다
  audio_ref       text,              -- 음성 원본 (보존 무제한 · 유호님 확정 08-04)
  transcript      text,
  transcript_state text,
  redaction_ver   text,              -- 외부 모델로 나가기 전 비식별 검사 버전
  redaction_result jsonb,            -- 무엇이 가려졌나
  occurred_at     timestamptz not null,
  schema_ver      text not null
);
```

> 🔴 **`task_snapshot`이 v1.1의 최대 신설**(P0-3). v1은 `숙제ID·숙제문항 → task_ref`를 1:1이라 썼는데 **틀렸다** — `task_ref`는 참조고 `숙제문항`은 스냅샷이다. **2년 뒤 문제가 수정되면 그때 학생이 무엇을 보고 답했는지 영원히 알 수 없다.** 계약이 문항 스냅샷을 필수로 요구하는 이유가 이것이고, 파생이 아니라 **그 순간에만 얻을 수 있는 원본 증거**다. **c4에서 계약 파일에도 합류**했고(c3에는 이 필드가 없어 `task_ref`가 둘을 겸하고 있었다) 라이브 대응은 `task_ref: [숙제ID]` / `task_snapshot: [숙제문항, 문제]`로 갈랐다.
>
> **필수 4 + 버전**: 질문 · **보기(오답 선택지 포함)** · 정답 · 지시문, 그리고 문항 버전(`task_schema_ver`는 스냅샷 *모양*의 버전이므로, 문항 자체의 판은 스냅샷 안에 넣는다). 🔴 **보기를 빠뜨리면 「왜 그 오답을 골랐나」를 영원히 못 묻는다** — 오답 선택지는 개념 진단의 재료 그 자체다(코어엔진 §9 ② 개념 매핑을 나중에 해도 되는 유일한 근거가 이 스냅샷의 완전성이다).
>
> ⚠ **실측(2026-08-06)**: 라이브 `quiz_log`는 `문제`·`정답`은 남기지만 **보기와 문항 버전을 안 남긴다**(`퀴즈ID`·`유형`·`문제`·`고른답`·`정답`·`정답여부`·`확신도`). 새 앱은 위 규격대로 채우고, **라이브 열 보강은 별건**이다 — 학생 0명 구간이라 S1 차단자는 아니지만 개원(2027-02) 전에는 닫아야 소급 불가 손실이 안 생긴다.
>
> **`learner_id`를 두지 않는다**(v1.1 · 중요-6): v1은 `event_id`와 `learner_id`를 함께 뒀는데 **둘이 같은 학생인지 강제되지 않아** A학생 이벤트에 B학생 제출물이 붙을 수 있었다. 학생은 `event_id`를 통해 조회한다.
>
> 원문을 이벤트 payload에 넣지 않는 이유: ①원문은 불변, 이벤트는 계속 늘어난다 ②본문 검색·용량 특성이 다르다 ③철회 시 **원문만 지우고 통계는 남기는** 처리가 가능해진다(A-6).

### 3-4. `engine.corrections` — 교정 (생성 후 불변)

```sql
create table engine.corrections (
  correction_id    uuid primary key default gen_random_uuid(),
  submission_id    uuid not null references engine.submissions(submission_id) on delete restrict,
  reviewed_correction_id uuid references engine.corrections(correction_id),  -- 강사가 평가한 AI 교정
  actor_kind       engine.actor_kind not null,      -- 'ai' | 'teacher'
  corrected_text   text,
  error_tags       text[] not null default '{}',    -- 계약 23종 — 검증은 서버 (아래 정정)
  explanation      text,
  model            text,
  prompt_ver       text,
  reviewer         text,
  verdict          text,                            -- 계약 골든 판정 3값 (CHECK)
  verdict_reason   text,
  reviewer_confidence numeric(3,2) check (reviewer_confidence between 0 and 1),
  created_at       timestamptz not null default now(),
  schema_ver       text not null

```

> **가변 필드를 전부 뺐다**(v1.1 · P0-4). v1은 여기에 `seen_at`·`learner_response`·`responded_at`을 뒀는데, `learning_events`에도 `correction.responded`가 있어 **정본이 두 군데**가 됐다 — 앱이 한쪽만 쓰거나 서로 다른 값을 쓸 수 있다. 이제:
> - `corrections` = 교정 **결과 자체**, 생성 후 불변
> - `correction.viewed` 이벤트 = 학생이 **본** 사건
> - `correction.responded` 이벤트 = **채택·무시·수정** 사건
> - 「현재 상태」가 필요하면 나중에 이벤트에서 계산(파생)
>
> 🔴 **`error_tags`에 DB CHECK를 걸지 않는다**(v1.2 정정 — v1.1은 `(CHECK)`라 적었다). 배열 CHECK는 23개 태그 리터럴을 DDL에 복제해 **계약 파일과 이중 정본**을 만든다. 스칼라 값목록(`event_type`·`task_type`·`verdict`)은 c3에 동결돼 바뀌면 c4라는 명시적 개정을 거치므로 CHECK로 박았지만, **오류 태그 23종은 아직 다듬어지는 어휘**라 DB 제약으로 굳히면 마이그레이션만 잦아진다. → 태그 검증은 서버(계약 파일이 정본). ⚠ 그래서 **박아둔 3개가 계약과 갈라지는 것**은 회귀가 막는다(`tests/계약.test.js` · 변이 5/5 실측).
>
> **`reviewed_correction_id` 신설**: 여러 모델이 같은 제출물을 교정하면 **강사 판정이 어느 교정에 대한 것인지 모호해진다** — 골든셋의 분모가 흐려지는 자리라 지금 못 박는다.
>
> **`confidence` 세 뜻 분리**(중요-2): 학생 확신도 = `learning_events.payload.confidence`(라이브 `quiz_log` 확신도 · 1~5) / 추정 신뢰도 = `estimator_confidence`(c3 명명 · 0~1) / 검수자 확신 = `reviewer_confidence`(여기 · 0~1). **한 이름으로 두면 「AI가 얼마나 확신하나」와 「학생이 얼마나 확신하나」가 한 칸에서 섞인다.**
>
> **`actor_kind`와 `source_kind`를 나눈 이유**(중요-3): `source_kind`는 *어떻게 알게 됐나*(추정 메타)이고, 교정에 필요한 건 *누가 했나*다. v1은 `source_kind=inferred`를 "AI가 교정했다"는 뜻으로 써서 두 의미가 섞였다.

```sql
create table engine.consents (

  learner_id    uuid not null references engine.learners(learner_id) on delete cascade,
  consent_ver   text not null,
```

**서버가 이벤트 저장 전 반드시 확인한다**(v1.1 · 중요-5) — `consent_ver`가 단순 문자열이면 **동의한 적 없는 버전으로도 저장된다**:

```
agreed_at <= occurred_at
  AND (revoked_at IS NULL OR occurred_at < revoked_at)
  AND event.consent_ver = 그 학생의 유효한 consent 버전
```

> ⚠ **의도적으로 여기서 멈춘다.** 외부 검토문의 동의 4종 분리는 **유호님이 「동의는 전 버전 그대로 최대한 간략하게」로 확정**(코어엔진 §6)해 기각됐다. 별도 `consent_ledger`도 만들지 않는다.

> ⚠ 만 14세 미만 법정대리인 동의는 이 구조와 **별도**로 필요하다(법적 검토 대기 · v18.9 트랙).

## 4. 인증·권한 (v1.2 확정 — 유호님 "학원 발급 코드로 가자" 2026-08-05)

**DDL 실물 = `supabase/L0_스키마.sql`**(이 절의 실행 가능한 형태). 아래는 그 근거다.

### 4-1. 🔴 로그인 코드는 `student_code`와 **별개의 비밀**이다

현행 `student_code`는 **`SYNK-001` 순번**이다(`엔진_폼리포트.js` `학생ID_포맷_`). 순번을 로그인 코드로 쓰면 `SYNK-002`를 넣는 것만으로 남의 계정에 들어간다 — **「학원 발급 코드」는 반드시 새 비밀**이어야 한다. `student_code`를 고엔트로피로 바꾸는 쪽은 기각이다(출석·포인트·리포트카드가 이미 물려 있고 매일 부르는 문자열 · memory `student-id-autoissue-2026-08-04`).

| | `student_code` | **로그인 코드** |
|---|---|---|
| 예 | `SYNK-001` | `K7M4-P2X9` |
| 성격 | 사람이 부르는 이름표 — **비밀 아님** | **비밀** (= 비밀번호) |
| 어디 사나 | `engine.learners.student_code` | **`auth.users`만** — 평문을 우리 표에 적지 않는다 |
| 바뀌나 | 안 바뀐다 | 분실·유출 시 재발급 |

**코드 규격**: `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` 32자집합(`I·O·0·1` 제외 — 손으로 옮겨 적는다) **8자** = 32⁸ ≈ 1.1조. ⚠ **순번·생년·전화번호에서 만들지 않는다** — 추측 가능해지는 순간 이 설계 전체가 무너진다.

**표기형 ≠ 정규형**(둘을 안 나누면 반드시 갈라진다):

| | 값 | 쓰는 곳 |
|---|---|---|
| **표기형** | `K7M4-P2X9` | 학생에게 보여주고 인쇄하는 형태 (하이픈은 읽기 편하라고) |
| **정규형** | `K7M4P2X9` | **하이픈 제거 + 대문자 8자** — 인증에 실제로 쓰는 유일한 형태 |

앱은 입력을 받는 즉시 정규형으로 바꾼다(하이픈·공백 제거 → 대문자). 8자라 Supabase 비밀번호 최소 길이(6)를 넘는다.

### 4-2. Supabase Auth 매핑 — 인증 서버를 따로 짓지 않는다

코드 로그인을 위해 **커스텀 JWT 발급기를 만들지 않는다.** Supabase 내장 이메일/비번 provider에 **합성 이메일**로 얹으면 `auth.uid()`가 그대로 나오고 §4-3 정책이 손대지 않고 작동한다.

| | 값 (코드가 `K7M4-P2X9`일 때) | 비고 |
|---|---|---|
| email | `k7m4p2x9@synk.invalid` | 정규형을 **소문자화** — Supabase가 이메일을 소문자로 저장하므로 |
| password | `K7M4P2X9` | **정규형 그대로(대문자)** — 비밀번호는 대소문자를 구분한다 |
| 앱 호출 | `signInWithPassword` 1회 | `signUp`은 앱에서 **절대 부르지 않는다** |

> 🔑 이 두 줄(소문자 이메일 / 대문자 비밀번호)이 실전에서 깨지는 자리다. **앱과 발급 도구가 같은 함수 하나를 공유한다** — 두 곳에 적으면 갈라지고, 갈라지면 증상은 「로그인이 안 된다」뿐이라 원인이 안 보인다.
>
> ⏳ **`@synk.invalid` 수용 여부는 미실측이다.** `.invalid`는 RFC 2606 예약 TLD라 **어떤 메일도 실제로 배달될 수 없어** 합성 주소로는 가장 안전하지만, Supabase 이메일 형식 검사가 거부할 가능성이 남아 있다. **계정 1개를 만들어보는 것이 판정 방법**이고, 거부하면 `@code.synk.mn`으로 간다(그때는 **그 도메인에 MX 레코드를 두지 않는다** — 우리는 메일을 안 보내지만, 받을 수 있는 상태로 두면 그 자체가 표면이다).

**계정은 학원이 미리 만든다** — 학생 등록 시 서버가 `auth.admin.createUser({ email, password, email_confirm: true })`(service_role). 대시보드에서 **공개 가입 OFF · 이메일 확인 OFF**. 그래서 등록되지 않은 코드로는 계정 자체가 생기지 않고, **코드 열거 공격의 입구가 닫힌다**.

**재발급 = 유일한 복구 경로**(분실·유출 공통 · 2026-08-06 보강): ①본인 확인(강사·원장 — 대면·보호자 채널) → ②발급 도구가 새 코드 생성 + `auth.admin.updateUserById`로 email·password **동시에** 교체(옛 코드 즉시 무효) → ③**전 세션 폐기**(완료조건은 아래 — 비밀번호 교체만으로는 이미 로그인된 기기가 죽지 않는다) → ④**감사 기록**(누가·언제·어느 learner·사유 — 발급 도구가 남긴다 · **평문 코드는 기록 금지**). `learner_id`·`auth_user_id`는 안 바뀌므로 **과거 학습 데이터가 끊기지 않는다**.

> 🔴 **③은 특정 API 호출이 아니라 보안 완료조건이다**(2026-08-06 정정 — 이전 판의 `auth.admin.signOut(user_id)` 표기는 오류: 실제 `admin.signOut`은 user_id가 아니라 그 사용자의 **유효한 JWT**를 받고, 세션·refresh token을 폐기해도 **이미 발급된 access token은 만료 시각까지 유효하다**). 완료조건: **재발급 즉시 옛 refresh token의 재사용이 차단되고, 만료 전인 옛 access token도 보호 데이터에 접근하지 못한다.** 구현 방식은 E1 인증 물리 설계에서 확정 — 선택지 둘: ⓐ access token 최대 잔존 시간을 짧게 설정하고 그 시간을 명시 ⓑ `revoked_before`/`session_generation` 표식을 두고 RLS·Edge Function이 이전 토큰을 즉시 거부. **아래 실측 테스트를 통과하기 전에는 완료로 보지 않는다**: 옛 코드 로그인 실패 · 옛 refresh token 갱신 실패 · **옛 access token의 학생 데이터 접근 실패** · 새 코드 로그인 성공 · 다른 학생 세션 무영향.

> ⛔ **앱에는 비밀번호 재설정·이메일 복구 UI를 두지 않는다** — `resetPasswordForEmail`은 `signUp`과 나란히 금지 목록이다(합성 주소로 발송돼 배달 불가 · 증상은 「메일이 안 온다」뿐). 학생 화면에 합성 이메일을 **노출하지 않는다** — 로그인 UI는 「학원 코드」 입력 하나다. 「다음 로그인 시 비밀번호 변경」류 절차는 이 설계에 **해당 없음**: 학생은 비밀번호를 만들지 않고, 회전은 재발급이 담당한다.

> ⚠ **평문 코드를 시트·문서에 모아두지 않는다.** 모아두는 순간 그 파일 하나가 전 학생 계정이 된다. 발급 도구가 화면에 1회 보여주고 끝내고, 분실은 재발급으로 푼다.

### 4-3. 정책 — 학생 토큰은 **읽기만**

쓰기는 전부 Edge Function(service_role)을 지난다 — payload 검증(§3-2)이 이미 거기 있어서 쓰기 통로를 둘로 만들 이유가 없다. 그래서 정책은 `select`만 존재한다.

```sql
-- 조인을 정책마다 다시 적으면 갈라진다 — 한 곳에서 파생시킨다
create or replace function engine.current_learner_id() returns uuid
  language sql stable security invoker set search_path = engine, public as
$$ select learner_id from engine.learners where auth_user_id = auth.uid() $$;

create policy learner_self_events on engine.learning_events for select to authenticated
  using (learner_id = engine.current_learner_id());
-- learners·submissions·corrections·consents 도 각각 (전문 = supabase/L0_스키마.sql §4)
```

**`engine` 스키마는 지금 API에 노출하지 않는다**(Settings → API → Exposed schemas 건드리지 않음). 앱은 Edge Function만 통하므로 노출이 필요 없고, 노출을 미루면 정책 실수의 영향 범위가 0이다. RLS는 **그래도 켠다** — 나중에 노출하는 날 잊어도 닫힌 채로 실패하게.

> **기본은 「아무도 못 본다」**이고 정책이 열어주는 것만 보인다 — 새 테이블에 정책을 잊으면 **닫힌 채로 실패**하지 열린 채로 새지 않는다.
>
> ⚠ **`service_role`은 RLS를 우회한다.** 서버 함수가 요청에 담긴 `learner_id`를 그대로 믿으면 RLS가 있어도 남의 데이터를 읽고 쓴다 — **서버는 항상 토큰에서 학생을 확정**한다.

### 4-4. 도전안 (기각 — 라벨 병기)

**Supabase Auth를 아예 안 쓰고** 앱이 코드를 서버에 보내면 서버가 자체 세션 토큰을 발급하는 안. Auth 설정 0이고 코드 형식도 자유롭다. **기각 근거**: RLS라는 마지막 방어선이 사라져 **서버 코드 버그 하나 = 전 학생 데이터 유출**이 되고, 세션 만료·갱신·폐기를 직접 짜야 한다. 지금 얻는 건 설정 몇 개고 잃는 건 「닫힌 채로 실패」라는 성질이다.

### 4-5. 강사·원장·운영자 인증 — **S1 범위 밖** (명시적 · 2026-08-06)

S1에는 **학생 읽기 전용 토큰만** 존재한다. 강사·원장·발급 도구 운영자의 로그인은 **미설계**이며, 운영 작업은 앱이 아니라 **service_role 도구(서버·로컬)**로만 한다 — **앱에 관리자 모드를 만들지 않는다**(운영 데이터에 닿는 경로가 앱에 없음). **N10(강사 검수 탭) 착수 전에 P0 설계로 승격**해 확정한다 — 그때 실이메일·SMTP 필요 여부도 함께 재판정한다(지금 SMTP 계획을 안 만드는 근거 = 학생 경로에 메일이 0이기 때문 · §4-2).

## 6. 판정이 필요한 2건

### 6-1. `intervention.delivered` 외 2종 = **✅ c4로 해소** (2026-08-06)

`event_type` 값목록의 정본은 계약 파일이다. 이 문서가 제안한 3종(`intervention.delivered`·`correction.viewed`·`data_use.granted`)은 **c4 개정으로 값목록에 들어갔다**(9종 · 값 추가는 하위호환 · C0 §6). 제약 이름도 `_c3`→`_c4`로 갈아끼웠고 회귀가 계약 버전에서 이름을 파생시킨다(`tests/L0스키마.test.js`). 🔴 **DB에 c3가 이미 적용된 상태라면 재실행으로는 안 바뀐다** — `supabase/L0_스키마.sql` 헤더 ⚠의 `alter` 3쌍으로 이행하고, 꼬리 확인 ④가 `_c3`를 드러낸다.

c4가 함께 낸 자리(코어엔진 §9 빈 곳 ①⑤ — S1 전 필요한 원본 고리): `task_snapshot`(계약에 없던 것 합류) · `selection_reason` · `rejected_all` · `cited_refs`. 물리 열은 §3-2·§3-3에 이미 있거나(위) payload 규격으로 간다.

### 6-2. `privacy_class` — **열을 만들지 않는 쪽으로 해소** (v1.1 판정)

c3는 이 열을 **「보류·유호님 확정 대기」**로 뒀다. 근거: A-10 ⑤의 3등급은 유호님 기각(*"동의·출처만 넣어. 「이 행을 훈련에 써도 되나」를 말하는 열은 넣지마"*)과 글자 그대로 부딪치고, A-10은 그 기각 **뒤에** 쓰인 AI 설계안이라 기각을 넘지 못한다. **그 지적이 맞다.**

**그런데 유호님께 다시 여쭐 필요가 없다 — 열 없이 같은 일을 할 수 있다:**

- **원본 이벤트는 언제나 개인용**이다. 신분을 나타내는 열 자체를 두지 않는다(= 기각과 충돌 0 · append-only와도 정합 — 원본 행을 나중에 `UPDATE`하지 않는다).
- **회사 통계**는 원본의 신분을 바꾸는 게 아니라 **별도의 비식별 집계 산출물**로 만든다.
- **훈련 데이터 승격**은 미래의 `data_use.granted` 이벤트 / `dataset_item`으로 — **행이 아니라 사건으로** 기록한다.

즉 **3관문은 유지하되 「원본 데이터의 신분을 바꾸는 방식」을 버린다.** v1의 `privacy_class` enum·컬럼은 이 문서에서 제거했다.

**승격 사건이 남겨야 할 것**(2026-08-06 보강 · 같은 날 정정 — `dataset_item` 최소 필드 · DDL은 E1/E3 착수 때 · 전부 미래 사건이라 소급 불가분 없음): 원본 `event_id` 목록 + **승격 시점의 비식별 정규화 결과를 별도의 불변 산출물로 보관**하고 `artifact_ref` + `content_hash` + `serializer_ver` 기록(🔴 해시는 「내용이 같은가」를 검증하는 지문일 뿐 **삭제·변경된 내용을 복원하지 못한다** — 원본은 철회 시 지워질 수 있으므로 해시만 남기는 안은 재현 불가다. 철회 대상은 산출물에서도 삭제·제외하되, 내용 대신 「어느 데이터셋·모델에서 제외됐는지」 **계보만** 남긴다) · `dataset_ver` · 목적 + 당시 `consent_ver` **+ 근거 `consent_id`·검사 시각**(`consent_ver`만으로는 어느 동의 행을 근거로 통과했는지 고정되지 않는다 — consents 테이블 PK 그대로) · 비식별·라벨링 규칙 버전(계약 파일 버전 축) · 라벨 출처(teacher_gold 등) · **승인자(사람)·승인 시각**(자동 승격 금지 — 사람 확정 고리) · 평가 결과 참조(A-7 평가셋) · **제외·철회·롤백도 사건으로**(A-6 철회 전파와 조인). 하나라도 빠지면 「무엇으로 학습했나」를 나중에 재현하지 못한다.

| `submissions` | `stt_segments`·`stt_confidence`·`code_switch_spans`·`audio_duration_sec`·`image_refs` | 세그먼트는 무음 하이라이트·검수 우선순위의 원천. `image_refs`는 손글씨 답안(TOPIK 쓰기) |
| `submissions` | **`audio_deleted_at`** | 철회 이행 표식(§9-3) |
| `learning_events` | **`retry_of_event_id`** | 교정 후 다시 낸 고리. 🔑지금 설계의 필드가 거의 전부 「입력·성향」인데 **결과 변수는 이것 하나뿐**이다 — 없으면 엔진이 상관만 배우고 처방을 못 배운다 |
| `corrections` | `l1_source_phrase`·`rubric_scores`·`review_listened_ms` | 몽골어 관용구 매핑 키 / 🔴강사만 매길 수 있는 첨삭 점수 / 검수자 1명 체제의 유일한 품질 계기판 |
| `learners` | `home_aimag`·`gender`·`goal_track` | 가입 **1회** 문항. 뒤에 붙이면 재적 전원에게 다시 물어야 한다. 🔑`gender`는 **화자 편향을 재는 유일한 계기판**이고 학습 라벨이 아니라 **분포 점검 전용**이다 |
| `submissions.task_snapshot` (기존 열) | `challenge_id`·`addressee_level`·`target_phonemes`·`prompt_seed` | 전부 **과제 설계 시점에만 아는 값** — 「그때 학생이 본 것」의 정의에 그대로 들어맞아 새 열이 필요 없다 |

**테이블 추가 2 — 둘 다 학습 내용을 한 글자도 담지 않는다**

- **`engine.pipeline_jobs`** — 큐. `learning_events`는 append-only이고 `submissions`의 원문은 불변인데 큐는 **본질적으로 가변**이다(집었다 놓았다 재시도한다). 불변 테이블에 가변 열을 섞으면 「원문을 갱신하지 않는다」가 지켜지는지 아무도 못 본다.
  - 신뢰성은 **3개면 실패 모드가 덮인다**: `for update skip locked` + `lease_until`(죽은 워커가 행을 영원히 잠그지 않게) + `attempt_id`(늦게 돌아온 유령 워커의 쓰기를 가른다). 🚫claim·heartbeat·DLQ·outbox 풀세트는 파일럿 10~20명·단일 워커에 과하다 — 규모가 오면 그때.
  - ⚠ `status`는 **처리 상태이지 학습 사실이 아니다.** 「검수됐다」의 진실은 언제나 `corrections` 행이고 `'verified'`는 그 캐시다. 어긋나면 `corrections`가 맞다.
- **`engine.daily_activity`** — 접속 0인 날. 이벤트 테이블만 보면 **「안 왔다」와 「기록이 안 됐다」가 똑같이 생긴다** — 이탈 신호를 영영 못 배운다. 부재는 이벤트가 아니라서 append-only 통로로는 담기지 않는다.

### 9-3. 폐기 ≠ 철회 (동의문 위반 수리)

`docs/동의_문구_v1.md`는 철회 시 **「보관 중인 녹음을 모두 삭제」**를 약속한다. 발주서 v1은 `파일 삭제 정책 없음(폐기=소프트)` 한 줄로 그것을 덮어썼다 — **문구가 거짓말이 되는 자리**다. 두 사건을 갈랐다:

| | 폐기 `discarded` | 철회 `revoked` |
|---|---|---|
| 누가 | 검수자 (교육상 판정) | 학생·보호자 (권리 행사) |
| 통로 | `pipeline_jobs.status='discarded'` | `consents.revoked_at` + **`data_use.revoked` 이벤트**(c5 신설) |
| 파일 | **남긴다** — 노이즈도 강건성 학습 재료다 | **지운다** + `submissions.audio_deleted_at` 기록 |
| 행 | 남는다 | **남는다** — 통계·계보는 유지하고 내용만 없어진다 |
| 이미 학습된 것 | 해당 없음 | 되돌리지 않는다(동의문이 그대로 고지). 계보만 남긴다(§6-2 승격 사건) |

> 🔑 **승격이 사건이면 철회도 사건이어야 대칭이 맞는다** — 한 축으로 두면 「지웠어야 할 것이 남는다」가 조용히 성립하고, 증상이 없어서 첫 감사 때까지 아무도 모른다.
> ⏳ **남은 실물 2건**: ①Storage 경로 규칙(동의문 §57이 지목한 부채 — 어디에 무엇이 있는지 모르면 **삭제를 실행할 수 없다**) ②철회 처리 도구(수동 · 앱 내 삭제 버튼은 D5로 이미 「오픈 전 필수 아님」 확정). 둘 다 첫 철회 요청 전까지.

### 9-4. 이미 c3·c4가 적용된 DB가 있다면 (ALTER 경로)

기준선은 **아직 어느 DB에도 적용되지 않았으므로** c5를 alter 체인이 아니라 기준선 파일에 흡수했다 — 행이 0인 스키마에 마이그레이션 이력을 쌓는 건 비용만 남는다. **다만 이미 선 DB가 있다면 재실행으로는 안 바뀐다**(`create table if not exists`가 문장을 통째로 건너뛴다). 그 경우 순서:

1. `alter type engine.job_status` 대신 **enum·새 테이블 2개를 먼저** 만든다(`create type` / `create table if not exists` 그대로 통과).
2. 열 추가 — `alter table … add column if not exists` (위 §9-2 표의 열 전부).
3. CHECK 3개 **이름째 교체**: `drop constraint …_c4` → `add constraint …_c5`(새 값목록) + `submissions_task_format_c5` 신설.
4. 꼬리 확인 ④가 `_c4`를 드러내면 3번이 안 돈 것이다.
