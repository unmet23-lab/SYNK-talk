# L0 데이터 계약 — Postgres 스키마 정본 (초안 v1)

> **자리**: M0 마일스톤의 「계약 동결 3종」 중 **N1(learning_events 단일 이벤트 계약)의 실물**.
> **담당** = 클로드 레인(L0) · **동결 조건** = Codex 소비자 승인(C0 절차 준용) · **적용 전제** = Supabase 프로젝트 생성(⏳유호님 1회).
> **필드 정본은 이 문서가 아니다** — 오류 태그·골든 판정·픽스처 규격의 정본은 `계약/수집_교정_계약.json`, 라이브 구현 필드의 정본은 SYNK-appsscript `docs/학습데이터_스키마감사.md`(v9.187). **이 문서는 그것을 Postgres 모양으로 옮긴 것이지 제3의 원천이 아니다**(코어엔진 부록 A-0).

## 0. 계약 코드 — 혼선 정리 (실측 2026-08-05)

세 정본이 서로 다른 코드를 써서 한 번 정리한다. **같은 것을 다르게 부른 게 아니라 실제로 층이 다르다.**

| 코드 | 무엇 | 정본 위치 | 확정 주체 |
|---|---|---|---|
| **P0** | 제품 계약 — 사용자 시나리오·완료 조건·S1 선정 | SYNK-talk `docs/개발_분업.md` §2 | **유호님** |
| **F0** | 개발 기반 1회 — CI·환경 분리·Mock·공통 앱 기반 | 〃 | 상호 검수 |
| **C0** | **API 계약** — 앱↔서버 인터페이스·타입·예시 payload·오류 규격·버전 정책 | 〃 | Codex 소비자 승인 후 동결 |
| **L0** | **DB 스키마** — Postgres DDL·권한(RLS) | **이 문서** | 클로드 레인 |
| **M0** | 마일스톤 — 「지금~L0 확정」에 계약 동결 3종(N1+엔진 조항+N2) | SYNK-appsscript `docs/앱기능_역할별_전수분석.md` | — |

⚠ **C0와 L0는 다르다**: C0는 *앱이 서버에 무엇을 보내고 받는가*, L0는 *그것이 DB에 어떤 모양으로 앉는가*. 둘이 1:1일 필요는 없고(오히려 아니어야 한다 — DB 구조가 API에 새면 나중에 못 바꾼다), **잇는 자리는 서버 함수 한 층**이다.

## 1. 설계 기준선 — 무엇을 지금 만들고 무엇을 안 만드는가

> **원본 증거는 지금, 파생 상태는 나중.** 원본이 있으면 파생은 언제든 다시 계산되지만, 원본이 없으면 파생을 **영원히 못 만든다**(코어엔진 §10).

**지금 만든다 (6개)**: `learners` · `learning_events` · `submissions` · `corrections` · `skills` · `consents`

**지금 안 만든다**: `learner_skill_state`·`learner_misconceptions`·`memory_items`·`interventions`·`outcomes`·`learner_profile` — 전부 위 6개에서 **계산되는 파생**이다. 🚫V3식 선행 구축 금지 + E0 「엔진 전용 코드 0줄」 유지.

**단 하나의 예외 = `intervention_id`.** 「AI가 이 학생에게 무엇을 했나」에 ID가 없으면 나중에 성과를 이어붙일 수 없다. 성과 계산은 늦어도 되지만 **ID와 시각은 그 순간에만 남길 수 있다** — 그래서 테이블이 아니라 `learning_events`의 컬럼으로 지금 넣는다.

## 2. 공통 규약 (모든 테이블)

| 규약 | 내용 | 근거 |
|---|---|---|
| `schema_ver` | 모든 행이 **자기가 몇 번 규격으로 적혔는지** 스스로 들고 있다. 계약 파일의 `버전`(현 `c2`)을 저장 시 자동 기입 | 부록 A-8 · **유호님 확정 "넣어"** |
| 시각 2종 | `occurred_at`(실제 발생) ≠ `ingested_at`(서버 수신). 오프라인 제출·재시도가 있는 앱에서 하나로 합치면 순서가 뒤집힌다 | A-10 |
| `idempotency_key` | 재시도가 같은 사건을 두 번 세지 않게. `UNIQUE` 제약으로 DB가 강제 | A-10 |
| `correlation_id` | 한 수업·한 세션의 흐름을 잇는 키 | A-10 |
| `privacy_class` | `personal_only`(그 학생에게만) / `company_aggregate`(가명화·집계) / `training`(삭제 요구 반영할 계보 보유) — **개인 데이터가 회사 엔진으로 넘어가는 경로는 이 세 등급으로만 열린다** | A-10 ⑤ · A-3 |
| 원문 불변 | 학생이 쓴 원문은 **고치지 않는다**(오류가 곧 데이터). 교정은 항상 별도 행 | 제품방향 불변식 2 |
| 식별자 분리 | 이름·연락처·생년 등 **식별자는 `learners`에만**. 다른 테이블은 `learner_id`만 본다 | A-3 |

```sql
-- 이름공간: 학습 데이터는 engine, 운영 데이터는 public
create schema if not exists engine;

create type engine.source_kind  as enum ('explicit','teacher','observed','inferred');
create type engine.privacy_class as enum ('personal_only','company_aggregate','training');
```

## 3. 테이블 정의

### 3-1. `engine.learners` — 학생 (식별자가 사는 유일한 곳)

```sql
create table engine.learners (
  learner_id      uuid primary key default gen_random_uuid(),
  student_code    text unique not null,        -- 기존 student_id(운영 학생ID)와 잇는 키
  display_name    text,                        -- 식별자 ⚠ 외부 모델로 나가지 않는다
  contact         text,                        -- 식별자
  birth_year      int,                         -- 식별자 ⚠ 소수 인원에선 날짜도 식별자다
  level_current   text,                        -- 현재 급수(운영 파생 — 스냅샷은 이벤트에 별도)
  created_at      timestamptz not null default now(),
  schema_ver      text not null
);
```

> `student_code`가 **기존 라이브 `student_id`와 새 앱을 잇는 유일한 다리**다. 분업 정본 §6이 "학생 식별 키를 기존 학생ID와 어떻게 잇는지는 C0에서 확정"이라 했고, **DB 쪽 답이 이 열**이다.

### 3-2. `engine.learning_events` — 모든 학습 행동 (N1 단일 이벤트 계약)

```sql
create table engine.learning_events (
  event_id         uuid primary key default gen_random_uuid(),
  learner_id       uuid not null references engine.learners(learner_id) on delete cascade,
  event_type       text not null,              -- 'submission.created' | 'quiz.answered' | 'choice.selected'
                                               -- | 'correction.responded' | 'preference.stated' | 'session.abandoned' ...
  occurred_at      timestamptz not null,
  ingested_at      timestamptz not null default now(),
  correlation_id   uuid,                       -- 한 수업 흐름
  idempotency_key  text not null,
  session_id       uuid,
  content_id       uuid,                       -- 어떤 문항·콘텐츠였나
  skill_ids        text[] default '{}',        -- 무엇을 재는 행동이었나 (3-5 참조)
  level_snapshot   text,                       -- 급수 스냅샷 ⚠ 지금 값이 아니라 그때 값 (소급 불가)
  intervention_id  uuid,                       -- AI가 무엇을 했나 — 성과를 나중에 붙일 유일한 고리
  model            text,                       -- 출처: 어느 모델이 만들었나
  prompt_ver       text,                       -- 출처: 어느 프롬프트 지문이었나
  consent_ver      text not null,              -- 동의: 어느 동의 아래 수집됐나
  degraded         boolean not null default false,  -- 강등 경로로 처리됐나 (부록 A-4)
  privacy_class    engine.privacy_class not null default 'personal_only',
  payload          jsonb not null default '{}',
  schema_ver       text not null,
  unique (learner_id, idempotency_key)   -- ⚠ 전역 unique 아님 (아래 주)
);

create index on engine.learning_events (learner_id, occurred_at desc);
create index on engine.learning_events (event_type, occurred_at desc);
create index on engine.learning_events using gin (skill_ids);
```

> ⚠ **`idempotency_key`는 학생 단위로만 유일하다.** 전역 unique로 두면 두 학생의 클라이언트가 같은 키를 만드는 날(키를 UUID가 아니라 「과업ID+시각」류로 조립하면 실제로 생긴다) **뒤에 온 학생의 제출이 조용히 거부된다** — 중복 방지 장치가 데이터 손실 장치가 된다. 키 생성 규격은 C0에서 못 박는다.
>
> ⚠ **이 테이블은 append-only다.** 이벤트는 갱신·삭제하지 않는다(잘못된 사건은 정정 이벤트를 새로 쌓는다). 동의 철회 시의 파기는 §6-6 절차를 따른다.

**`payload` 규격 — `choice.selected`**(A-10 ② 선택 로그 9항목):

```json
{
  "choice_dimension": "correction_style",
  "options_shown": ["즉시 자세히 설명", "힌트만 제공", "수업 후 정리"],
  "position": 2,
  "recommended_option": "즉시 자세히 설명",
  "selected_option": "힌트만 제공",
  "changed_selection": false,
  "latency_ms": 4200,
  "skipped": false
}
```

> 🔑 **`recommended_option`과 `position`이 없으면 학생의 진짜 선호와 「우리가 밀어준 것」이 영원히 구분되지 않는다** — 편향된 데이터로 개인화를 학습하게 된다. 최종 선택 하나만 저장하면 부족하다.

**`payload` 규격 — `quiz.answered`**: `{ "question": "...", "chosen": "...", "answer": "...", "is_correct": true, "confidence": 3, "attempt_no": 2 }`
— `confidence`(확신도)는 라이브 `quiz_log`에 이미 있고, `attempt_no`(재시도 차수)는 신규(성향 축 ②).

### 3-3. `engine.submissions` — 학생 산출물 원문

```sql
create table engine.submissions (
  submission_id   uuid primary key default gen_random_uuid(),
  event_id        uuid not null references engine.learning_events(event_id) on delete restrict,
  learner_id      uuid not null references engine.learners(learner_id) on delete cascade,
  task_kind       text not null,              -- 'homework' | 'talk' | 'voice' | 'quiz_free'
  task_ref        text,                       -- 숙제ID·퀴즈ID·미션 등 원 과업 참조
  body_original   text,                       -- ⚠ 원문 — 절대 갱신하지 않는다
  audio_ref       text,                       -- 음성 원본 참조 (보존 = 무제한 · 유호님 확정 08-04)
  transcript      text,                       -- 전사문 (있으면)
  transcript_state text,
  privacy_class   engine.privacy_class not null default 'personal_only',
  occurred_at     timestamptz not null,
  schema_ver      text not null
);
```

> 원문을 `learning_events.payload`에 넣지 않고 분리한 이유: ①원문은 **불변**이고 이벤트는 계속 늘어난다 ②본문 검색·용량 특성이 다르다 ③동의 철회 시 **원문만 지우고 통계는 남기는** 처리가 가능해진다(A-6).

### 3-4. `engine.corrections` — 교정과 검수 판정

```sql
create table engine.corrections (
  correction_id    uuid primary key default gen_random_uuid(),
  submission_id    uuid not null references engine.submissions(submission_id) on delete cascade,
  corrected_text   text,
  error_tags       text[] not null default '{}',   -- 통제 어휘 23종 — 정본 = 계약/수집_교정_계약.json
  explanation      text,
  source_kind      engine.source_kind not null,    -- inferred(AI) | teacher(강사) | explicit(학생)
  model            text,
  prompt_ver       text,
  reviewer         text,                           -- 강사·검수자 (teacher일 때)
  verdict          text,                           -- 골든 판정 3값 — 정본 = 계약 파일
  verdict_reason   text,
  seen_at          timestamptz,                    -- 학생이 교정을 열어본 시각 (null = 아직 안 봄)
  learner_response text,                           -- 🔴 성향 축 ④: 'accepted'|'ignored'|'modified' (null = 미응답)
  responded_at     timestamptz,
  confidence       numeric(3,2),
  privacy_class    engine.privacy_class not null default 'personal_only',
  created_at       timestamptz not null default now(),
  schema_ver       text not null
);
```

> 🔴 **`learner_response`가 이 계약의 최대 신규분**이다. 지금 라이브에는 「학생확인」(봤다) 만 있고 **「받아들였나」가 없다** — 유호님이 말한 「발전 방향까지 지도」의 핵심 재료가 통째로 비어 있었다(코어엔진 §10 축 ④).
>
> ⚠ **`seen_at`을 따로 두는 이유**: `learner_response`가 비었을 때 「보고도 무시했다」와 「아직 안 봤다」는 **완전히 다른 신호**인데, 한 칸이면 구분이 안 된다. 안 본 것을 「무시」로 세면 성향 축 ④가 통째로 틀린다(가장 조용히 틀리는 자리라 지금 나눈다).

### 3-5. `engine.skills` — 개념 축 (§9 빈 곳 ② 해소)

```sql
create table engine.skills (
  skill_id     text primary key,              -- 'skill-ko-grammar-particle-topic' — 변하지 않는다
  label_ko     text not null,
  label_mn     text,
  domain       text not null,                 -- 'grammar'|'pronunciation'|'conversation'|'career'
  parent_id    text references engine.skills(skill_id),
  error_tags   text[] default '{}',           -- 이 개념과 이어지는 오류 태그(계약 어휘)
  schema_ver   text not null
);
```

> **이름이 아니라 ID로 묶는다** — 사람이 읽는 이름은 바뀌지만 `skill_id`는 안 바뀐다. 이름으로 묶으면 표기를 고치는 날 과거 데이터가 끊긴다. 선행 관계는 `parent_id` 한 겹만(🚫온톨로지·그래프DB 신축 — 규모 도달 시 재판정).

### 3-6. `engine.consents` — 동의 (간략 · 유호님 확정)

```sql
create table engine.consents (
  consent_id    uuid primary key default gen_random_uuid(),
  learner_id    uuid not null references engine.learners(learner_id) on delete cascade,
  consent_ver   text not null,               -- 'v18.9' 등 문서 버전
  agreed_at     timestamptz not null,
  revoked_at    timestamptz,                 -- 철회 시각 (null = 유효)
  schema_ver    text not null
);
```

> ⚠ **의도적으로 여기서 멈춘다.** 외부 검토문은 동의를 4종(서비스/개인화/연구·모델개선/마케팅)으로 쪼개라 했으나 **유호님이 「동의는 전 버전 그대로 최대한 간략하게」로 확정**(코어엔진 §6)했다. 항목을 늘리지 않고 **버전 하나 + 철회 시각**만 둔다. 별도 `consent_ledger`도 만들지 않는다 — 행 단위 `consent_ver`가 이미 각 이벤트에 박힌다.

## 4. 권한 (RLS) — L0 계약 항목

```sql
alter table engine.learners        enable row level security;
alter table engine.learning_events enable row level security;
alter table engine.submissions     enable row level security;
alter table engine.corrections     enable row level security;
alter table engine.consents        enable row level security;

-- 학생: 자기 것만
create policy learner_self on engine.learning_events
  for select using (learner_id = (select learner_id from engine.learners
                                  where student_code = auth.jwt() ->> 'student_code'));
-- 강사·서버: 서비스 역할로만 (앱 번들에 키를 두지 않는다 — 부록 A-2)
```

> **기본은 「아무도 못 본다」**이고 정책이 열어주는 것만 보인다. 정책을 안 쓴 테이블은 서버(service_role)만 접근한다 — 새 테이블을 추가하고 정책을 잊으면 **닫힌 채로 실패**하지 열린 채로 새지 않는다.

## 5. 라이브 필드 ↔ L0 대조 (제3원천이 아님을 증명)

| 라이브 (Apps Script 시트) | L0 자리 | 비고 |
|---|---|---|
| `hw_feedback`: 제출문 / 고친문장 / 오류태그 / model·prompt_ver / 급수 / 숙제ID·숙제문항 | `submissions.body_original` / `corrections.corrected_text` / `.error_tags` / `.model·.prompt_ver` / `learning_events.level_snapshot` / `submissions.task_ref` | 1:1 |
| `hw_feedback`: **학생확인** | `corrections.learner_response` | ⚠ **의미 확장** — 「봤다」에서 「채택/무시/수정」으로 |
| `quiz_log`: 정답여부 / **확신도** | `learning_events.payload` (`quiz.answered`) | 확신도는 라이브에 이미 있다 |
| `talk_log`: 학생문·AI답 / 턴 / audio_ref | `submissions` + `corrections` / `correlation_id` | 턴 = 흐름이라 `correlation_id`로 |
| `voice_log`: 파일URL·file_id / 전사·전사상태 | `submissions.audio_ref` / `.transcript`·`.transcript_state` | 보존 무제한 유지 |
| `gold`: 강사판정·강사교정·사유 / fb_id | `corrections.verdict`·`.corrected_text`(source_kind=teacher)·`.verdict_reason` / `submission_id` | 골든셋이 별도 테이블이 아니라 **교정의 한 종류**로 흡수 |
| 오류 태그 23종 · 골든 판정 3값 | `계약/수집_교정_계약.json` **그대로 참조** | 여기 복제하지 않는다 |

**신규는 4개뿐**: `learner_response`(교정 수용) · `attempt_no`(재시도) · `choice.selected` 이벤트(선택 로그) · `skill_ids`(개념 축). 나머지는 전부 라이브에 있는 것의 이사다.

## 6. 열린 항목 (동결 전 닫아야)

1. **Supabase 프로젝트 없음** — ⏳유호님 1회. 그때까지 이 문서는 **적용되지 않은 정의**다.
2. **Codex 소비자 승인** — C0 절차 준용(분업 정본 §2). 앱이 실제로 쓸 모양인지 반대편 확인이 동결 조건.
3. **`student_code` 이행 규칙** — 기존 학생ID 체계와 1:1인지, 재발급 시 어떻게 되는지(학생ID 자동발급 트랙과 대조 필요).
4. **`event_type` 어휘 동결** — 오류 태그처럼 **통제 어휘**여야 한다(자유 문자열이면 같은 사건이 열 가지 이름으로 쌓인다). 계약 파일에 넣을지 여기 둘지 = A-0 판단 필요.
5. **AI스택 가이드 §Supabase 정합** — 그 문서는 "Free로 시작, 유료는 사용량이 요구할 때"인데 코어엔진 A-9는 "**실학생 투입 전 유료 전환 + 복구 시험**"이다. 근거가 사용량이 아니라 **백업 부재**라 A-9가 맞다 — 그 문서를 고쳐야 한다.
6. **학생 인증 방식 미확정** — §4 RLS 정책이 `auth.jwt() ->> 'student_code'`를 전제하는데, **학생이 어떻게 로그인하는지가 아직 안 정해졌다**(전화번호? 학원 발급 코드? 소셜?). 정책은 인증 설계가 서야 확정된다 — **P0 몫**이고, 그때까지 이 정책문은 형태 예시다.
7. **`privacy_class` 승격 절차 없음** — 기본값 `personal_only`에서 `company_aggregate`로 **누가 언제 올리는지**가 비어 있다. 승격 게이트 없이 열어두면 개인 데이터가 조용히 회사 학습으로 흘러간다(코어엔진 §9 「생성물→회사 지식 승격 게이트」와 같은 자리). E1 전에 규격 필요.
8. **`skills` 초기 데이터 출처** — `skill_id` 목록을 누가 만드나. 후보 = 교재 시냅스코어 권1 목차 + 오류 태그 23종의 개념 축. **먼저 만들 필요는 없다**(비면 `skill_ids`가 빈 배열일 뿐 수집은 돈다) — 다만 비워 두면 §9 빈 곳 ②가 안 닫힌다.

> ⚠ **음성 「보존 무제한」은 「철회 면제」가 아니다.** 유호님 확정(08-04)은 *보존 기간을 두지 않는다*는 뜻이고, 동의 철회 시 파기(A-6)는 별개 사유로 그대로 적용된다. 두 조항이 충돌하는 것처럼 읽히지 않게 여기 못 박는다.
