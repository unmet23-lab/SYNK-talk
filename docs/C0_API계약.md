# C0 API 계약 — 앱↔서버 인터페이스 (초안 v1)

> **자리**: 개발 분업 §2의 **C0**. 기반(F0·C0)은 **한 번만** 만들고 그 뒤 기능마다 반복하는 그 「한 번」이다.
> **담당** = 클로드 초안 · **동결** = **Codex 소비자 승인 + §7 왕복 6 통과** · **DB 정본** = `docs/L0_데이터계약.md` · **필드 정본** = `계약/수집_교정_계약.json`.
> **⚠ 아직 동결 전이다 — 그러나 「구현 금지」는 더 이상 사실이 아니다.** 이 줄의 v1은 「승인 전에는 이
> 문서를 근거로 화면을 만들지 않는다」였는데, 그 뒤 유호님 판단으로 **화면·서버가 먼저 섰다**(인증 3종
> 라이브 · 조회 3종 리허설 · 왕복 6 초록). 그래서 지금 이 문서의 위험은 「미승인 구현」이 아니라
> **문서가 구현보다 뒤처지는 것**이다 — 실제로 2026-08-09 심문 97건 중 **약 절반이 그 뒤처짐**이었다.
> 🔑 **고칠 때는 코드를 먼저 열고 이 문서를 맞춘다**(반대가 아니다). 상태 표시는 절마다 붙는다:
> ✅라이브 / ⛔운영 미배포(리허설만) / 🔴미구현.

## 0. 세 계약의 경계 — 무엇을 어디서 찾나

| 묻는 것 | 정본 | 여기서 하는 일 |
|---|---|---|
| 무엇이 **필수 필드**인가 · 값목록 | `계약/수집_교정_계약.json`(**현행 c10**) | **참조만.** 값을 복사하지 않는다 |
| DB에 **어떤 모양**으로 앉나 · 권한 | `docs/L0_데이터계약.md` | 참조만 |
| 앱이 **무엇을 보내고 받나** | **이 문서** | 정한다 |

⚠ **C0와 L0를 1:1로 만들지 않는다**(L0 §0). 1:1이면 DB 구조가 API로 새서 나중에 테이블을 못 바꾼다. 잇는 자리는 **Edge Function 한 층**이다.

🔴 **값목록을 이 문서에 복사하지 않는다.** c1→c3에서 두 문서가 실제로 갈라졌고(이름 4건) 그 사고를 다시 사지 않는다. 아래 예시에 박힌 값은 **회귀가 계약 파일과 대조**한다(`tests/계약.test.js`).

## 1. 통로 — 앱은 DB를 직접 만지지 않는다

```
[Expo 앱] ──JWT──> [Edge Function] ──service_role──> [Postgres engine.*]
                        └ 값목록·payload·동의 검증이 여기 한 곳에만 있다
```

- **쓰기는 전부 Edge Function**을 지난다(L0 §4-3). 학생 토큰에는 쓰기 정책이 아예 없다.
- **조회도 Edge Function**이다 — `engine` 스키마는 지금 **API에 노출돼 있지 않다**(L0 §4-3). 앱이 `supabase.from('learning_events')`를 부르면 실패한다. **Codex는 이 경로를 쓰지 않는다.**
- 🔴 **그럼 Edge Function 자신은 어떻게 `engine`에 닿나 — `SUPABASE_DB_URL` 직결이다**(2026-08-06 실측으로 확정). 노출되지 않은 스키마는 **`service_role`이어도** PostgREST를 통과하지 못한다: `PGRST106 · Only the following schemas are exposed: public, graphql_public`. 즉 함수 안에서 `createClient(...).from()`을 쓰면 **모든 쓰기가 런타임에 죽는다** — 그런데 그게 생태계의 기본 예제라 아무 의심 없이 그렇게 짜게 된다. 플랫폼이 함수에 넣어주는 `SUPABASE_DB_URL`로 Postgres에 직접 붙으면(실측: 역할 `postgres` · PG 17.6) 스키마 노출도 새 SQL 객체도 필요 없다. **`engine`을 API에 노출하는 것으로 푸는 길은 쓰지 않는다** — L0 §4-3이 미룬 이유(정책 실수의 영향 범위가 0)를 되돌리는 값이다.
- 예외 하나: **인증**과 **Storage 업로드**는 Supabase SDK를 직접 쓴다(§2·§4-2).
- 경로 매핑: `POST /v1/events` = Edge Function 이름 `events` → 실제 URL `https://<project>.supabase.co/functions/v1/events`.

## 2. 인증 — 토큰을 얻고 싣는 법

로그인 자체는 우리 API가 아니라 **Supabase Auth**다. ⚠ **2026-08-06 개정** — 이 절의 v1은 「학원 발급 코드(`K7M4-P2X9`)를 비밀번호로 쓴다」였는데 **유호님이 그 판을 뒤집었다**(L0 §4-1·§4-2 · 판단 기준 = "내 손이 가장 안 가는 것"). 아래가 현행이다.

| | 값 | 성격 |
|---|---|---|
| 아이디 | **`student_code`**(`SYNK-042`) | 비밀 아님 — 남이 알아도 된다 |
| 비밀번호 | **학생이 첫 로그인에서 직접 정한다** | 비밀 · `auth.users`에만 산다 |

1. **이미 등록한 학생**: 앱이 `signInWithPassword({ email: 합성이메일(학생번호), password: 학생이_친_값 })` **1회**.
   - 합성 이메일 = 정규형을 소문자화 + `@synk.invalid`(`SYNK-042` → `synk042@synk.invalid`).
   - 🔴 **아이디는 정규화하고 비밀번호는 손대지 않는다.** 비밀번호를 대문자화·트림하면 학생이 정한 값과 달라져 「분명히 맞게 쳤는데 안 된다」가 된다.
   - 🔑 정본은 **`lib/학생계정.js` 하나**이고 앱과 서버가 그것을 **같이 쓴다**(Edge Function은 `동봉`으로 같은 파일을 싣는다). 두 곳에 적으면 갈라지고, 증상은 「어떤 학생만 로그인이 안 됨」이라 원인을 찾는 데 가장 오래 걸린다.
   - ⚠ **자릿수를 접지 않는다** — `SYNK-42`와 `SYNK-042`를 같은 것으로 보면 두 학생이 한 계정을 가리킬 수 있다.
2. **아직 계정이 없는 학생**: **`POST /v1/auth/first-login`**(§4-4) 한 번 → 그 자리에서 계정이 서고, 그 뒤로는 1번으로 로그인한다.
3. 앱은 `signUp`을 **절대 부르지 않는다** — 이 금지는 그대로 살아 있다. 계정 생성은 **서버(Edge Function·`service_role`)만** 한다.

> 🚫 **`/v1/learners/link` 재제안 금지는 유지되지만 근거가 바뀌었다.** v1의 근거는 「계정은 학원이 미리 만든다」였는데 **그 전제가 뒤집혔다**(미리 만들면 전달해야 할 초기 비밀번호가 생겨 전달물 0이 깨진다). 지금의 근거는 다른 것이다 — **결합은 앱이 주장할 일이 아니다.** 앱이 「나는 이 learner다」라고 말하는 순간 `service_role`이 RLS를 우회해 남의 계정을 만든다. 그래서 §4-4는 학생을 **본문이 아니라 게이트로** 확정한다.
4. 이후 모든 호출은 supabase-js `functions.invoke()`로 — 세션 토큰이 자동으로 실린다. 직접 `fetch`하면 `Authorization: Bearer <access_token>`과 `apikey: <anon key>`를 **둘 다** 넣어야 한다.

🔴 **앱은 자기가 누구인지 요청 본문에 적지 않는다.** `learner_id`·`student_code`를 보내면 **400**이다. 서버는 항상 **토큰에서** 학생을 확정한다 — `service_role`은 RLS를 우회하므로, 본문의 학생을 믿는 순간 RLS가 있어도 남의 데이터를 쓴다(L0 §4-3 경고).

## 3. 공통 봉투

**요청 헤더**

| 헤더 | 예 | 없으면 |
|---|---|---|
| `Authorization` | `Bearer <access_token>` | 401 `AUTH_REQUIRED` |
| `X-Contract-Ver` | `c10` | 400 `CONTRACT_VER_MISSING` |
| `X-App-Ver` | `0.3.1 (42)` | 통과(로그용) |

**응답 봉투 — 성공**

```json
{ "ok": true, "contract_ver": "c10", "results": [ ... ] }
```

**응답 봉투 — 요청 전체 실패**

```json
{ "ok": false, "contract_ver": "c10",
  "error": { "code": "AUTH_EXPIRED", "message": "토큰이 만료됐습니다", "retryable": true } }
```

- 시각은 전부 **ISO 8601 UTC**(`2026-08-05T13:20:11.412Z`). `occurred_at`=앱이 관찰한 발생 시각, `ingested_at`=서버 수신 시각(서버가 채운다).
- 🔴 **`session_id`·`content_id`·`task_schema_ver`·`consent_id` 는 DB 열과 서버 코드에는 있는데 「필드 정본」에는 없다**(2026-08-09 실측 · 심문 3벌 중 2벌이 다른 결론으로 짚었다). 실측은 이렇다 — `functions/events` 가 넷 다 읽어 `insert` 하고(`index.ts` 235·419·426·470·477·299·446), `lib/이벤트검증.js` 에는 **미등록 필드를 거절하는 로직이 아예 없다.** 그래서 심문의 「앱이 보내면 거절된다」는 **틀렸다**(갈래 C). 틀리지 않은 절반은 **정본이 뒤처졌다**는 것이다: `계약/수집_교정_계약.json` 의 필드 목록에 이 넷이 없어, **계약만 읽는 소비자**(Apps Script·n8n·다음 세션)는 그 값이 실재하는 줄 모른다. 🔑 검증기의 장부 규칙은 「계약의 모든 필드가 어딘가에 있어야 한다」 **한 방향뿐**이라, 반대 방향(**저장하는 열이 계약에 있는가**)은 아무도 안 본다 — 그래서 조용히 벌어졌다. 처방(계약 개정 + 역방향 회귀)은 갈래 B로 뺀다.
- 🔴 **uuid 칸은 진짜 uuid다** — `correlation_id`·`session_id`·`content_id`·`retry_of_event_id`·`parent_event_id`. c6까지 §4-1 예시가 `content_id`를 `"c-hw-0031"`로 적고 있었는데 **L0 스키마의 그 열은 `uuid`**라, 예시를 그대로 따른 앱은 전건 400을 맞는다(2026-08-06 Edge Function 구현 중 발견 · 예시 정정). 서버는 모양을 **먼저** 본다 — 안 그러면 Postgres가 `22P02`로 죽어 400이어야 할 것이 500이 되고, 5xx는 `retryable`이라 앱이 영구 오류를 무한 재시도한다.
- ⚠ **기기 시계는 못 믿는다.** `occurred_at`이 미래여도 **거부하지 않는다**(거부하면 학생이 시계를 잘못 맞춘 날의 학습이 통째로 사라진다). 서버는 그대로 저장하고 **로그에만** 남긴다 — 컬럼을 늘리지 않는다.

## 4. 엔드포인트

**쓰기 통로는 둘**이다(§4-1·§4-2). 화면이 정해지지 않은 API를 먼저 동결하면 **쓰이지 않는 계약**이 굳는다(§10).

🔴 **「엔드포인트 둘」은 더 이상 이 문서의 범위가 아니다**(2026-08-09 심문 3벌 전부가 같은 자리를 짚었다).
그 문장은 c0 초안 시점의 것이고, 그 뒤 화면이 정해지면서 **조회 3종(§4-3)·인증 3종(§4-4~4-6)이 같은 문서로
들어왔다.** 지금 이 문서가 정의하는 것은 **여덟**이다 — 쓰기 2 · 조회 3 · 인증 3. 「둘」로 읽고 승인하면
**여섯 개가 승인 없이 굳는다.**

| 묶음 | 엔드포인트 | 동결 축 |
|---|---|---|
| 쓰기 | `POST /v1/events` · `POST /v1/uploads/sign` | **학생 데이터면** — §7 왕복 6이 재는 자리 |
| 조회 | `GET /v1/tasks` · `/v1/corrections` · `/v1/progress` | S1 화면이 정해져서 생겼다(§4-3) · 왕복 6 **밖** |
| 인증 | `POST /v1/auth/{first-login,reset,temp-login}` | 라이브 · `tools/인증왕복시험.js` 36/36 이 재는 자리 · 왕복 6 **밖** |

⚠ **동결 판정(§8)의 「여섯 칸 초록」은 쓰기 2개에 대한 증거다** — 조회·인증까지 덮지 않는다.

### 4-1. `POST /v1/events` — 유일한 쓰기 통로

모든 기능이 여기로 들어온다(「모든 버튼이 학습이 되게」). **배치**이며 **멱등**이다.

**요청**

```json
{
  "events": [
    {
      "idempotency_key": "b6f1c0a2-…",
      "event_type": "submission.created",
      "task_type": "숙제제출",
      "occurred_at": "2026-08-05T13:20:11.412Z",
      "correlation_id": "1f0c…",
      "session_id": "9a22…",
      "content_id": "7d1a4e90-2c33-4f8a-9b21-6e0b5c8d1f42",
      "skill_ids": ["skill-ko-grammar-particle-topic"],
      "skill_taxonomy_ver": "kt.2026-08",
      "level_snapshot": "Lv3",
      "goal_snapshot": "study",
      "retry_of_event_id": null,
      "parent_event_id": null,
      "turn_no": null,
      "payload": { "ver": 1, "attempt_no": 1 },
      "submission": {
        "task_ref": "hw-2026-08-05-3",
        "task_format": "자유발화",
        "task_snapshot": { "지시문": "…", "문항": "…", "보기": ["…"], "정답": "…" },
        "task_schema_ver": "hw.v1",
        "body_original": "어제 친구를 만나서 밥을 먹었어요",
        "audio_ref": null,
        "capture_meta": null
      }
    }
  ]
}
```

**누가 무엇을 채우나** — 앱이 서버 칸을 보내면 **400**(조용히 덮어쓰면 위조가 통과처럼 보인다).

| 서버가 채운다 | 왜 |
|---|---|
| `event_id`·`ingested_at` | 서버 채번·서버 시계 |
| `learner_id` | **토큰에서**(§2) |
| `consent_id`·`consent_ver` | 위조 방지 + `occurred_at` 시점의 **유효한 동의**로 확정(L0 §3-6). 유효 동의가 없으면 저장하지 않는다.<br>🔴 **두 칸이다 — 판 번호만으로는 어느 동의 행이 근거였는지 못 짚는다**(같은 판으로 재동의하면 행이 둘이고, 철회는 **행 단위**다). `functions/events` 는 이미 둘 다 읽어 적는데(`select consent_id, consent_ver …`) c9까지 이 표에 `consent_ver` 만 있어서, 계약만 읽은 소비자는 승격 계보를 **판 단위로만** 재구성했다 |
| `schema_ver` | 계약 파일 버전을 **저장 시 자동 기입**(A-8 · 유호님 확정) |
| `model`·`prompt_ver`·`intervention_id`·`degraded` | AI 호출이 서버에서 나므로 앱은 알 수 없다. 🔑 **성과 이벤트의 `intervention_id`는 서버가 계승한다**(c6): 앱이 `retry_of_event_id`로 「무엇에 대한 재시도인가」만 말하면, 서버가 그 사건의 `intervention_id`를 읽어 이 행에 적는다. c5까지는 앱이 못 보내고 서버도 이을 근거가 없어서, 「성과는 같은 개입 ID를 가리킨다」는 규칙에 **실행 경로 자체가 없었다** |
| `source_kind`·`estimator_*` | 추정 메타 — 추정하는 쪽이 적는다 |

| 앱이 반드시 채운다 | 왜 |
|---|---|
| `idempotency_key` | UUID v4. 🔴 **이벤트를 만들 때 한 번 생성하고 재시도해도 바꾸지 않는다** — 재시도마다 새로 만들면 멱등이 통째로 죽고, 증상은 오프라인에서 돌아온 학생의 기록이 **여러 벌** 쌓이는 것이다.<br>⚠ **서버 배치는 예외로 결정론적 키를 쓴다**: `task:{learner_id}:{YYYY-MM-DD}`(몽골 시간대). 배치가 두 번 돌아도 두 번째는 `duplicate`로 접히므로 **「하루 1건」에 새 유일 제약이 필요 없다** — 이미 있는 멱등이 그 일을 한다 |
| `event_type` | 계약 값목록 |
| `occurred_at` | 서버 수신 시각과 **다르다**(오프라인) |
| `level_snapshot` | 🔑 **앱이 보낸다.** 3일 전 오프라인 제출을 오늘 올리면 서버의 현재 급수는 **그때 급수가 아니다.** 급수 이력 테이블은 만들지 않는다(파생 선행 구축 금지) — 그때 화면이 알던 값을 그때 적는 것이 유일하게 정확하다. 빠지면 400 |

**payload 규격**

- `payload.ver`(정수) **필수**. 모양이 바뀌면 `2`로 올리고 과거 행은 `1`로 남는다.
  > 🔑 **이벤트 이름에 `.v1`을 붙이지 않는다**(L0 §3-2 표기 정정 요청 · §9). 이름에 붙이면 값목록이 payload 개정마다 배로 늘고, 집계가 `like 'choice.selected%'`가 된다. `payload.ver`는 **컬럼도 값목록도 늘리지 않는다.**
- payload 필드 이름도 **현행 계약(c10) 필드 목록에서 고른다**(`confidence`·`attempt_no`·`learner_response`·`options_shown`·`position`·`recommended_option`·`selected_option`·`changed_selection`·`latency_ms`·`skipped`·**`selection_reason`**·**`rejected_all`**·**`cited_refs`**·**`output_text`**). 목록에 없는 이름이 필요하면 **다음 판 개정**이지 자유 추가가 아니다.
  > 🔴 **굵은 4개는 c4·c5가 계약에 넣었는데 이 목록이 따라오지 않았다**(2026-08-06 외부 검토가 잡았다). 계약은 「필수」라 하고 이 문서는 「목록에 없는 이름은 자유 추가가 아니다」라 해서, **앱이 그 필드를 보내는 순간 계약 위반으로 거절되는** 상태였다. 두 문서가 각자 맞는 말을 하는데 합치면 구현이 불가능한 형태 — 계약을 늘릴 때 이 목록을 함께 늘리지 않으면 반드시 재발한다.
- **선택지는 `{option_id, label}`로 싣는다**(c6). `option_id`는 안 바뀌는 조인 키고 `label`은 그때 표시된 문구의 스냅샷이다. 문구만 문자열로 남기면 문구를 개정하는 날 **판을 가로지르는 집계가 끊긴다** — 스킬에 「이름 말고 불변 ID로 묶는다」를 적용한 것과 같은 이유이고, c5까지 선택지에만 그 규칙이 빠져 있었다.
- 🔴 **`is_correct`(정답여부)를 만들지 않는다.** `submission.body_original`(고른 답) + `task_snapshot.정답`이 있으면 채점은 **언제든 다시 계산되는 파생**이다. 원본을 두고 파생을 저장하면 채점 규칙이 바뀌는 날 과거가 거짓말을 한다.
- 빈 껍데기 방지: `event_type`이 요구하는 payload가 비면 **저장하지 않는다**(L0 §3-2 두 층 검증). 검증은 이 함수 한 곳에만 있다.

**응답**

```json
{ "ok": true, "contract_ver": "c10",
  "results": [
    { "idempotency_key": "b6f1…", "status": "stored",    "event_id": "3c9e…" },
    { "idempotency_key": "77a2…", "status": "duplicate", "event_id": "1b40…" },
    { "idempotency_key": "e551…", "status": "rejected",
      "error": { "code": "CONTRACT_VIOLATION", "field": "event_type",
                 "message": "값목록에 없는 event_type", "retryable": false } }
  ] }
```

- **`duplicate`는 오류가 아니다** — 같은 `(학생, idempotency_key)` 재전송은 **200 + 원래 `event_id`**. 오류로 주면 큐가 영원히 재시도한다.
- 🔑 **부분 실패는 HTTP 200이다.** 한 건이 영구 실패인데 배치 전체를 4xx로 돌려주면 **그 한 건이 큐 맨 앞에서 나머지를 영원히 막는다**(head-of-line blocking). 전건 실패 사유(인증·계약 버전)만 4xx.
- 앱은 `status`가 `stored`·`duplicate`인 항목만 로컬 큐에서 지운다. `rejected`는 **격리 보관** 후 보고(사용자에게는 조용히).
- 상한: **100건 / 1MB**. 넘으면 413. *(임의값 — S1 실측으로 조정한다)*

### 4-2. `POST /v1/uploads/sign` — 음성·이미지

발화 과업(`발화녹음`·`출석발화`)의 원본은 **Storage 비공개 버킷**에 있고, 이벤트에는 참조만 실린다.

```json
요청  { "kind": "audio", "content_type": "audio/wav", "byte_size": 482913 }
응답  { "ok": true, "contract_ver": "c10",
        "upload_url": "https://…", "audio_ref": "voice/9f2c…(learner_id)/3c9e….wav",
        "expires_at": "2026-08-05T13:35:00.000Z" }
```

**순서**: ①서명 받기 → ②Storage에 직접 PUT → ③성공하면 `audio_ref`를 `submission`에 실어 `/v1/events`.

> **구현 = `functions/uploads`(슬러그 `uploads` · 뒷마디 `/sign` 까지 본다) · 라이브 2026-08-06.**
> 버킷 = 비공개 `learner-media` 하나(`voice/`·`image/` 는 그 안의 폴더). 경로 규칙 정본은 `lib/업로드경로.js` 를 **동봉**해서 쓰고, `events` 도 같은 파일로 받은 참조를 검사한다.
> 🔴 **동의 게이트가 여기 있다** — 서명을 내주는 것이 곧 수집 허가다. `events` 에만 두면 동의 없는 학생의 음성이 **Storage 에는 이미 올라간 뒤** 행만 거절되고 파일은 남는다.
> 🔴 **서명 키는 `STORAGE_SIGN_KEY`(레거시 service_role JWT)다.** 플랫폼이 넣어주는 `SUPABASE_SERVICE_ROLE_KEY` 는 새 형식(`sb_secret_…`)이라 Storage 가 거절한다(`Invalid Compact JWS` · 헤더 조합 5가지 실측). 함수가 키 모양을 **먼저** 검사하고, 아니면 이름을 대고 멈춘다. 설정 = `tools/스토리지키_설정.js`.

- 🔑 **업로드 성공 뒤에 이벤트를 보낸다.** 반대로 하면 참조가 가리키는 파일이 없는 행이 남고, 그건 나중에 「전사 실패」와 구분되지 않는다.
- 오프라인이면 로컬 파일을 큐에 두고 복귀 시 ①②③을 그대로 밟는다.
- 서버가 `content_type`·`byte_size`를 검증한다(상한 **25MB**, 임의값). 음성은 **보존 무제한**(유호님 확정)이라 용량 실수의 비용이 **영구적**이다.
- 🔴 **정본 포맷 = PCM WAV 16kHz / 16bit / mono · 기기 음성처리(AGC·노이즈 억제·에코 제거) off.** 소급 불가 배선①이다 — 압축과 자동 게인이 **떨림·미세 발음을 지우고**, 지워진 신호는 원본이 없으므로 영영 복원되지 않는다.
  - ✅ **압축 축은 닫혔다 (2026-08-07 · 유호님 확정 「wav 로 하자」).** 앱이 컨테이너 인코더(`useAudioRecorder` = m4a/AAC)를 버리고 마이크 **PCM 스트림**(`useAudioStream`)을 받아 직접 RIFF 를 씌운다 — 조립 정본 = `lib/wav조립.js`. 🔑 **새 네이티브 의존성 0**(`expo-audio` 57 에 이미 있다) → dev build 를 새로 만들 필요가 없다. 요청 규격은 `음성헤더.정본` 에서 **파생**하므로 요청과 검사가 갈라지지 않는다.
    - 🔴 **헤더에 적는 값은 요청값이 아니라 스트림이 보고한 값이다.** 기기가 16kHz 를 못 주면 네이티브가 조용히 폴백한다(`AudioStream.kt` `FALLBACK_SAMPLE_RATES` = 48000·44100·16000·22050·8000). 요청값을 적으면 그 파일이 **자기가 무엇인지 거짓말하는 원본**이 되고, 서버가 그 헤더를 재므로 `spec_violations` 까지 같이 거짓이 되어 규격 위반이 **영영 안 보인다.** 모르면 던진다 — 추측한 헤더는 쓰지 않는다.
    - 🔴 **AGC 축은 안 닫혔다 — 라이브러리에 손잡이가 없다.** `useAudioStream` 은 Android 를 `AudioSource.MIC` 로 고정해 열고(`AudioStream.kt:142`) 옵션이 없다. 처리 없는 소스(`UNPROCESSED`)는 **녹음기 쪽에만** 있는데 그건 m4a 만 낸다(`AudioRecords.kt:157`) — 즉 오늘 `expo-audio` 에서 **무압축과 무처리는 서로 반대편에 있다.** iOS 도 `setAudioModeAsync` 에 `.measurement` 가 없다. 그래서 `agc_requested` 는 계속 `null`, `agc_verified` 는 계속 `"unknown"` 이다(모르는 것을 `false` 로 적지 않는다). ⏳ 처방 후보 = 라이브러리 패치/PR · 별도 네이티브 모듈 · MIC 로 감수 — **유호님 판정 대기.**
    - ⚠ **아직 실기기에서 안 재 봤다.** 회귀가 증명하는 것은 「조립한 바이트를 서버 파서(`lib/음성헤더.js`)가 위반 0 으로 읽는다」까지다(`tests/wav조립.test.js`). 실기기 2대 헤더 실측은 `발주_수집파이프라인.md` §8 그대로 남아 있다.
  - 🔑 **규격 밖이어도 업로드를 거부하지 않는다.** 거부하면 학생의 발화가 영영 사라지고, 「수집이 채점보다 우선」 원칙에 어긋난다. 대신 **서버가 파일 헤더에서 실제 값을 파생해 저장**하고(`codec`·`sample_rate`·`bit_depth`·`channels`), 규격 밖이면 **경고를 남긴다**. 규격은 사람이 지키는 약속이 아니라 **행마다 붙는 관측값**이어야 한다.
  - 🔴 **저장 자리 = `submissions.capture_meta`**(c6 신설). c5까지 이 문단은 「서버가 파생해 저장한다」고 약속만 하고 **담을 열이 없었다.** 두 갈래를 **분리해서** 적는다: `server`(헤더에서 실제로 잰 값 · 길이 불일치 포함) / `app`(기기·OS·앱 빌드·마이크 경로·**요청한** 처리 설정·녹음 중단 여부). 🔑 **AGC·노이즈 억제는 WAV 헤더에 흔적이 없다** — 앱이 「off로 요청했다」는 것과 「실제로 off였다」는 것은 다른 사실이므로, 검증할 수 없으면 `agc_verified: "unknown"`으로 남긴다. 모르는 것을 `false`로 적으면 그 행이 **「off였다」는 거짓 증거**가 되고, 떨림·미세 발음이 학생 특성인지 기기 처리 결과인지 영영 못 가른다.
  - **구현 = `functions/events` (2026-08-07 · 리허설 실왕복 18/18).** 제출 이벤트에 `audio_ref`가 있으면 서버가 그 객체의 **앞 4KB만** 읽어 `capture_meta.server`를 채운다 — `codec`·`sample_rate`·`bit_depth`·`channels`·`duration_ms`·`byte_size`·`spec_violations`·`agc_verified:"unknown"`. 앱이 보낸 `app` 칸은 그대로 두고 `server`만 얹는다. 파싱 정본 = `lib/음성헤더.js`(앱 번들에도 얹히는 의존성 0 순수 함수).
    - 🔴 **길이는 봉투 안에만 두지 않는다 — 정본은 `submissions.audio_duration_sec`(초 · 소수 2자리)다**(2026-08-09 · talk `5d8c8bb` · 업로드왕복 28/28). `capture_meta.server.duration_ms`(밀리초)는 **같은 값의 관측 기록**이고, 검수 큐 22열·게임 「발화 길이」·「몇 초 말했나」 집계가 읽는 곳은 **열 쪽**이다. c9까지 이 문단이 봉투만 적어서 그 열이 **영구 빈 칸**이었다 — 봉투에 값이 있는데 소비자 전량이 0을 봤다. 🔑 **한 번 잰 값을 두 자리에 적는 것이지 두 번 재는 게 아니다**(같은 `lib/음성헤더.js` 결과에서 파생 · 앱은 길이를 보내지 않는다).
    - **왜 별도 finalizer가 아니라 events 시점인가**: `capture_meta`는 `submissions` 열이라 **그 행을 만드는 순간**이 쓸 자리가 확실한 유일한 시점이다. 업로드 웹훅이면 아직 행이 없어 어딘가 임시로 뒀다 이어붙여야 하고, **그 이어붙이기가 실패하면 조용히 빈다.**
    - 🔴 **못 재도 행은 저장한다**(「수집이 채점보다 우선」). 대신 `state`로 남긴다 — `measured` / `missing`(참조가 가리키는 파일이 없다) / `unmeasured`(못 쟀다 · `reason` 동반). 조용히 비우면 **「측정 실패」와 「규격 정상」이 빈 칸 하나로 같아진다.**
    - 🔑 **`state:"missing"`이 위 「업로드 성공 뒤에 이벤트」 규칙의 파수꾼이다** — 순서가 뒤집힌 행을 ingest 시점에 못 박는다(안 박으면 나중에 「전사 실패」와 구분되지 않는다). ⚠ 실측: Storage는 없는 객체를 **`400`**으로 돌려주고 `404`는 **본문 안에만** 있다(`"code":"NoSuchKey"`) — 상태 코드만 보면 이 신호가 「일시 실패」에 섞인다(2026-08-07 리허설 왕복이 적발).
    - ⚠ **규격 밖(m4a·aac 등)은 `codec`만 적고 나머지 칸은 `null`이다** — MP4 박스 파서를 짜지 않는다. 「m4a가 쌓이고 있다」는 사실이 그 값들보다 크고, **0이나 추정값을 적으면 틀린 관측이 영구히 쌓인다.**
  - ⚠ **인수 조건은 「2대 1회 실측」이 아니라 「매 건 기록」이다.** 앱 업데이트로 설정이 조용히 켜지면 그 뒤 전량이 오염되는데 증상이 없다 — 1회 검사는 그 순간만 증명한다.
  - 인수 조건: 실기기 2대(iOS/Android)의 실제 파일 **헤더**로 검사한다. 앱 설정 코드를 읽는 것은 검사가 아니다.
- 재생은 조회용 서명 URL로 — 버킷은 공개하지 않는다.
- 🔴 **경로 규칙 = `{voice|image}/{learner_id}/{uuid}.{ext}` — 첫 칸 뒤가 반드시 `learner_id`다**(정본 L0 §9-3).
  **날짜로 나누지 않는다.** 동의문은 철회 시 「보관 중인 녹음을 **모두** 삭제」를 약속하는데, `voice/YYYY/MM/`으로
  쌓으면 한 학생의 파일이 **모든 달 폴더에 흩어져** 유호님이 손으로 지울 수가 없다 — 동의문 §57이 지목한 부채가
  정확히 이것이다. learner 프리픽스면 **폴더 하나를 지우면 끝**이다.
  - `learner_id`인 이유는 **안 바뀌기 때문**이다. `student_code`(SYNK-001)는 사람이 읽기 쉽지만 재발급되면
    옛 코드 밑의 파일이 미아가 된다 — 삭제 보증이 깨진다. 사람이 읽는 몫은 철회 절차 1번이 진다(L0 §9-3-2).
  - ⚠ **소급 불가** — 첫 업로드가 이 규칙 밖으로 나가면 그 파일은 규칙을 고쳐도 **안 옮겨진다.** 배선①(WAV)과
    같은 등급이라 Edge Function 구현 **전에** 못박는다. 회귀 = `tests/철회경로.test.js`.

### 4-3. 조회 — ✅ S1 3종 확정 (2026-08-06 · `P0_제품계약.md` §4-3이 화면을 정했다)

공통 규약:

- 경로 `GET /v1/<복수명>` · 응답 봉투는 §3과 같고 `results` 대신 `data` + `next_cursor`.
- **커서 기반**(offset 금지 — append-only라 페이지가 밀린다).
- 자기 것만 — 서버가 토큰에서 학생을 확정한다. **쿼리로 학생을 지정할 수 없다.**
- 🔴 **빈 상태는 오류가 아니다** — `data: []` + HTTP 200. 첫날·배치 실패·교정 미확정이 전부 정상 경로다. 404를 쓰면 앱이 오류 화면을 띄우고, 그건 학생에게 「고장」으로 보인다.

#### ① `GET /v1/tasks` — 오늘 낼 것 (✅구현 · **리허설 실측** 2026-08-07 · ⛔운영 미배포)

| 항목 | 값 |
|---|---|
| 쿼리 | `date`(생략 시 오늘 · **`Asia/Ulaanbaatar` 기준 날짜**) |
| `data[]` | `task_id`(= 그 `task.assigned` 이벤트 id) · `task_snapshot`(그날 학생이 본 것 그대로) · `task_format` · **`task_ref`·`level_snapshot`·`goal_snapshot`**(제출에 **되돌려 실을** 값 — 아래 🔑) · `intervention`(①듣기용 · `output_text`·`intervention_id`·**`event_id`**) · `degraded`(강등으로 나온 과제인가) |
| 빈 상태 | `data: []` = **오늘 배정이 없다.** 앱은 고정 도입 과제로 내려간다(`P0 §6-4`) — 오류로 취급하지 않는다 |
| S1 사용 | 1건만 읽는다(하루 1건이므로 `next_cursor`는 항상 `null`) |

🔴 **읽을 것이 어디 있나**(2026-08-07 배치 구현으로 확정 · `P0 §6-1`): `task_snapshot`은 **`engine.submissions`**에 있고 그 행은 `event_id`로 `task.assigned` 사건에 붙는다. payload가 아니다 — 계약 필드층이 그 이름을 「내용」에 두었기 때문이고, 그래서 **계약 개정이 0**이었다.
⚠ 그 대가로 `submissions`에는 **제출이 아닌 행**이 산다. 이 엔드포인트를 짤 때도, 「제출 수」를 세는 `GET /v1/progress` ③을 짤 때도 **반드시 `learning_events.event_type`으로 거른다** — 안 걸면 배정 1건이 제출 1건으로 세어져 첫날부터 「어제의 나」가 거짓말을 한다.

**응답 예 · 실패 표** (`supabase/functions/tasks`):

```json
{ "ok": true, "contract_ver": "c10", "date": "2026-08-07", "next_cursor": null,
  "data": [ { "task_id": "…", "task_snapshot": { "ver": 1, "호흡": [ … ] },
              "task_format": null, "task_ref": "task-2026-08-07",
              "level_snapshot": "Lv2", "goal_snapshot": "study",
              "retry_of_event_id": null, "degraded": false,
              "intervention": { "intervention_id": "…", "event_id": "…", "output_text": "…" } } ] }
```

| 상황 | 응답 |
|---|---|
| `X-Contract-Ver` 없음 / 꼴 아님 | `400 CONTRACT_VER_MISSING` / `426 CONTRACT_VER_UNSUPPORTED` |
| DB보다 새 판을 선언 | `426` (§4-1과 같은 축 — 함수가 DB보다 앞설 수 없다) |
| 토큰 없음 · anon 키 · 학생 행 없음 | `401 AUTH_REQUIRED` |
| `date`가 `YYYY-MM-DD`가 아님 | 🔴 `400 CONTRACT_VIOLATION` — **500이 아니다.** 모양을 먼저 안 보면 Postgres가 `22007`로 죽고, 5xx는 `retryable`이라 앱이 영구 오류를 무한 재시도한다 |
| `GET` 아님 · `/tasks` 아래 다른 경로 | `405` / `404` (조회가 쓰기를 겸하지 않는다 · 오타 경로가 「이미 돌던 것」이 되지 않는다) |

- 🔑 **`task_format`은 항상 `null`로 온다** — 배정 1건에 ②낭독 + ③자유발화 두 형식이 들어서 행에 담지 않는다(`P0 §2-1`). 형식은 `task_snapshot.호흡[]` 안에 있다.
- 🔑 **`intervention`은 `intervention_id`로 잇는다**(시각·순서가 아니다). 하루 2건이 서는 날 시각으로 이으면 조용히 어긋난다.
- 🔑 **`intervention.event_id` = 그 `intervention.delivered` 사건의 id — 앱이 `content.viewed`의 `parent_event_id`로 쓸 유일한 값**(c9 · 절단문서 ①-2·①-12 · 2026-08-07). 🔴 **`intervention_id`로 대신하지 못한다**: 그건 배달과 성과가 함께 드는 **업무 키**라 여러 행에 같은 값이 실리고, 그 값으로 가리키면 같은 개입을 두 번 내보낸 날 두 열람이 한 행으로 접힌다(`lib/이벤트검증.js`가 `task_ref` 대안을 기각한 것과 같은 축). 이 칸이 없어서 `content.viewed`는 이름·물리·검증기가 다 선 뒤에도 **생산자가 0**이었다 — 앱이 가리킬 대상을 손에 못 들었기 때문이다. ⚠ `null`일 수 있다(배정엔 `intervention_id`가 있는데 배달 사건 행을 못 찾은 경우) → 그때 앱은 열람을 **보내지 않는다**.
- 🔴 **`retry_of_event_id` = 오늘 것이 교정문이면 그 교정의 원 제출 사건**(2026-08-08 · 계약 개정 0 · 마이그레이션 0). 앱은 이 값을 제출 사건의 `retry_of_event_id`로 되돌려 싣는다 — **설계 전체의 유일한 결과 변수**(`L0 §9-2`)이고, 없으면 엔진이 상관만 배우고 처방을 못 배운다. 🔑 **막고 있던 것은 이름도 물리도 검증기도 아니라 배달이었다**: `functions/deliver`의 교정 lateral이 `corrected_text`만 집고 그 교정이 **어느 제출**에 대한 것이었는지를 버려서, 교정문이 다음 날 ②슬롯에 나가도 앱에는 채울 재료가 없었다(이름·FK·CHECK·서버 INSERT는 c5부터 전부 서 있었다 = **생산자 0**). 🔴 **앱이 문장을 대조해 짐작하지 않는다** — 같은 문장이 두 번 교정된 날 조용히 갈리고, 그 오염은 결과축 자체를 못 믿게 만든다. 그래서 「어느 제출의 교정인가」를 아는 유일한 자리(배정을 정한 곳)에서 박아 내려보낸다. ⚠ 배정 행(`task.assigned`)이 이 칸을 들지만 성과 집계(`§4-3 ③` 교정재발화)는 `submission.created`만 세므로 숫자는 안 흔들린다. 🔑 `null`이 정상이다(교정문 날이 아니면 재시도가 아니다).
  - 🔴 **부작용을 미리 적는다 — 이 값이 서면 `intervention_id` 계승이 처음으로 실제로 발화한다**(§4-1 「서버가 채운다」 표). `functions/events`는 `retry_of_event_id`가 있으면 **원 제출의 `intervention_id`를 그 행에 적는다** → 교정문 날의 제출은 **오늘 배달(B)이 아니라 원 제출의 개입(A)**을 가리킨다. 그 규칙은 c6부터 계약에 있었지만 **생산자가 0이라 한 번도 안 돌았다.** 지금 깨지는 하류는 없다(`/tasks`는 배정 행의 `intervention_id`로 잇고 `§4-3 ③`은 `event_type`으로 센다). ⚠ 다만 「어느 개입이 성과를 냈나」를 읽는 첫 소비자가 서는 날, **A와 B 중 무엇에 공을 돌릴지**는 계약이 이미 A로 정해 둔 것이라는 사실을 그때 다시 확인해야 한다 — 바꾸려면 계약 개정이다.
- 🔑 **`task_ref`·`level_snapshot`·`goal_snapshot`은 「되돌려 주려고」 싣는다**(2026-08-07 · S1-b 쓰기 절반). 셋 다 제출 사건에서 **앱이 채우는 칸**인데(§4-1 — 3일 전 오프라인 제출을 오늘 올리면 서버의 현재 급수는 그때 급수가 아니다) 앱은 알 길이 없었다: 급수는 로그인 응답에도 없고, `task_ref`는 배치의 작명 규칙(`task-{날짜}`)이라 앱이 지어내면 **규칙의 사본**이 된다. 사본은 배치가 규칙을 바꾸는 날 갈라지고 증상은 「제출이 큐와 안 이어지는 것」뿐이라 어디에도 오류로 안 남는다. 🔴 **`task_ref`가 없으면 앱은 그날 발화를 보내지 않는다**(지어내는 것보다 안 보내는 편이 옳다 · `lib/오늘과제.js` 화면과제).

🔑 **`since`는 시각이 아니라 앞선 응답의 `next_cursor`를 그대로 싣는 값**이다 — 꼴은 `<ISO 시각>|<correction_id>`. **시각만으로는 부족하다**: 같은 밀리초에 두 교정이 서면 쪽 경계에서 한 건이 조용히 사라지고, append-only라 되짚을 수도 없다. 🔴 이건 추정이 아니라 **실측이다** — 커서를 시각 하나로 되돌린 판을 리허설에 배포해 돌렸더니 경계의 한 건이 실제로 사라졌다(2쪽이 2건 → 1건). 꼴이 아니면 `400 CONTRACT_VIOLATION`(500이면 앱이 영구 오류를 무한 재시도한다 · ①의 `date`와 같은 축). 한 쪽은 20건.

#### ③ `GET /v1/progress` — 어제의 나와 비교 (✅구현 · **리허설 실측** 2026-08-07 · ⛔운영 미배포)

| 항목 | 값 |
|---|---|
| 쿼리 | 없음(서버가 오늘/어제를 정한다 — 기기 시계를 믿지 않는다 · §3) |
| `data[]` | 0건 또는 1건: `today`·`yesterday` 각각 `submission_count`·`retry_count`·`correction_retry` |
| 빈 상태 | `data: []` = **오늘이 첫날이다.** 비교 대상이 없다는 뜻이지 실패가 아니다 |
| 🔴 경계 | 이 엔드포인트는 **집계값만** 낸다. 점수·등수·타 학생 값은 담지 않는다(`P0 §2-1` 랭킹 금지) |

```json
{ "ok": true, "contract_ver": "c10", "date": "2026-08-07", "next_cursor": null,
  "data": [ { "today":     { "submission_count": 2, "retry_count": 1, "correction_retry": true },
              "yesterday": { "submission_count": 1, "retry_count": 0, "correction_retry": false } } ] }
```

세 값이 **각각 다른 축**이다(합치면 「연습을 많이 했다」와 「교정이 먹혔다」가 한 칸에서 섞인다):

- `submission_count` — `submission.created` 건수. 🔴 **`submissions` 표를 세지 않는다** — 거기엔 배정 행이 산다(§4-3 ① ⚠).
- `retry_count` — 그중 `payload.attempt_no >= 2`. **같은 과제를 다시 말한 것**(`P0 S1-7`: 재시도는 새 `event_type`이 아니라 attempt 증가로 남는다). ⚠ payload는 자유 JSON이라 숫자꼴일 때만 읽고 아니면 1로 본다 — 바로 캐스팅하면 행 하나가 조회 전체를 **500**으로 만들고 5xx는 앱이 무한 재시도한다.
- `correction_retry` — 그중 `retry_of_event_id`가 달린 것이 있나(**boolean**). 교정을 받고 **날을 건너** 다시 낸 고리이고, 지금 설계에서 **결과 변수는 이것 하나뿐**이다(`L0 §9-2`).

🔴 **「첫날」은 「어제가 0」과 다르다.** 어제 있었는데 아무것도 안 낸 학생에게 `yesterday: 0`은 참이고 보여줄 값이다(오늘 1 > 어제 0이 곧 동기). 비우는 것은 **어제라는 시점이 이 학생에게 아직 없는** 경우뿐이다 — 그때 0을 보여주면 없는 과거를 지어내는 것이 된다. 판정은 그 학생의 **첫 사건 시각**이 오늘 이후인가로 한다(서버·`Asia/Ulaanbaatar`).

- **실측 = `tools/배달왕복시험.js` ⑩**(리허설). 사건을 심고 이 엔드포인트가 그 수를 그대로 내는지 **같은 실행에서** 대조한다 — 특히 **배정 행이 제출로 세어지지 않는 것**과 **첫날 빈 배열**을 잰다.

⚠ **이 셋 말고는 S1에서 열지 않는다.** 화면이 안 읽는 조회를 미리 만들면 그 순간부터 유지 대상이 된다.

### 4-4. `POST /v1/auth/first-login` — 첫 등록 (✅라이브 · 2026-08-06)

계정이 서는 **유일한 통로**다. 로그인 전이라 **anon 키로 부른다**(세션 토큰이 없다).

```jsonc
{ "student_code": "SYNK-042", "phone_last4": "2233", "password": "학생이 정한 값",
  "home_aimag": "ulaanbaatar", "gender": "undisclosed", "goal_track": "study",  // 가입 1회 문항 — 필수
  "recovery_email": "parent@example.com", "recovery_phone": "99001122" }   // 복구 2칸은 선택
```

| | |
|---|---|
| 성공 | `200 { ok: true, student_code, display_name }` · 이미 선 계정이면 `{ ok: true, already: true }` |
| 게이트 실패 | `401 SIGNUP_GATE_FAILED` — **없는 학생번호 · 뒷자리 불일치 · 잠김이 전부 같은 응답**이다 |
| 비밀번호 규격 | `400 PASSWORD_TOO_SHORT`(6자 미만) · `PASSWORD_TOO_LONG`(72바이트 초과 — bcrypt가 자른다) |
| 가입 문항 | `400 CONTRACT_VIOLATION` + `field` — 셋 중 하나가 없거나 값목록 밖 |
| 본문에 신분 주장 | `400 CONTRACT_VIOLATION` — `learner_id`·`auth_user_id`를 실으면 거절 |

- 🔴 **응답을 가르지 않는 것이 이 엔드포인트의 핵심이다.** 가르면 학생번호의 **존재 여부가 새어** 명단을 훑을 수 있다. 잠김도 안 가른다 — 「잠겼다」는 응답 자체가 그 번호가 실재한다는 뜻이 되기 때문이다. 반면 **비밀번호 규격은 알려준다**(학생 본인이 방금 정한 값이라 새는 정보가 0이고, 안 알려주면 이유를 모르는 화면이 된다).
- 🔴 **`X-Contract-Ver`를 요구하지 않는다** — §4-1과 다른 판단이다. 그 헤더는 **학습 데이터의 모양**을 가르는 것이고 로그인은 학습 데이터를 싣지 않는다. 요구하면 앱의 판이 DB보다 앞선 날 **학생이 앱에 아예 못 들어온다.** 응답 봉투에는 일관성을 위해 DB의 판을 실어 준다.
- 🔴 **시도 제한이 이 판의 급소다** — 뒤 4자리는 1만 가지뿐이라 자릿수가 지키는 게 아니다. 뒷자리 실패만 `signup_attempts`를 올리고 **5에 이르면 잠긴다**(해제는 원장의 §4-5 — 2026-08-07까지 그 통로가 잠긴 학생을 못 집었다. 절단문서 ②-19). 규격 오류는 게이트를 밟기 전이라 세지 않는다.
- 🔑 **동시에 두 번 눌려도 계정은 하나다** — 잇기가 `where auth_user_id is null`이라 진 쪽은 덮어쓰지 못하고 `already: true`를 받는다. **두 번째 요청이 비밀번호를 바꾸지 못하는 것**이 계정 탈취를 막는 자리다(실측).
- 🔴 **가입 1회 문항 3칸이 여기 실리는 이유 = 다시 물을 자리가 없어서다**(2026-08-09 · L0 §704·§850). `home_aimag`·`gender`·`goal_track`은 「뒤에 붙이면 재적 전원에게 다시 물어야」 하는 값이고, 그중 `goal_track`은 덮어써지는 칸이라 나중에 물으면 **그때 목적이 아니라 오늘 목적**이 나온다(`goal_snapshot` = 유일한 완전 소급 불가). 그래서 **선택이 아니라 필수**이고, 검사는 **계정을 만들기 전에** 돈다 — 뒤로 밀면 거절당한 학생이 세 칸 빈 채로 등록돼 「이미 등록됨 = 게이트 실패」로 이 통로에 다시 못 들어온다. 값목록의 정본은 `lib/가입문항.js` 하나이고 앱·서버가 **같은 파일**을 쓴다(auth는 동봉).<br>⚠ 이 셋을 요구하는 판을 서버에 먼저 올리면 **옛 앱을 든 학생이 등록에서 400**을 만난다 — 배포 순서는 앱 → 서버다.

### 4-5. `POST /v1/auth/reset` — 원장의 「비밀번호 초기화」 (✅라이브 · 2026-08-07)

**director 토큰**으로 부른다. 입력 `{ student_code }` → 출력이 **두 갈래**다.

| 학생 상태 | 출력 | 무엇을 한 것인가 |
|---|---|---|
| 계정 있음(`auth_user_id` 있음) | `200 { ok, student_code, temp_password, expires_in_minutes: 30 }` | 비밀번호 초기화 |
| 계정 없음(첫 등록 전) | `200 { ok, student_code, unlocked: true }` — **`temp_password` 없음** | 첫 등록 잠금 해제 |

- 🔴 **잠금 해제가 이 통로에 있는 이유**(절단문서 ②-19 · 2026-08-07 수리). 뒤 4자리를 5번 틀리면 그 학생의 첫 등록이 잠기는데(§4-4), `signup_attempts`를 0으로 되돌리는 곳은 ⓐ첫 등록 성공 ⓑ임시로그인 성공 ⓒ여기 셋뿐이고 **앞의 둘은 잠긴 학생이 못 지난다.** 그런데 이 통로가 `auth_user_id is not null`로 걸러 **잠긴 학생만 정확히 빠져나갔다** — 학생번호는 순번이라 아무나 5번씩 틀려 전교생을 그 상태로 몰 수 있었고, 되돌리는 길은 DB 직접 수정뿐이었다.
- 🔴 계정이 없는 학생에게는 **임시번호를 내지 않는다** — 줄 계정이 없어서다. 화면은 두 결과를 갈라 그린다(한 갈래로 그리면 원장이 빈칸을 「번호」로 읽어 학생에게 불러 준다).
- 🔴 **`temp_password`는 이 응답에서 딱 한 번만 나온다.** 화면이 보여주고 끝이며 **저장·전달 금지**(L0 §4-2-2 ⚠). 서버도 평문을 안 갖는다 — **해시로만** 든다.
- 🔴 **GoTrue를 먼저 갈고 DB를 나중에 쓴다**(절단문서 ②-18). 둘은 한 트랜잭션에 못 묶이므로 순서가 곧 「반쯤 실패했을 때 남는 상태」다. 반대로 하면 GoTrue가 실패한 날 **감사표엔 「초기화했다」가 남고 옛 비밀번호는 살아 있다** — 초기화가 막으려던 바로 그 사고에서 초기화가 아무것도 안 한 것이 되고, 원장 화면엔 500만 떠서 아무도 모른다. 지금 순서면 실패는 「비번은 죽었고 임시번호는 안 나왔다」로 남고 **한 번 더 누르면 복구된다**.
- 🔴 **역할은 서버가 표에서 확정한다** — 클라이언트는 주장만 하고, `service_role`은 RLS를 우회하므로 그 주장을 믿는 순간 아무나 남의 비밀번호를 초기화한다. 살아 있는지 판정은 `engine.session_alive()` **한 곳**에서 온다(토큰 주장을 `request.jwt.claims`에 넣어 RLS와 같은 함수를 부른다 — 여기서 조건을 다시 적으면 두 축이 갈라진다).
- 🔑 **「원장이 아니다」와 「그런 학생이 없다」를 가르지 않는다** — 둘 다 `403 FORBIDDEN`. 가르면 원장 아닌 토큰으로 학생번호의 실재 여부를 훑을 수 있다.
- 함께 일어나는 일: 옛 비밀번호 무효화(난수로 갈아끼움) · `revoked_before=now()`(기존 세션 폐기) · `signup_attempts=0` · `staff_access_log` 1행(**번호는 안 적는다**). 잠금 해제 갈래는 `signup_attempts=0` + `staff_access_log` 1행(`action='learner.signup_unlock'`)만 — 비밀번호도 세션도 없어 나머지가 할 일이 없다.

### 4-6. `POST /v1/auth/temp-login` — 임시번호로 들어와 새 비밀번호를 정한다 (✅라이브 · 2026-08-07)

anon 키로 부른다. 입력 `{ student_code, temp_password, new_password }` → `200 { ok: true }`. 그 뒤 §2의 1번(`signInWithPassword`)으로 들어간다.

- 없는 번호 · 초기화된 적 없음 · **만료** · 틀림 · 잠김이 **전부 같은 401**이다(§4-4와 같은 축).
- 🔴 **1회용** — 성공하면 해시·만료를 지운다. 안 지우면 만료까지 계속 되는 두 번째 비밀번호가 된다.
- 틀리면 `signup_attempts`가 오르고 5에서 잠긴다 — 6자리(100만 가지)를 만료 전까지 마음껏 대입하지 못하게 하는 유일한 장치다.

> **라이브 실측 36/36** = `tools/인증왕복시험.js`(리허설 · 재실행 가능). 회귀가 못 보는 것만 잰다 — 동봉이 풀렸나 · GoTrue가 계정을 만드나 · 실패가 실제로 세지나 · **만든 계정으로 정말 로그인되나** · 학생 토큰으로 초기화가 막히나 · 평문이 DB·감사표에 없나 · **초기화가 옛 비밀번호도 죽이나** · 임시번호가 1회용인가 · **만료된 번호가 맞아도 막히나** · **잠긴 학생이 원장 해제 뒤 앱에서 다시 등록되나**(그전엔 이 시험이 `update` 로 직접 풀고 있었다 — 회귀가 제품에 없는 통로를 쓰면 그 통로가 없다는 사실이 안 보인다).
>
> ⚠ 시험이 만든 **리허설 원장은 지우지 않는다** — `staff_access_log`가 append-only이고 FK가 `restrict`라 **감사 행이 있는 직원은 지울 수 없다.** 결함이 아니라 감사 무결성이 설계대로 도는 것이고, 지우려 들면 시험이 2회차부터 영원히 빨개진다.

## 5. 오류 규격

```json
{ "code": "CONSENT_MISSING", "message": "사람이 읽는 한국어 한 문장",
  "field": "consent_ver", "retryable": false }
```

| code | HTTP | 재시도 | 앱이 할 일 |
|---|---|---|---|
| `AUTH_REQUIRED` | 401 | ✗ | 로그인 화면 |
| `AUTH_EXPIRED` | 401 | ✓ **1회** | 토큰 갱신 후 재전송. 또 실패하면 로그인 화면.<br>🔴 **이 코드를 내는 서버 코드는 저장소에 0줄이다** — `verify_jwt=true` 라 만료 토큰은 게이트웨이가 함수 **앞에서** 자르고 그 응답에는 우리 봉투가 없다(`error.code` 가 비어 온다). 그래서 앱의 분기 조건은 **HTTP 401 자체**이고, 아래 「`code`로만 분기」의 **유일한 예외**다(§7-6). 코드로 가르는 통로를 지었으면 한 번도 안 돌았다 |
| `CONSENT_MISSING` | 409 | ✗ | 🔴 **재전송으로 풀리지 않는다**(c6 정정). 서버 검사가 `agreed_at <= occurred_at`이라 **사후 동의는 과거 사건을 유효하게 만들지 못한다**(그리고 철회 뒤에는 `occurred_at`을 철회 전으로 적어도 `revoked_at > now()` 검사가 막는다 — 「철회 후 수집 0건」 · 20260807120000) — c5까지 이 칸은 「보관하고 동의 후 재전송」이라 적혀 있었고, 그대로 구현하면 앱이 **영원히 거절되는 큐**를 안고 돌거나 학생 기록을 조용히 잃는다. 정답은 **수집 전에 막는 것**이다: 녹음·제출 화면에 들어갈 때 유효 동의를 확인하고, 없으면 **흐름을 안 열고 막힘 카드를 그린다.** 🔴 **앱이 동의를 받지 않는다** — 동의는 운영자 통로이고(닫힌 결정) 앱에는 그 화면이 없다. 그래서 학생 쪽 처방은 「동의하고 계속」이 아니라 「원장에게 문의」다. 🔴 **막는 것은 화면만이 아니라 오프라인 큐까지다**(2026-08-09 · talk `f8c8758`) — 렌더만 막으면 초기화 효과·`AppState` 복귀가 밀린 발화를 그대로 밀어 서버에서 `retryable:false` 로 접히고 **`밀린것` 에서 영영 빠진다**(동의가 다시 서는 날 나갈 수 있었던 발화가 죽는다 · 판정 정본 = `lib/제출로그.js` `보낼것(로그, 막힘)`). 이 오류가 실제로 뜨면 **앱 게이트가 뚫린 것**이므로 개발자 보고 대상이고, 그 이벤트는 파기한다 |
| `CONTRACT_VIOLATION` | 400 | ✗ | 그 항목만 격리 + 개발자 보고. 값목록·필수 필드 위반 |
| `PAYLOAD_INVALID` | 400 | ✗ | 〃 (payload 모양) |
| `CONTRACT_VER_MISSING` | 400 | ✗ | 헤더 누락 — 앱 버그 |
| `CONTRACT_VER_UNSUPPORTED` | 426 | ✗ | 업데이트 안내 |
| `PAYLOAD_TOO_LARGE` | 413 | ✗ | 배치를 쪼개 재전송 |
| `RATE_LIMITED` | 429 | ✓ | `Retry-After` 만큼 대기 |
| `SERVER_ERROR` | 5xx | ✓ | 지수 백오프(최대 6회, 상한 15분) |
| (네트워크 실패) | — | ✓ | 큐 유지 |

🔑 **`retryable`이 계약에 없으면 앱은 영구 오류를 무한 재시도한다** — 배터리·쿼터·서버가 같이 탄다. 반대로 일시 오류를 버리면 학습이 사라진다. **판단을 앱에 맡기지 않고 서버가 말한다.**

🔑 **`message`는 사람이 읽는 문장이고 분기 조건이 아니다.** 앱은 **`code`로만** 분기한다(문구는 몽골어 번역·다듬기로 계속 바뀐다) — 예외는 위 `AUTH_EXPIRED` 하나이고, 그건 봉투가 아예 안 오기 때문이다.

## 6. 버전 정책

| 축 | 무엇 | 규칙 |
|---|---|---|
| `api_ver` | URL `/v1` | **깨는 변경만** 올린다. 올리면 구 버전을 최소 1개 릴리스 주기 병행 |
| `contract_ver` | `c8`… | 앱이 헤더로 알리고 서버가 응답에 자기 것을 싣는다. **이 문서의 값은 예시가 아니라 정본과 대조된다**(`tests/C0계약.test.js`) |
| `payload.ver` | 정수 | 이벤트별 payload 모양 (§4-1) |

- **값목록 추가는 하위호환이다** — 구 앱은 새 값을 안 보낼 뿐 계속 작동한다. **이름 변경·삭제는 금지**(과거 집계가 깨진다 · c3 `값목록_규칙` 승계).
- 새 **필수** 필드가 생기면: 서버가 그 값을 유추할 수 있으면 유추하고, **없을 때만** `CONTRACT_VER_UNSUPPORTED`로 앱 업데이트를 요구한다. 필수 필드 추가마다 구 앱을 끊으면 앱 심사 지연이 곧 데이터 구멍이 된다.
- Codex는 **화면 편의를 위해 승인 없이 이 계약을 바꾸지 않는다**(분업 §3). 변경은 C0 개정 절차로.
