## 0. 이 문서가 있는 이유

2026-08-05 유호님 확정 2건이 이 저장소의 성격을 바꿨다.

1. **Glide 앱 폐기 · 네이티브 전체 재구축** — 이 저장소는 「회화 앱 v0」이 아니라 **학생 접점의 본진**이다.
2. **분업** — 기획은 유호님 1인, 설계는 같이(펜은 하나), 코딩은 나눈다.

작업자가 셋(유호님·Claude·Codex)이고 도구가 서로의 하네스를 못 본다. 그래서 **완료 조건과 결정권을
문서 한 곳에 못박는다** — 프로즈로 부탁하는 대신 표로 정하고, 기계가 볼 수 있는 것은 CI가 본다.

## 1. 가장 중요한 원칙 — 층이 아니라 기능으로 완성한다

> **수직 슬라이스**: 기능 하나를 데이터부터 실기기까지 **끝까지 관통시킨 뒤** 다음 기능으로 간다.

초안 v1은 층별(계약→백엔드→화면→통합)로 나눴다. **GPT 적대 검수가 이 지점을 정확히 반박했고 채택했다** —
층별로 각자 완성한 뒤 마지막에 합치면 통합 문제가 **가장 늦게(=가장 비쌀 때)** 드러난다.
우리 실측도 같은 말을 한다: 회귀 15/15 초록을 라이브가 뚫었고(F081), 이 저장소의 0일차 원칙 자체가
「기능 0개 상태에서 배포 경로부터 관통」이었다.

기반(F0·C0)은 **한 번만** 만들고, 그 뒤로는 기능마다 이 순서를 반복한다:

```
사용자 시나리오 → 데이터 계약(그 기능 몫 · 의미→물리) → 백엔드 구현(§6 스택: Supabase·Edge Fn 정본
— 시트·Apps Script/n8n은 이행기 어댑터 몫만) → Expo 화면 구현
→ 실제 연동 → 오류·빈 상태 검증 → 몽골어 검수 → 기능 단위 승인 → 다음 기능
```

대조군 유지). 클로드 몫 = 의미 계약 · 시트/AS 어댑터 · CI · 통합 판정.

## 3. 결정권 — 모두 의견을 내되 최종은 한 명

| 결정 대상 | 최종 결정권자 |
|---|---|
| 제품 범위 · UX 우선순위 · 출시 여부 | **유호님** |
| 데이터 계약 **의미층**(무엇을 남기나·필드 뜻·성과 정의) | 클로드 — Codex 기술 거부권 (§8-1) |
| 데이터 계약 **물리층**(DDL·RLS·마이그레이션) · 그 테스트 | **Codex** — 클로드 의미 거부권 (§8-1 · v3 개정) |
| Expo 컴포넌트 · 프런트 구조 | **Codex** |
| 몽골어 표현 정본 | 원어민 검수자(미채용 시 보류 — 제미나이는 검문이지 정본이 아니다) |
| 통합 · **출시 준비 완료 판정** | 클로드 — 실제 출시·운영 배포 승인은 **유호님**(첫 행) |
| 브랜드 시각 정본(색·폰트·워드마크) | 유호님 확정 킷 (`DESIGN.md`) — 누구도 임의 변경 불가 |

- 클로드는 통합 책임자라고 해서 **Codex의 프런트 구조를 임의로 바꾸지 않는다**(지적은 리뷰로).
- Codex는 화면 편의를 위해 **승인 없이 API 계약을 바꾸지 않는다**(변경 요청은 C0 개정 절차로).
- **운영 배포 승인(유호님)은 전 경로에 걸린다** — EAS production·스토어 제출·`eas update`(OTA)·Supabase 운영
  마이그레이션/Edge Fn 배포·n8n 운영 활성화·운영 환경변수/시크릿 변경. (Apps Script는 기존 `/deploy`·`deploy-live`
  통로 유지.) 승인은 **정확한 커밋·산출물에 고정**되고 이후 변경은 재승인 · 긴급 롤백만 예외(사후 즉시 기록·보고).
  기계 탐지의 범위는 정확히: 워크플로 안의 EAS·Supabase **직접 명령만** 잡는다(`tests/출시가드.test.js` —
  간접 명령·n8n·시크릿·로컬 수동 배포는 승인 **정책**층) · 절차 정본 = `docs/배포_경로.md`.

## 4. 검수는 전수가 아니라 위험도 기반

전부 교차 검수하면 안전하지만 느리다. 공용지침의 검증 결정표(규모 ∝ 되돌림 비용)를 이 저장소에 적용한다.

| 위험도 | 대상 | 검수 |
|---|---|---|
| **전수 교차** | 데이터 계약 · 인증·권한 · 핵심 데이터 쓰기 · 전역 상태 · 배포 설정 | 상대방이 반드시 본다 |
| 간단 | 개별 화면 · 스타일 · 단순 문구 | 1패스 |
| 자동 | 포맷 · 타입 · 반복 컴포넌트 | CI만 |
| 원어민 | 학생에게 **직접 보이는** 몽골어 | 사람이 본다(제미나이는 1차 필터) |

**발주서는 작성자와 검수자를 나눈다** — 클로드가 쓴 발주서를 Codex가 구현 **전에** 검수한다:
①입출력이 구체적인가 ②빈 값·중복·네트워크 실패가 정의됐는가 ③완료 기준을 테스트로 판정할 수 있는가
④모바일에서 구현 불가능하거나 모순된 요구가 없는가. (자기 가정을 자기가 통과시키는 것을 막는다.)

## 5. 반드시 들어가는 운영 안전장치 (착수 전 배선)

GPT 검수가 지적한 누락 — 기능이 아니라 **없으면 나중에 소급 불가**가 되는 것들.

- **개발용 / 검수용 / 운영용 시트 분리** (실학생 데이터에 개발이 닿지 않는다)
- Apps Script 호출 권한·비밀값 관리 · **할당량과 타임아웃 대응**(현 개인 계정 등급 기준 — 메일 100통/일 · 실행 6분)
- 동시 수정·중복 요청 방지(멱등 키)
- 스키마 변경 시 **기존 데이터 마이그레이션 절차**
- 로그·오류 추적 · 백업·롤백 절차 · 최소한의 실기기 테스트
- **결정 기록 — 결정의 정본 = repo 커밋 문서**(이 문서·계약·설계 정본·기각 이력). **memory = 검색·인수인계
  보조 색인**(결정권 없음). 둘이 갈리면 정본이 이기되 **충돌 자체가 「정본 미반영 결함」**이다 — 더 새로운
  유호님 확정을 즉시 정본에 옮긴다

## 6. 스택 — ✅ 유호님 확정 (2026-08-05)

| 층 | 확정 |
|---|---|
| **원본 데이터** | **Supabase(Postgres)** — 학습 데이터의 정본이 여기 산다 |
| 운영·리포트·수동 검토 | 구글 시트 (사람이 눈으로 보고 손으로 고치는 층) |
| 자동화·배치 | n8n · Apps Script |
| 앱 | Expo(네이티브 + 웹) |

「시트를 원본으로 유지」(A안)는 **기각됐다 — 🚫재제안 금지.**
⚠ 시트로 **역방향 쓰기**가 생기는 지점은 P0 계약에서 명시적으로 정한다(두 곳이 같은 값을 쓰면 갈라진다).

**Apps Script 천장 — 현 개인 계정 등급의 공식 쿼터**(왜 원본을 옮기는지의 근거 · 2026-08-05 확인 ·
Workspace 등급은 수치가 다르고 Google이 예고 없이 바꾼다 — 인용 전 재확인+잔여 실측): 동시 실행 **30/사용자** ·
실행 **6분** · 트리거 총 **90분/일** · 메일 100통/일 · URLFetch 2만/일.
(CORS/302 함정은 네이티브 앱엔 무해하고 Expo **웹 버전에만** 해당된다.)

- 🔴 **인증**: Glide가 로그인을 대신하고 있었으므로 폐기와 함께 통로가 사라진다 → **Supabase Auth**로 간다
  (스택 확정으로 자연히 정해졌다). 학생 식별 키를 기존 학생ID와 어떻게 잇는지는 **C0 계약에서 확정**.
- ⚠ 알림은 메일이 아니라 **Expo 푸시**로 옮긴다(무료·초당 600건) — **알림 경로에서** 메일 천장을 치운다.
  단 푸시는 도착 보장이 아니다(중요 통지는 앱 내 표시 병행). 인증 메일은 애초에 없다 — L0 §4 합성 이메일이라
  가입 확인·복구 메일 흐름 자체가 없다(복구 = 학원 재발급 · L0 §4-2).
- 상류 레인 = **`계약/`**(두 저장소 공용 어휘).

> **그래도 유지하는 설계**: 화면은 백엔드를 직접 모른다. `계약/`이 정의한 API만 알고 그 뒤에 어댑터 한 층을 둔다.
> 스택이 확정됐다고 이 층을 빼지 않는다 — 시트↔Postgres 두 소스가 공존하는 이행기가 실재하기 때문이다.

## 7. S1 = 실측 게이트 겸임

첫 슬라이스는 기능이면서 동시에 **분업 구성의 성적표**다. 세는 단위는 유호님이 직접 셀 수 있는 것으로:

- 리뷰 반려 횟수 · 재작업 왕복 수 · 착수→실기기 도달 시간 · 그 주 각 도구의 한도 잔량
- **§8-4 품질 계수의 위반·미달 건수**(기계가 재고, 보고는 건수로 환산)

같은 기능을 두 번 만들지 않는다(낭비). 미달 레인은 **숫자를 보고** 재배치한다 —
「어느 모델이 낫다」는 믿음이 아니라 계수로 정한다.

## 8. 엔진·계약 국면 역할 — v3 확정 (2026-08-06)

> 코어 엔진(회사의 뇌) 설계와 데이터 계약의 역할분배. 핵심 축 = **「엔진이 학습할 수 있도록 설계」** —
> 유호님: "지금 아니면 할 수 없으니 손해가 있더라도 확실하게."

### 8-1. 두 승인키 — 펜과 거부권의 대칭

| 층 | 펜(초안) | 거부권(미해결 P0 = 동결 불가) |
|---|---|---|
| **교육·학습 설계**(엔진 설계 정본·학습자 모델·오류 의미·개인화 규칙) | 클로드 | Codex 심문(8-2 게이트) |
| **의미 계약**(무엇을 남기나·필드 뜻·이벤트·성과 정의·학습 불변조건) | 클로드 | **Codex — 기술 실행 키** |
| **물리 계약**(DDL·RLS·마이그레이션·인덱스·Edge Function·계약 준수 테스트) | **Codex** | **클로드 — 교육 의미 키** |
| 최종 사업적 선택 · 계약 안의 제품 방향 자리(동의·보존·학습 범위·프라이버시 경계) | **유호님** | — |

- **문서는 쪼개지 않는다** — L0 등 기존 문서의 **개정 발의자**를 층으로 가른다.
- **기존 L0·C0·M0 재작성 금지**: C0=Codex 소비자 승인(기존 절차)이 곧 인수 · L0=Codex 실행 가능성 인수 검수 1회(필요 수정만).
- **첫 물리층 발주 1건 = Codex 작성자 실측 게이트** — 검수자 실측(P0 11건 적중)은 있으나 작성자 실측은 0. 반려·왕복·시간 계수로 확정(§7과 같은 축).
- 모델 충돌 시 어느 AI도 임의 결정하지 않는다 — 유호님께 선택지+영향만(§3 기존 원칙).

### 8-2. 동결 게이트 6조항 (설계·계약 공통 · 계약/정본 동결 직전 필수)

> ⏸ **이 게이트는 꺼져 있다** (2026-08-06 유호님 지시: *"앞으로 심문은 하지마. 필요할 때 다시 말할게"*) — 어떤 세션도 동결 심문을 실행하지 않는다. 재가동 조건 = **유호님의 명시 지시 하나뿐**(그때 아래 6조항 그대로 적용). 꺼진 동안 정본의 효력 = 유호님 확정 그 자체.
>
> **심문 상태 구분(오독 방지 · 2026-08-06 정밀화)**: **미실행·타임아웃·유호님 중단 = 「판정 없음」**이다 — 결함 발견이 아니며, 현행 정본으로 쓸 수 있으나 **동결 통과로 간주하지 않는다**(조항②와 같은 축). **실제 P0가 발견된 상태(failed_p0)만 결함**이다 — 수정 전 동결 불가, 사용도 수정이 먼저다. 유호님이 특정 커밋에 한해 면제하면 사용 가능하되 **면제도 통과가 아니다**.

①심문 입력 = 대상 문서 **전문** + repo 커밋된 프롬프트 템플릿(appsscript `docs/_ops/동결심문_프롬프트.md` — 회차별 선별 금지) ②빈 출력·타임아웃 = **확인 불가 = 동결 불가**(통과 아님) ③동결은 codex 있는 **로컬 세션 전용** ④심문 P0 기각 시 유호님 보고 1줄 ⑤수정 후 지문이 바뀌면 **재심문** ⑥렌즈에 문서 간 모순 검사 + **「기능→이벤트→필드→엔진 부품→회수 시점」 사슬** + 「지도 질문→필요 필드」 대응표(결정론 검사) 포함. 심문 모델 = luna max 기본(sol은 유호님 지시 시만).
