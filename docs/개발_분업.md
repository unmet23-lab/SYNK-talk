# SYNK-talk 개발 분업과 완료 기준

> 2026-09-09 · 현재 역할·자율 실행·모델 선택·인계는 [공통 원칙 연결](공용지침.md)의 SYNK-appsscript 운영 정본을 따른다. 이 문서는 앱의 기능 완성 방식과 계약·품질 기준을 연결한다. 과거의 고정 모델 배치, Codex 실행 장애, 커밋마다 재승인하는 규칙은 현재 절차로 사용하지 않는다. 제품·동의·데이터·브랜드 계약은 그대로 유지한다.

## 0. 책임과 범위

직접 요청을 받은 주담당이 조사·설계·구현·검증·통합·보고까지 책임진다. 필요한 전문가와 독립 검토는 목표·근거·수용 조건을 주어 배치한다. 역할을 정했다는 이유로 구현·통합을 다른 모델 호출 뒤에 항상 대기시키지 않는다. 공동 파일과 배포의 통합 책임은 하나다.

## 1. 기능 하나를 끝까지 완성한다

사용자 시나리오 → 관련 제품·데이터·API 계약 → 서버와 Expo 구현 → 실제 연동 → 오류·빈 상태·재시도·오프라인 확인 → 필요한 언어 검수 → 완료 증거로 이어간다. 이미 만들어진 기반을 다시 만들지 않고 현재 코드와 시험을 먼저 확인한다.

## 2. 단계와 계약의 자리

아래 코드는 자료를 찾는 이름이다. 과거 단계표의 체크나 담당자 이름을 현재 구현 상태로 취급하지 않는다.

| 구분 | 원문과 완료 기준 |
|---|---|
| P0 제품 | `P0_제품계약.md`: 사용자 시나리오·범위·완료 조건. 새 제품 방향·사업 약속은 사용자 결정 |
| F0 기반 | 현재 앱 진입·인증·공통 API·테마·CI. 개발 빌드와 관련 시험으로 실재 확인 |
| C0 API | `C0_API계약.md`: 요청·응답·오류·버전·소비자 호환과 왕복 시험 |
| L0 데이터 | `L0_데이터계약.md`와 `supabase/migrations/`: 저장 형태·불변·권한·이행 검증 |
| S1~Sn 기능 | 해당 기능이 저장부터 사용 경험까지 이어지는지 확인. 작은 기능 단위로 통합 |
| 콘텐츠·언어 | 현행 브랜드 원칙·용어·교육 계약. AI 의미 대조와 원어민 검수를 구분 |
| 출시·배포 | `배포_경로.md`의 현재 도구, 실제 권한 절차, 배포 후 재조회·실기기·복구 증거 |

## 3. 결정과 변경 권한

현재 요청과 이미 받은 권한 안의 구현·검증·커밋·push·배포는 단계마다 재승인받지 않는다. 요청 범위 밖의 새 사업 약속·지출·실제 인증 당사자 확인은 필요한 사용자 결정만 받는다. 배포가 요청되면 기존 배포 경로로 반영과 사후 확인까지 수행한다. CI가 스스로 운영 배포하게 만들거나 하네스·서비스의 보호 절차를 우회하지 않는다.

화면 편의를 위해 데이터·API 의미를 조용히 바꾸지 않는다. 변경 필요성을 관련 계약과 소비자 코드에 함께 반영하고, 이미 허용된 목표 안의 기술 결정을 특정 모델의 독점 권한으로 묶지 않는다. 동의·보관·교육 목적·브랜드의 새 의미 결정은 기존 확정 범위와 구분한다.

## 4. 검토와 검증

계약·인증·핵심 데이터 쓰기·전역 상태·배포 설정처럼 영향이 큰 변경은 독립 접근으로 검토한다. 단순 변경은 관련 증거에 맞는 검사로 끝낸다. 모델 3개 호출·반박 횟수·시험 선작성 순서를 모든 작업에 고정하지 않는다.

구현·인수 검토에서는 ①입출력 ②빈 값·중복·네트워크 실패 ③시험 가능한 완료 조건 ④실기기 제약과 계약 모순을 확인한다. 학생에게 직접 보이는 몽골어의 최종 원어민 검수는 AI 대조 결과와 구분한다. 빈 응답·시간 초과·미실행을 통과로 보고하지 않는다.

## 5. 운영과 변경 기록

개발·검증·운영의 대상과 데이터를 구분한다. 관련 변경에는 중복 방지, 데이터 이행, 로그·오류 추적, 백업·롤백과 실기기 검증을 적용한다. 원본·동의·권한의 불변은 [저장소 규약](이_저장소_규약.md)과 L0 계약을 따른다.

결정의 근거는 현재 사용자 요청과 저장소의 최신 결정 문서다. 기억은 찾는 단서이며 정본을 대신하지 않는다. 완료 시 관련 appsscript 트랙·결과·PR을 갱신하고, 배포 증거는 기존 `docs/_ops/배포장부.jsonl`과 대조한다. 새 중앙 큐나 상태 장부를 만들지 않는다.

## 6. 스택과 저장 경계

학습 원본은 Supabase(Postgres), 앱은 Expo, 인증은 Supabase Auth다. 구글 시트는 사람이 확인하는 운영·리포트 층이며 Apps Script·n8n 연결은 실제 사용 중인 어댑터와 계약을 확인한다. 시트를 학습 원본으로 되돌리지 않는다. 시트로 역방향 쓰기가 필요하면 P0의 해당 계약을 따른다.

화면은 C0 API를 사용하며 DB 직접 쓰기로 경계를 건너뛰지 않는다. 필드·값목록은 `계약/수집_교정_계약.json`의 현재 내용으로 대조한다. 과거 문서의 버전·할당량·기능 지원 수치를 복사하지 않고 필요한 시점에 현재 원문과 실제 환경을 확인한다.

## 7. 결과로 작업 방식을 조정한다

필요한 기능에서 재작업·반려·왕복·완료까지 걸린 시간과 오류를 확인한다. 실제 결과를 근거로 분업을 바꾸고, 특정 모델의 오래된 장애나 성적표를 현재 능력 제한으로 사용하지 않는다. 같은 기능을 비교용으로 중복 구현하지 않는다.

## 8. 엔진·계약 검토

### 8-1. 의미와 물리 구조를 함께 본다

의미 계약(무엇을 남기고 어떻게 쓰는가)과 물리 계약(DDL·권한·마이그레이션·서버)을 같은 목표로 연결한다. 관련 설계·L0·C0·계약 JSON의 경계를 유지하고 필요한 부분만 수정한다. 기존 계약을 새 매트릭스로 통째로 재작성하지 않는다. 작성·검토자는 해당 작업에 맞춰 배치하며 모델별 펜·거부권을 고정하지 않는다.

### 8-2. 중요한 계약 변경의 완료 증거

관련 원문과 소비자 코드를 실제로 읽고 문서 간 모순, 기능→이벤트→필드→엔진 소비→성과 회수 경로를 확인한다. 실제로 확인한 범위와 못 읽은 범위를 적는다. 미실행·시간 초과는 미확인이며 중요한 결함은 수정·재검증한다. 기존 계약이 정한 호환·왕복·동결 조건을 생략하거나 빈 결과로 통과시키지 않는다.

### 8-3. 언어·자료·다른 접근의 활용

Gemini/Antigravity를 포함한 전문가의 역할은 공통 운영 원칙과 현재 도구 지원을 따른다. 필요한 원문·최소한의 합성 자료로 작업하며 학생 식별 데이터와 자격증명은 넘기지 않는다. 몽골어 대조는 원어민 최종 검수와 구분한다.

### 8-4. 데이터·엔진 품질 기준

관련 변경에서 정상·중복·오프라인 재시도·동의 철회·타학생 접근·구버전 요청을 확인한다. 마이그레이션은 빈 DB·기존 데이터·중간 실패·복구를 검증하고 RLS·서버 키·개인정보 로그와 재현 가능한 모델·프롬프트·스키마 정보를 확인한다.

교육 품질은 개입→선택→전달→성과→검수의 기존 배선을 따라 확인한다. 수집과 학습 승격은 L0 §6-2·상위 엔진 계약을 따르며, 수집 원본·회사 비식별 집계·훈련 승격을 같은 상태로 간주하지 않는다. 파일럿의 검수 경로 조건은 P0·L0의 관련 계약으로 확인한다.

유지하는 수용 기준: **동의 철회 후 수집 0 · 타학생 접근 성공 0 · 같은 멱등키의 논리 중복 0 · 파생 재계산 불일치 0 · 필수 필드 완전성 100%**. 개입→선택→전달→성과 연결률·고아 이벤트 허용치·처리 기한은 해당 기능의 실측과 현재 계약으로 정한다. 문서에 기준을 적은 것과 운영에서 달성한 것은 구분한다.
