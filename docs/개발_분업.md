# SYNK-talk 개발 분업 — 정본 v2

> **유호님 확정 2026-08-05.** 초안(클로드) → 적대 검수(GPT) → 병합 → 유호님 채택으로 확정된 구성.
> 이 파일이 **누가 무엇을 정하고 무엇으로 통과를 판정하는지**의 유일한 정본이다.
> 개정은 유호님 확정으로만. 레인·커밋 규칙 등 저장소 고유 규칙은 `이_저장소_규약.md`.

## 0. 이 문서가 있는 이유

2026-08-05 유호님 확정 2건이 이 저장소의 성격을 바꿨다.

1. **Glide 앱 폐기 · 네이티브 전체 재구축** — 이 저장소는 「회화 앱 v0」이 아니라 **학생 접점의 본진**이다.
2. **분업** — 기획은 유호님 1인, 설계는 같이(펜은 하나), 코딩은 나눈다.

작업자가 셋(유호님·Claude·Codex)이고 도구가 서로의 하네스를 못 본다. 그래서 **완료 조건과 결정권을
문서 한 곳에 못박는다** — 프로즈로 부탁하는 대신 표로 정하고, 기계가 볼 수 있는 것은 CI가 본다.

## 1. 가장 중요한 원칙 — 층이 아니라 기능으로 완성한다

> **수직 슬라이스**: 기능 하나를 데이터부터 실기기까지 **끝까지 관통시킨 뒤** 다음 기능으로 간다.

초안 v1은 층별(계약→백엔드→화면→통합)로 나눴다. **GPT 적대 검수가 이 지점을 정확히 반박했고 채택했다** —
층별로 각자 완성한 뒤 마지막에 합치면 통합 문제가 **가장 늦게(=가장 비쌀 때)** 드러난다.
우리 실측도 같은 말을 한다: 회귀 15/15 초록을 라이브가 뚫었고(F081), 이 저장소의 0일차 원칙 자체가
「기능 0개 상태에서 배포 경로부터 관통」이었다.

기반(F0·C0)은 **한 번만** 만들고, 그 뒤로는 기능마다 이 순서를 반복한다:

```
사용자 시나리오 → 데이터 계약(그 기능 몫) → Apps Script 구현 → Expo 화면 구현
→ 실제 연동 → 오류·빈 상태 검증 → 몽골어 검수 → 기능 단위 승인 → 다음 기능
```

## 2. 단계표

| 단계 | 주 담당 | 검수·결정 | 통과 기준 |
|---|---|---|---|
| **P0** 제품 계약 | 클로드 초안 | **유호님 확정** · Codex 실현성 검토 | 사용자 시나리오·완료 조건·S1 선정 |
| **F0** 개발 기반 *(1회)* | 클로드=CI·환경 분리·Mock / Codex=공통 앱 기반 | 상호 검수 | 개발 빌드가 폰에 뜬다 · CI가 타입·테스트·빌드·계약일치·환경변수를 본다 |
| **C0** 데이터 계약 | 클로드 초안 | **Codex 소비자 승인** 후 동결 | 타입 · 예시 payload · **오류 규격** · 권한 · 버전 정책 |
| **S1** 첫 기능 관통 | 백엔드=클로드 / 화면=Codex | 클로드 통합 승인 | 실제 시트 → 실기기까지 작동 **+ 실측 계수 확보** |
| **S2~Sn** 나머지 기능 | 기능별 수직 분업 | 기능별 교차 검수 | 기능마다 독립 배포 가능 |
| **콘텐츠·몽골어** | 클로드 정본 | 제미나이 1차 → **원어민 게이트** | 용어집·금칙어·골든 문장 통과 |
| **시스템 QA** | Codex 중심 | 클로드 판정 | 주요 흐름·오류·재시도·오프라인 |
| **출시 후보** | 클로드 릴리스 책임 | Codex 독립 검수 + **유호님 승인** | 실기기·로그·롤백·백업 확인 |

**F0의 공통 앱 기반은 Codex 단일 소유로 선행한다** — 내비게이션 · 전역 상태 · API 클라이언트 층 ·
디자인 토큰 배선 · 공통 폼/오류 처리. 이걸 여럿이 동시에 만지면 화면 병렬화가 충돌로 되돌아온다.
⚠ 단, **토큰의 값은 브랜드 킷 정본이 상위**다(Codex는 배선하되 색·폰트를 정하지 않는다).

## 3. 결정권 — 모두 의견을 내되 최종은 한 명

| 결정 대상 | 최종 결정권자 |
|---|---|
| 제품 범위 · UX 우선순위 · 출시 여부 | **유호님** |
| 데이터 계약 · 백엔드 구조 | 클로드 |
| Expo 컴포넌트 · 프런트 구조 | **Codex** |
| 몽골어 표현 정본 | 원어민 검수자(미채용 시 보류 — 제미나이는 검문이지 정본이 아니다) |
| 통합 · 릴리스 여부 | 클로드 |
| 브랜드 시각 정본(색·폰트·워드마크) | 유호님 확정 킷 (`DESIGN.md`) — 누구도 임의 변경 불가 |

- 클로드는 통합 책임자라고 해서 **Codex의 프런트 구조를 임의로 바꾸지 않는다**(지적은 리뷰로).
- Codex는 화면 편의를 위해 **승인 없이 API 계약을 바꾸지 않는다**(변경 요청은 C0 개정 절차로).

## 4. 검수는 전수가 아니라 위험도 기반

전부 교차 검수하면 안전하지만 느리다. 공용지침의 검증 결정표(규모 ∝ 되돌림 비용)를 이 저장소에 적용한다.

| 위험도 | 대상 | 검수 |
|---|---|---|
| **전수 교차** | 데이터 계약 · 인증·권한 · 핵심 데이터 쓰기 · 전역 상태 · 배포 설정 | 상대방이 반드시 본다 |
| 간단 | 개별 화면 · 스타일 · 단순 문구 | 1패스 |
| 자동 | 포맷 · 타입 · 반복 컴포넌트 | CI만 |
| 원어민 | 학생에게 **직접 보이는** 몽골어 | 사람이 본다(제미나이는 1차 필터) |

**발주서는 작성자와 검수자를 나눈다** — 클로드가 쓴 발주서를 Codex가 구현 **전에** 검수한다:
①입출력이 구체적인가 ②빈 값·중복·네트워크 실패가 정의됐는가 ③완료 기준을 테스트로 판정할 수 있는가
④모바일에서 구현 불가능하거나 모순된 요구가 없는가. (자기 가정을 자기가 통과시키는 것을 막는다.)

## 5. 반드시 들어가는 운영 안전장치 (착수 전 배선)

GPT 검수가 지적한 누락 — 기능이 아니라 **없으면 나중에 소급 불가**가 되는 것들.

- **개발용 / 검수용 / 운영용 시트 분리** (실학생 데이터에 개발이 닿지 않는다)
- Apps Script 호출 권한·비밀값 관리 · **할당량과 타임아웃 대응**(메일 100통/일 · 실행 6분)
- 동시 수정·중복 요청 방지(멱등 키)
- 스키마 변경 시 **기존 데이터 마이그레이션 절차**
- 로그·오류 추적 · 백업·롤백 절차 · 최소한의 실기기 테스트
- **결정 기록**(이 문서 + memory) — AI 작업자가 참고할 단일 명세

## 6. 백엔드 — ⏳ 유호님 판정 대기 (0일차 「Supabase」 전제가 08-05에 흔들렸다)

0일차 규약은 「Expo + Supabase」였다. 08-05 재구축 확정 뒤 백엔드를 다시 재고 중이다.
**실측된 천장**(공식 쿼터 · 2026-08-05): 동시 실행 **30/사용자**·1,000/스크립트 · 실행 **6분** ·
트리거 총 실행 **90분/일**(Workspace 6시간) · 메일 100통/일(Workspace 1,500) · URLFetch 2만/일(Workspace 10만).
**CORS/302 함정은 네이티브 앱에는 해당 없다**(브라우저 정책) — 단 Expo **웹 버전은 해당된다**.

- 🔴 **함께 드러난 구멍: 인증.** Glide가 로그인을 대신하고 있었다 — 폐기하면 **학생 인증 통로가 없다.**
  백엔드 선택보다 이게 먼저 정해져야 한다(자체 토큰 / Supabase Auth만 / 구글 계정).
- 세 길과 권고는 memory `app-rebuild-native-2026-08-05` 「백엔드 판정」 절.
- 확정 전까지 **상류 레인은 `계약/`**(두 저장소 공용 어휘)로 둔다 — 어느 백엔드든 이 계약을 읽는다.

> **어느 쪽이든 지키는 설계**: 화면은 백엔드를 직접 모른다. `계약/`이 정의한 API만 알고,
> 그 뒤에 어댑터 한 층을 둔다. 백엔드를 바꿔도 화면을 다시 쓰지 않는다.

## 7. S1 = 실측 게이트 겸임

첫 슬라이스는 기능이면서 동시에 **분업 구성의 성적표**다. 세는 단위는 유호님이 직접 셀 수 있는 것으로:

- 리뷰 반려 횟수 · 재작업 왕복 수 · 착수→실기기 도달 시간 · 그 주 각 도구의 한도 잔량

같은 기능을 두 번 만들지 않는다(낭비). 미달 레인은 **숫자를 보고** 재배치한다 —
「어느 모델이 낫다」는 믿음이 아니라 계수로 정한다.
