# 검수 내부 계약 v1 — 직원 통로 (`review`)

> 발주 §3 이 **「4구멍의 요청/응답·오류 코드·멱등키·권한 검사는 착수 전에 한 자리에 적는다」**
> 고 못박은 그 한 자리다. 없으면 Expo 화면과 Edge Function 이 서로를 상상하며 짓는다.
>
> **정본 관계** — 물리·권한 = `docs/L0_데이터계약.md` §4-5 · 화면·게이트 = `docs/발주_수집파이프라인.md` §3
> · 판(무엇을 읽는가) = `engine.review_queue`(`20260809050000_review_c10`) · 학생 API = `docs/C0_API계약.md`.
> 🔴 **C0 의 닫힌 엔드포인트 2개는 바뀌지 않는다** — 직원 통로는 학생 API 가 아니다(별도 축).

---

## §0 판정 — 함수는 **넷이 아니라 하나**, 경로가 셋이다

발주 §3 의 「4구멍」은 **능력 목록이지 배포 단위가 아니다.** 갈라 보면 넷 중 하나는 엔드포인트가 아니다:

| 발주의 구멍 | 실제 정체 |
|---|---|
| 큐 읽기 | 엔드포인트 ① |
| 오디오 signed URL | 엔드포인트 ② |
| 승인 쓰기 | 엔드포인트 ③ (⛔ c11 선행) |
| **조회 감사** | **엔드포인트가 아니라 §2 불변식** — ①·②의 부수 효과다 |

그래서 **Edge Function 1개(`review`) + 하위 경로**로 짓는다. 근거 셋:

1. **L0 §4-5 ④ 가 「읽는 지점이 하나」라는 전제 위에 서 있다.** 함수를 넷으로 쪼개면 그 전제를
   **배포 구조가 먼저 흔든다** — 새 형제가 감사 1행을 빠뜨려도 증상은 「통과」다(가드가 등록층에서
   새는 형태 ③: 라우팅이 규칙보다 좁아지는 자리).
2. **직원 인증·폐기 판정이 한 자리에 남는다.** `lib/토큰.js` 가 사본을 금지하는 것과 같은 축 —
   그 판정도 새는 방향이 언제나 「통과」다.
3. Supabase 는 `review/*` 하위 경로를 **같은 함수로 라우팅**하므로 REST 경로를 포기하지 않는다.

🚫 **재제안 금지**: 함수 4개로 쪼개기 · `action` 파라미터(경로가 이미 그 일을 한다) ·
직원 경로를 학생 함수에 합치기 · 조회 감사를 비동기로 빼기(§2).

## §1 공통

**인증** — `Authorization: Bearer <직원 토큰>`. 플랫폼의 `verify_jwt` 는 **서명만** 본다.

- 주체 = `토큰주체(req)`(`lib/토큰.js`) · 없으면 `AUTH_REQUIRED`.
- 폐기 = **`살아있는직원(sql, 주체, iat)` 을 `lib/토큰.js` 에 신설**하고 그것만 쓴다.
  🚫 Edge Function 안에 사본을 두지 않는다 — `살아있는학생` 이 다섯 곳에서 빠져 있던 자리와
  같은 형태다(절단문서 ②-15). `iat` 는 **폐기된 적 있는 계정에서만** 본다(SQL `session_alive()` 와
  같은 순서 · 못 읽으면 거부 = fail-closed).
- 역할 = `inspector` 또는 **`director`**. 🔑 `director` 를 넣는 이유: 검수자 채용은 2027-02 이고
  **그때까지 검수자는 원장 본인**이다. 안 넣으면 오늘 이 통로를 쓸 수 있는 사람이 0명이다.
  (외부 검수자 게이트 = 동의 「제3자 열람」 조각 + NDA · L0 §4-5 ②-1 · ⏳유호님 판정.)

**봉투** — 학생 통로와 같다. `X-Contract-Ver` 필수.

```
요청 헤더: X-Contract-Ver: c13
응답 본문: { "contract_ver": "c13", "ok": true,  "data": … }
           { "contract_ver": "c13", "ok": false, "error": { "code", "message", "retryable", "field"? } }
```

**오류 코드**

| code | HTTP | 언제 |
|---|---|---|
| `CONTRACT_VER_MISSING` | 400 | `X-Contract-Ver` 없음 |
| `CONTRACT_VER_UNSUPPORTED` | 426 | 계약판 형식이 아님 |
| `AUTH_REQUIRED` | 401 | 토큰에 `sub` 없음 |
| `NOT_STAFF` | 403 | 직원이 아니거나 **폐기됨**(둘을 같은 코드로 묶는다 — 가르면 계정 존재 여부가 샌다) |
| `CONTRACT_VIOLATION` | 400·404·405 | 메서드·경로·인자 모양 |
| `NOT_FOUND` | 404 | 그 `submission_id` 가 **지금** 큐에 없다(폐기·철회·확정 포함) |
| `GATE_NOT_MET` | 409 | 승인 게이트 4조건 중 하나가 미충족(§5) |
| `SUPERSEDE_CONFLICT` | 409 | 재검수 대상이 **이미 다른 재검수에 대체됐다**(§5-1 · 계보가 갈리면 「최신 1행」이 둘이 된다) |
| `INTERNAL` | 500 | 그 밖 |

🔴 **읽기는 사건을 만들지 않는다**(C0 와 같은 축) — 단 **조회 감사는 유일한 예외**다.
그건 「읽었다」의 기록이라, 재시도로 한 행이 더 생겨도 그것이 사실이다.

## §2 불변식 — 조회 감사 (모든 경로가 진다)

**감사 종류 셋 — 「미리 받음」과 「열어 봄」을 가른다**(2026-08-09 개정 · 유호님 판정 ㉮)

| `action` | 언제 | 게이트 ②의 증거인가 |
|---|---|---|
| `review.queue` | 큐 응답 1회 = 1행 · `target_ids` = 그 응답이 실어 보낸 `submission_id` **전부** | ✗ |
| `review.audio` | 서명 **발급** 1회 = 1행(§4) · `target_ids={submission_id}` | 🔴 **아니다** |
| `review.audio.played` | 재생이 실제로 **시작**됐다(§4-2) · `target_ids={submission_id}` | ✅ **유일한 증거** |

🔴 **왜 갈랐나 — 안 가르면 게이트 ②가 두 자리에서 동시에 샌다.**

1. **프리로드가 게이트를 미리 연다.** 서명 발급이 곧 감사 1행이고 그 행이 게이트를 열면,
   다음 항목을 미리 당겨오는 것만으로 **열지도 않은 항목이 통과 상태가 된다**. §3 이
   「서버가 밀면 안 된다」고 적은 구멍이 클라이언트에서 그대로 열리는 자리다(화면이 순서로
   좁혀 마지막 하나까지 줄였지만 0은 아니었다).
2. **재검수의 청취 증거가 통째로 자백이 된다**(2026-08-09 실왕복 실측). 이 장부는
   **append-only 라 행이 영원히 산다** — 서명 기록이 **612초** 된 확정분에 새 서명을 안 받고
   재검수를 보내니 **200** 이 왔다. 같은 순간 §4 는 **404**(확정분엔 서명을 안 준다).
   즉 정직한 검수자는 다시 들을 수 없는데 `review_listened_ms:3000` 을 적어 보내면 통과했다.

🔑 **발급과 재생을 가르면 둘이 한 처방으로 닫힌다** — 프리로드는 발급만 하므로 **몇 개를
당겨도 게이트가 0개 열리고**, 재검수는 「마지막 판정 이후의 재생」을 요구할 수 있게 된다.

- 🚫 **감사가 실패하면 응답을 내주지 않는다**(같은 트랜잭션). 감사 없는 읽기가 성립하면 §4-5 ④ 의
  「읽는 지점이 하나」는 세는 것이 없는 문장이 된다.
- ⚠ 한계는 정직하게: `played` 는 **재생을 시작했다**를 재지 **들었다**를 재지 못한다(그 층은
  게이트 ①의 `review_listened_ms` 몫이고 그것도 클라이언트가 잰 값이다). 이 개정이 없앤 것은
  「한 번도 열지 않고 통과」이지 「대충 듣고 통과」가 아니다. 그 이상은 §0 감사 표본 몫.
- 🚫 **`played` 를 클라이언트가 여러 번 보내는 것을 막지 않는다** — 재생은 실제로 여러 번
  일어나고, 「몇 번째 재생인가」는 게이트가 묻는 것이 아니다(묻는 것은 **마지막이 언제인가**).

## §3 `GET /v1/review/queue` — 큐 읽기

**요청** `?limit=` (1~20 · 기본 10) · `?cursor=` (다음 쪽. 꼴 = 정렬키 짝, `corrections` 커서와 같은 계열)

**응답** `data[]` = `engine.review_queue` 그대로. 🔴 **원표를 읽지 않는다** — 판에 없는 열이 정말
필요하면 뷰와 `tests/검수큐.test.js` 를 같이 고친다(그 자리가 「검수자가 봐도 되나」의 판정 지점).

**정렬** `is_audit_sample desc, stt_confidence asc nulls last, occurred_at asc`
— 발주 §3 「감사 표본 우선 혼입 + 저신뢰 낮은 순」. 🔴 **뷰에 `order by` 를 넣지 않는다**(판은
무엇을 보여줄지만 정한다 · `20260809050000` 머리말). `nulls last` 인 이유: `stt_confidence` 가
null 인 행은 「신뢰도 0」이 아니라 **안 잰 것**이라 맨 앞으로 오면 안 된다.

**프리로드**(§3 UX) — 다음 항목 오디오는 **클라이언트가 §4 로 미리 받는다.** 서버가 밀지 않는다:
밀면 열지도 않은 항목에 서명이 생기고, 그 **서명 자체가 비공개 버킷의 열쇠**라 수명(10분)만큼
살아 있는 꼬리가 항목 수만큼 늘어난다.
✅ **게이트 누수는 §2 개정으로 닫혔다** — 발급(`review.audio`)은 더 이상 게이트 ②의 증거가
아니라서 **몇 개를 미리 당겨도 게이트가 0개 열린다**. 남은 이유는 서명 누수 하나뿐이라
「지금 항목을 통과한 뒤 다음 하나」라는 클라이언트 순서는 그대로 둔다(그 판정 = §6-4 ①).

## §3-2 반 모드 — 「오늘 수업 반」 (숙제서클 §10-3 · 2026-08-14 개정)

수업 첫 20분, 교사는 조 옆에 앉아 손으로는 **그 조 4명의 AI 초안**을 넘기고 귀로는 브리핑을
듣는다(`숙제서클_설계.md` §4). 그 자리의 큐는 기본 큐와 축이 다르다 — 감사 표본·저신뢰가 아니라
**교사의 동선(조 → 좌석)** 이 순서다. 경로는 안 늘리고 갈래 하나와 목록 하나를 연다.

### `GET /v1/review/queue?class=<uuid>` — 그 반의 큐

- **판이 다르다**: `engine.review_queue_class`(기본 22열 + `display_name`·`group_no`·`seat_no` ·
  `20260814100000`). 🔴 **정체 3열을 여는 판정**: 기본 큐가 이름을 안 주는 것은 그대로 두고
  (검수자 = 전사 축), 반 모드에만 연다 — 순회 검수는 교사가 학생 **눈앞에** 앉는 자리라 이름
  없이는 어느 초안이 그 학생 것인지 원리상 못 가른다(종이 서클 시트에 같은 이름이 이미 있다).
  `class_id` 는 응답에 안 되돌린다(요청이 들고 왔다) · `event_id` 는 여기서도 안 싣는다.
- **정렬** `group_no nulls last, seat_no nulls last, occurred_at asc, submission_id` — 편성 전
  학생은 맨 뒤로 가되 **빠지지 않는다**(그 학생 발화도 검수 대상이다). 커서는 반 모드 전용
  꼴 `g|<조>|<좌석>|<ISO 시각>|<uuid>`(`lib/검수커서.js` 반커서 계열)이고 기본 큐 커서와 섞어
  쓰면 400 이다.
  🔴 **머리의 `g|` 가 그 400 을 실제로 내는 물건이다** — 없던 동안 이 문장은 **실측 거짓**이었다
  (반박 P1-①): 칸 수·칸 모양이 같아 기본 커서 `1||<시각>|<uuid>`(신뢰 미측정)가 반 커서로
  읽히고(조=1·좌석=null → 1조의 좌석 있는 행 전부 건너뜀), 반 커서 `1|3|…` 이 기본 커서로
  읽혔다(신뢰='3' → 잰 행 전부 건너뜀). 400 이어야 할 자리에서 **200 + 조용히 빠진 목록**이
  나왔고, 큐는 줄어드는 목록이라 검수자에게는 증상이 없다. 기본 커서 꼴은 라이브에 나가
  있어 **안 건드린다** — 머리글자는 반 커서만 진다. 회귀 = `tests/검수커서.test.js`
  「두 모드의 커서는 서로를 통과하지 못한다」(만들기의 출력을 서로에게 먹인다 · 변이 1/1).
- **감사는 기본 큐와 같은 장부·같은 action**(`review.queue` · 실린 제출물들) — 조회 분모를
  모드가 가르지 않는다. `limit`·400 규칙·「읽기와 감사가 한 트랜잭션」 전부 §3 그대로.
- 반이 없는 학생(`class_id` null)은 **어느 반 큐에도 안 뜬다** — 그 발화는 기본 큐가 진다.
  반 모드는 기본 큐의 부분집합이지 대체가 아니다.

### `GET /v1/review/classes` — 반 카드 목록

- **응답** `{ classes: [{ class_id, class_key, display_name, waiting }] }` — `active` 반 전부.
  `waiting` = 그 반의 큐 행 수(목록을 그리는 순간의 스냅샷 — 반을 연 뒤의 수와 어긋나는 것이
  정상이다). 🔴 **빈 목록은 「전부 처리됨」이 아니라 「반 다리가 안 섰다」다** — 화면이 가른다.
- **감사** = `review.classes` 1행(대상 = 실린 반들). 큐 분모와 갈라 둔다 — 이 조회가 내주는
  것은 제출물이 아니라 반의 존재와 개수뿐이다.
- 문은 §1 그대로(inspector·director) — 반 모드는 검수자의 모드이지 강사 메뉴가 아니다
  (🚫 `review` 문에 `teacher` 넣기 — M2 §2 핀 그대로).

## §4 `POST /v1/review/audio` — 오디오 signed URL

**요청** `{ "submission_id": "<uuid>" }` · **응답** `{ "url", "expires_at" }`

- 수명 **10분** — `uploads` 와 같은 사유다(철회 뒤에도 수명만큼 살아 있는 「꼬리」).
- 🔴 발급 전에 그 행이 **지금** `engine.review_queue` 에 있는지 본다. 폐기·철회·확정분에 서명이
  나가면 뷰가 막아 둔 것이 이 문으로 도로 나간다. 없으면 `NOT_FOUND`.
- 비공개 버킷이라 **이것 없이는 재생 자체가 불가능하다** — 발주 v1 이 「3구멍」이라 적으며
  빠뜨렸던 자리다.
- 🔴 **발급은 승인 게이트 ②의 증거가 아니다**(§2 개정). 이 경로는 「열 수 있게 해 준 것」까지고
  「열었다」는 §4-2 가 진다. 🚫 이 소속 판정(큐 안)을 재검수 때문에 푸는 것 — 그러면 폐기·철회분
  서명이 이 문으로 도로 나간다(그 처방은 이 계약이 이미 기각했다).

## §4-2 `POST /v1/review/played` — 재생 시작 알림

**요청** `{ "submission_id": "<uuid>" }` · **응답** `{ "ok": true }`

- 🔑 **아무것도 발급하지 않는다.** 감사 1행(`review.audio.played`)만 남기고 끝난다 —
  서명이 안 나가므로 이 경로가 열려도 **서명 누수 위험이 0**이고, 그래서 §4 가 지키는
  「확정분에 서명을 안 준다」를 **한 글자도 안 건드리고** 재검수 창을 열 수 있다.
- **소속** = 큐 안 **또는** `pipeline_jobs.status='verified'`(재검수 창).
  `discarded`·`revoked` 는 거부(`NOT_FOUND`) — 폐기·철회분은 다시 들을 대상이 아니다.
- 함수는 여전히 **하나**고 경로가 다섯이다(§0 논리 그대로). 🚫 였던 것은 「함수 4개로 쪼개기」와
  「값목록을 내주려고 엔드포인트를 신설」이지 **새 능력을 경로로 여는 것**이 아니다.
- ⚠ 이 경로는 **클라이언트가 부른다** — 서버는 재생을 관측할 수 없다(서명 URL 은 Storage 가
  직접 내려주고 이 함수를 안 지난다). 그래서 이것은 **자백을 없애는 장치가 아니라 자백의
  단위를 「밀리초」에서 「열었다는 사실」로 바꾸는 장치**다. 값싼 우회를 없애는 것이 아니라,
  **아무 우회도 없이 통과하던 자리**(프리로드·옛 기록)를 없앤다.

## §5 `POST /v1/review/approve` · `POST /v1/review/discard`

> ✅ **c11 선행이 풀렸다** — 물리 칸 넷이 `20260809090000_engine_c10` 으로 섰다.
> 🔴 **채택된 이름이 이 문서의 옛 표와 둘 다르다**(그 조각 머리말이 세션 조율로 못박았다):
> `promote_intent` → **`promotion_intent`** · `transcript_verified_at_review` → **`transcript_at_review`**.
> `_verified_` 를 뺀 것이 판정이다 — 검수자가 판정하는 시점에 화면에 있는 것은 보통 **기계 전사**이고
> `transcript_verified` 는 그 판정의 **산출물**이라, 이름에 넣으면 행마다 거짓을 적게 된다.

### §5-1 `POST /v1/review/approve` — 확정 = 기록 둘

**요청**

| 필드 | 필수 | 물리 자리 |
|---|---|---|
| `submission_id` (uuid) | ✅ | — |
| `reviewed_correction_id` (uuid) | ✅ | `corrections.reviewed_correction_id` — 평가한 **AI 행** |
| `transcript_verified` (text) | ✅ | `submissions.transcript_verified` **+** teacher 행의 `transcript_at_review` |
| `corrected_text` (text) | ✅ | `corrections.corrected_text` |
| `review_listened_ms` (int ≥0) | ✅ | `corrections.review_listened_ms` |
| `promote` (bool · 기본 **false**) | | `corrections.promotion_intent` — `Shift+Enter` 의 ② |
| `error_tags` (text[]) | | `corrections.error_tags` — `1`·`2`·`3` 이 여기 모인다 |
| `explanation` · `l1_source_phrase` · `rubric_scores` · `reviewer_confidence` | | 같은 이름의 열 |
| `supersedes` (uuid) | | `corrections.supersedes` — 재검수(`Z`)일 때만 |

🔑 **`verdict` 는 요청에 없다 — 서버가 낸다.** 세 텍스트를 **순서대로** 본다(발주 §3):
① `corrected_text = transcript_verified` → `원문이 이미 맞다` ② `= AI corrected_text` → `AI 교정이 맞다`
③ 나머지 → `고칠 곳이 있다`. 순서를 바꾸면 두 오답이 각각 조용히 성립한다(그 사유는
`lib/검수확정.js` 머리말). 비교는 `trim`+**NFC** 까지만 정규화한다 — NFD 로 온 한글을 안 접으면
아무것도 안 고친 확정이 `고칠 곳이 있다` 로 적히고, 더 접으면 라벨이 사람이 본 화면과 갈린다.

**응답** `{ correction_id, verdict, promotion_intent, listen_gate: { required_ms, measured } }`

🔴 **`listen_gate.measured` 를 응답에 싣는 이유**: 오늘 그 값은 **항상 `false`** 다 —
`submissions.stt_segments` 에 **쓰는 코드가 저장소에 0줄**이라(2026-08-09 실측) 게이트 ①의
문턱이 언제나 하한 3초로 접힌다. 그것을 「게이트가 섰다」로 읽지 않기 위해 미측정을 **응답에
드러낸다**. 지금 막는 것은 0초 승인·기계적 난사뿐이고, 구간 단위 청취(UX ②)의 실효는
`stt_segments` 생산자가 서는 날 함께 온다. 그 날 첫 실측 대상 둘 = 저신뢰 경계값(`0.7`)과
세그먼트 시간 단위(초 vs ms — 지금은 `start_ms` 가 있으면 ms, 없으면 초로 **둘 다** 받는다).

**한 트랜잭션에 넷** — 원자성이 이 계약의 절반이다:
① teacher `corrections` 행 insert(`actor_kind='teacher'` · `reviewer`=승인자 `staff_id`)
② `submissions.transcript_verified` 갱신 ③ `pipeline_jobs.status='verified'` ④ 감사 1행(`review.approve`).
③을 빠뜨리면 확정분이 **큐에 남고**(판이 빼는 「끝난 셋」 중 하나가 그것이다 · `20260809055000`),
승격 의사를 뒤로 미루면 그 사이 실패에 **사람이 누른 의사가 증발**한다(그 항목은 이미 큐 밖이라
다시 물을 방법이 없다). 🔴 「끝난 셋」으로 **소속을 정하지는 않는다** — 초판이 `='ai_processed'` 로
좁혔다가 되돌렸다(그 칸의 생산자가 없어 큐가 0행이 됐다 · L0 §3 「어긋나면 `corrections` 가 맞다」).

**동시성** — `pipeline_jobs` 행을 **먼저 잠근다**(뷰에는 `for update` 를 못 건다). 같은 항목의
동시 승인·폐기가 직렬화되고, 두 번째 요청은 상태를 다시 읽어 「이미 끝난 항목」으로 떨어진다.
그래서 **중복 teacher 행이 원리상 안 생긴다** — 재전송 멱등을 위한 별도 키가 필요 없다.

**멱등키는 원본 `event_id` 하나다**(승격 사슬 몫). 🚫 `(event_id, 목적)` 은 같은 원본을 train
**과** eval 에 각각 넣는 것을 오히려 허용해 평가 점수를 훈련 누출로 오염시킨다.

**승인 게이트 4조건**(서버가 매 승인에서 재검증 — UI 만 막으면 직접 호출로 0초 승인이 선다):

① `review_listened_ms ≥` 저신뢰 구간 길이 합(0이거나 잰 적 없으면 하한 3초 · ⚠ 「발화 전체」가
아니다 — UX ②가 「거기만 듣게」 만드는데 전체 청취를 요구하면 두 규칙이 서로를 무효화한다)
② 그 항목을 **요청자 본인이 재생한 기록**(`review.audio.played` · §4-2)이 실재. 서버는
`마지막청취 = max(at)` 를 읽고 **갈래로 판정**한다:
  - **첫 확정** — `마지막청취 != null`. **시간 무관**이다(듣고 오래 고민하는 것이 정상이고,
    조이면 그 처방이 「다시 열어라」인데 그건 성실한 검수자만 막는다).
  - **재검수(`Z`)** — `마지막청취 > supersedes 행의 created_at`. 즉 **마지막 판정 이후에
    한 번 더 열었어야** 한다. 옛 기록으로는 못 지난다(그것이 이 개정 전의 구멍이다).
  🔑 **요청자 본인의 기록**이어야 한다 — 남이 연 기록을 받으면 이 게이트는 「누군가 들었다」만
  보증하고, 검수자가 여럿이 되는 2027-02 에 새는 방향이 「통과」다.
  🚫 게이트에 **시간 리터럴을 박지 않는다**(「10분 안」 같은 상수). 아래 🔑 대로 그 창은
  상수 없이 성립하고, 박으면 첫 확정까지 같이 조인다. ③ 요청자가 활성 직원(§1 사슬)
④ `reviewed_correction_id` 가 **그 제출물의** AI 행 — 트리거는 「다른 제출물」만 막고 `teacher`
행을 평가 대상으로 가리키는 것은 물리가 안 막는다(그러면 사람이 사람을 평가한 라벨이 된다).

**재검수(`Z`)** — `supersedes` 를 실으면 갈래가 바뀐다. 첫 확정은 **큐 안**이어야 하고, 재검수는
확정으로 큐에서 나간 항목이라 **큐 밖 + `status='verified'`** 여야 한다(폐기·철회분은 어느 쪽으로도
안 받는다). `supersedes` 는 그 제출물의 teacher 행이어야 하고, **이미 다른 행이 그것을 대신했으면
거부**한다(`SUPERSEDE_CONFLICT`) — 사슬이 갈라지면 「원본당 최신 미폐기 행 하나」가 둘이 되고,
소비자 쿼리가 그 순간 어느 라벨이 정본인지 못 고른다. c11 의 CHECK 는 자기 참조만 막는다.
▶ **c11 권고**: `unique (supersedes) where supersedes is not null` 로 물리에 못박으면 이 검사가
잉여가 된다 — 그때까지는 서버의 이 한 줄이 유일한 방어선이다.

🔑 **재검수 창 = 「손에 쥔 URL 이 살아 있는 동안」이고, 그것이 시간 상수 없이 성립한다.**
확정분에는 §4 가 새 서명을 안 준다(`NOT_FOUND`) → 다시 들으려면 **아직 살아 있는 옛 URL**
뿐이다 → 그 URL 이 죽으면 새 `played` 행을 만들 길이 없고 → 게이트 ②의 재검수 조건
(`마지막청취 > supersedes.created_at`)이 **더 이상 충족될 수 없어 재검수가 자연히 닫힌다.**
즉 「10분」은 서버가 세는 상수가 아니라 **서명 수명이 물리적으로 만드는 창**이다.
🚫 그 자리를 §4 의 소속 판정을 푸는 것으로 메우지 않는다(폐기·철회분 서명이 도로 나간다) ·
🚫 게이트에 시간 상수 박기 · 🚫 문구만 고치고 게이트는 그대로 둔 채 「닫혔다」로 적기 —
2026-08-09 이전의 이 문단이 정확히 그 상태였다(서버가 지키지 않는 약속을 적어 두어, 읽는
사람이 게이트가 **있다고 믿었다**).

### §5-2 `POST /v1/review/discard` — 소프트 폐기

**요청** `{ "submission_id": "<uuid>", "reason": "<닫힌 어휘>" }` · **응답** `{ discarded: true, reason }`

- `pipeline_jobs.status='discarded'` + `discard_reason` + 감사 1행(`review.discard`). **파일은 남긴다**
  (노이즈도 강건성 학습 재료). ⚠ **철회는 다른 사건**이고 파일을 지운다(L0 §9-3) — 이 경로가 아니다.
- 폐기 사유(`discard_reason`) 닫힌 어휘 6: 무음 · 손상 · 중복 · 과제 불일치 · 타인 음성 · 판정 불가.
  🔴 **정본은 DB CHECK 하나**(`pipeline_jobs_discard_reason_c*` — 접미는 현행 계약판·c13 이 다시 이름째 갈았다)이고 **코드는 그 목록을 안 든다** —
  서버가 `pg_get_constraintdef` 로 읽어 대조한다(이름은 접두로 찾는다 · 판이 `_c11` 로 갈리는 날
  박아 둔 이름이면 **전 폐기가 조용히 500** 이 된다). 위 산문 사본 둘은 검수자가 읽는 자리라
  남기고 `tests/폐기사유.test.js` 가 CHECK 와 대조한다 — 없앨 수 없는 사본은 기계에 물린다.
  ⚠ 조각이 안 부어진 DB 에서는 어휘가 0개라 **폐기가 전부 거부된다**(`INTERNAL`). 사유 없는
  폐기를 남기는 것보다 안전한 방향이다.
- 청취 게이트는 **안 건다** — 무음·손상은 첫 초에 판정되고, 게이트를 걸면 그 처방이 「쓰레기를
  끝까지 들어라」가 된다. 감사 행은 그대로 남는다.

### §5-3 아직 이 계약 밖

| 자리 | 왜 밖인가 |
|---|---|
| 승격 사슬(비식별 → 산출물 → `data_use.granted`) | 이 함수는 **의사만** 원자적으로 남긴다. 뒤는 그 값을 읽어 도는 비동기 사슬(발주 §3) — 검수 루프를 막지 않는다 |
| `dataset_item(group_id)` | 승격 상호배타는 원본이 아니라 **묶음** 단위. 새 표라 ㉮ 가 미룬 C 계층 그 자체다 |
| `error_tags` 어휘 검증 | 정본 = `계약/수집_교정_계약.json` 의 `오류태그`. **AI 행도 같은 수준**(trim·빈 값 제거)으로 쓰므로(`lib/교정엔진.js`) 한쪽만 조이면 사람 라벨이 AI 라벨보다 좁아진다 |
| `verdict_reason` | 사람이 적는 칸이라 요청에 안 넣었다. 자동 판정의 근거를 여기 적으면 「사람이 쓴 사유」와 기계 문자열이 한 칸에서 섞인다 |

   「이 구간만 들으면 된다」고 칠한 자리와 서버 문턱이 갈리고, 증상은 **승인이 안 되는데 이유를
   화면이 못 말하는 것**이다.
   ④**재검수(`Z`)는 항목이 아니라 「방금 보낸 값」에서 잇는다.** 손에 든 항목은 큐를 읽던 시점의
