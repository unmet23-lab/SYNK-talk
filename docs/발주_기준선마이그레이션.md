## 0. 한 줄

**빈 개발용 Supabase 프로젝트에 `engine` 스키마를 처음 세우고, 그 절차를 다시 돌릴 수 있는 형태로 repo에 남긴다.**

지금 `supabase/L0_스키마.sql`은 **한 번 붙여넣으면 서는 파일**이지 마이그레이션이 아니다. 두 번째 변경부터는
`create table if not exists`가 통째로 건너뛰어서 **아무 일도 안 일어나는데 초록으로 보인다.** 그 성질을 파일 스스로
경고하고 있으나(헤더 ⚠), 경고는 아무것도 막지 못한다.

### 0-1. 적용 대상 — ✅ 유호님 답 수신 (2026-08-06)

**Supabase 프로젝트는 「synk talk」 하나뿐이다**(2026-08-05 생성). 유호님 답: *"빈 개발용 프로젝트에 세우는 게
더 시스템 구축에 좋다면 빈 개발용 프로젝트에 만들어줘."*

**판정 — 개발용과 운영용은 나눈다. 단 지금 새로 만들지 않는다.**

- ✅ **지금의 「synk talk」을 개발용으로 쓴다.** 이미 있고 비어 있을 가능성이 높아 **유호님 손이 0회 더 든다.**
- ✅ **운영용은 개원 전에 새로 만든다** — 그때 **개발 흔적 0인 상태로 태어난다.** 별도 발주다(§5).
- 🔴 나누는 이유: **개발용 DB는 지우고 다시 세우는 것이 정상 동작이다.** 실학생 데이터가 같은 DB에 있으면 그걸
  할 수 없어 **개발이 실학생을 인질로 잡는다.** 분업 §5는 이 분리를 **「없으면 나중에 소급 불가」**로 규정한다.
  실학생 0명인 **지금이 공짜인 유일한 시점**이다(개원 2027-02).
- 반대 방향(지금 것을 운영으로 아껴 두고 개발을 새로 만들기)은 손이 1회 더 들고, 운영 프로젝트가 개원까지 몇 달
  방치돼 무료 등급 일시정지에 걸린다 — 이득이 없다.

**남은 전제 1개 — 「비어 있는가」는 아직 안 쟀다.** `supabase/확인_적용전상태.sql`(읽기 전용 · 회귀로 못박음)을
유호님이 1회 Run 해 판정 칸을 회신하면 §3-3의 「실행 전 상태」 첫 칸이 채워진다. 🔴 **그 전에는 붓지 않는다** —
비어 있지 않은 DB에 부으면 `create table if not exists`가 통째로 건너뛰어 **초록인데 아무 일도 안 일어난다.**

## 1. 왜 지금인가 — 되돌릴 수 있는 마지막 지점

- 실학생 **0명**이다. 빈 DB에 잘못 세우면 지우고 다시 세우면 된다. 개원(2027-02) 뒤엔 그 선택지가 사라진다.
- 계약은 **c5에서 동결**됐다(2026-08-06 · `계약/수집_교정_계약.json` — 수집 파이프라인 흡수분까지 포함).
  기준선이 **처음부터 c5로 태어나면 `alter table` 이행 자체가 안 생긴다.** 낮은 판으로 세운 뒤 올리는 것보다
  싸고, 「조용한 미적용」 위험이 0이다.
  🔴 **버전을 이 문서에 손으로 적지 않는다** — 정본은 계약 파일의 `버전` 필드이고, 위 문장은 그것을 가리킬 뿐이다.
  어긋나면 아래 회귀가 빨개진다(`tests/L0스키마.test.js`).
- S1(첫 앱 화면)의 남은 전제가 이것 하나다.

## 3. 산출물

### 3-1. 커밋된 마이그레이션 (필수)

`supabase/L0_스키마.sql` 하나로는 두 번째 변경을 못 싣는다. **적용 순서가 파일에 드러나고 재실행이 안전한 형태**로
정리한다. 구체적 배치(디렉터리·파일명 규칙·Supabase CLI 채택 여부)는 **Codex가 정한다** — 아래 제약만 지킨다.

- **① 순서가 이름에 있다.** 나중에 온 사람이 실행 순서를 추측하지 않는다.
- **② 재실행이 안전하다.** 두 번 돌려도 에러가 안 나고 데이터를 안 지운다. ⚠ 단 **「안전」과 「반영」은 다르다** —
  재실행으로 반영되지 않는 변경(제약 이름·CHECK 값)은 별도 문장으로 적는다.
- **③ 유호님 실행 경로는 「SQL Editor에 붙여넣고 Run」을 유지한다.** 🔴 **유호님께 CLI·Docker·터미널 설치를
  요구하는 안은 반려 사유다** — 비개발자이고, 도구가 하나 늘면 그날 막힌다. CLI를 쓰려면 **AI 쪽에서만** 쓴다.
- **④ 기준선은 계약 파일이 선언한 현행 버전이다.** 제약 이름은 **그 버전을 접미사로 달고 있는 것 전부**이며,
  개수·이름 모두 `supabase/L0_스키마.sql`이 정본이다(지금 4개 — c5에서 `submissions_task_format_*`이 늘었다).
  값목록도 계약 파일에서 파생시킨다. 🔴 **여기에 이름을 나열하지 않는다** — 나열하는 순간 다음 개정 때 낡는다.

**⑤⑥⑦⑧은 적용 주체 A 확정(§6)에서 나온다** — 「사람이 손으로 실행한다」의 귀결이라 A인 한 협상 대상이 아니다.

- **⑤ 유호님이 붙여넣는 「마이그레이션 본체」는 1개다.** ①에 따라 파일을 쪼개는 것은 좋으나, 그 경우 **순서대로
  이어붙인 합본 1개**를 함께 산출한다. 🔴 **파일 개수·실행 순서를 사람이 기억하게 하는 안은 반려 사유다**
  (L0 §8 클릭 절차 4번이 「전문을 복사해 붙여넣기」 1회를 전제한다).
  - **합본을 손으로 쓰지 않는다** — 조각에서 기계로 생성하고 `합본 == 조각들을 이은 것`을 검사하는 회귀 1건을
    함께 낸다(변이 1건으로 빨개짐 실증). **회귀가 읽는 파일과 유호님이 붙여넣는 파일이 같은 바이트임**을 그
    테스트가 진다. 안 묶으면 조각만 고치고 합본을 잊었을 때 **CI는 초록인데 유호님은 낡은 것을 붙여넣는다.**
  - ⚠ **확인 쿼리를 합본 안에 넣지 않는다** — 초판의 「마지막 문장으로 넣는 쪽을 검토」는 **2R 판정으로 철회**한다.
    `commit` 뒤에 두면 **그 쿼리가 실패해도 적용은 이미 끝나 있어** ⑦의 「전부 아니면 0」이 깨진다.
    합본은 `commit`으로 끝내고 확인은 별도 Run이다 — 붙여넣기는 **본체 1 + 확인 1**로 굳는다.
  - ⑤는 **본체**에만 걸린다. **실행 전 상태 조회·확인 쿼리는 예외**다(§3-3이 요구하므로 0회로 만들 수 없다).
- **⑥ 경로를 바꾸면 그것을 가리키는 자리를 전부 함께 고친다.** L0 §8 클릭 절차 4·6번 · `tests/L0스키마.test.js`가
  읽는 경로 · L0·C0의 「DDL 실물」 링크. 배치만 바꾸고 절차를 두면 **조용히 틀린 파일을 가리킨 채 초록으로 보인다.**
  **구 `supabase/L0_스키마.sql`은 삭제하거나 합본이 그 자리를 그대로 차지한다 — 두 벌 존치 금지**(조각·합본·구파일
  3중 정본이 된다). 완료 판정 = `grep -rn 'L0_스키마.sql'`이 0건이거나 전부 새 경로.
- **⑦ 실패 상태는 「전부 아니면 0」이고, 어느 쪽인지는 사람이 판단하지 않는다.** 합본은 **단일 트랜잭션**으로
  실행된다(`begin; … commit;`) — 그래야 반쪽 상태가 안 생긴다. 「오류 문구로 진행도를 역산하라」는 요구는
  구현 불가능하다(Postgres 오류는 **직전 실패 문장만** 말한다).
  🔴 **단 「빨간 화면 = 0 적용」이라고 단정하면 틀린다**(2R 지적 · 초판의 오류). `commit`을 보낸 뒤 응답이
  유실되거나 타임아웃되면 **서버는 커밋했는데 화면은 오류**다. **화면은 결과의 증거가 아니다.**
  → **그래서 유호님의 행동을 화면과 무관하게 하나로 통일한다: 아무것도 다시 Run하지 말고 「확인 쿼리 1회」.**
  갈래를 사람이 고르게 하지 않는다 — 고르게 하는 순간 위 오판이 유호님 몫이 된다.
  - **⑦-a 빨간 오류** · **⑦-b 초록인데 판정 ❌**(🔴 **A에서 가장 흔하다** — 부분 복사·이미 선 DB·두 번째 Run은
    **전부 오류를 안 만든다**) · **⑦-c 결과를 못 봤다**(브라우저 닫힘·타임아웃·빈 편집창) — **셋 다 첫 조치는 같다.**
  - **산출물 = 확인 쿼리 「결과별 후속 판정표」.** 현재 버전 있음 / 없음 / 부분 상태 / 버전 불일치 각각에 대해
    **「다시 부어도 되는가 · 무엇을 보내야 하는가」**를 표로 낸다. 🔴 **재실행 허용 조건이 그 표에 없으면 미완이다.**
  - 이 통일 규칙과 판정표를 **L0 §8 절차 끝에 적는 것까지가 산출물이다.**
  - 파생: 합본에 트랜잭션 블록에서 못 도는 문장(`create index concurrently` 등)을 넣지 않는다.
- **⑧ 적용 이력은 DB 안에 산다.** 각 마이그레이션이 자기 버전을 DB에 기록하고(예: `engine.schema_migrations`)
  **이미 적용된 버전이면 자기 자신을 건너뛴다.** 확인 쿼리 `판정` 칸에 **현재 적용 버전**을 함께 낸다.
  🔴 **이게 없으면 ①·③·⑤와 A가 실제로 양립 불가다** — CLI를 못 쓰니 `supabase migration` 원장이 없고, 문서에 손으로
  적는 버전은 이 저장소가 반복해 데인 형태다. 그러면 c5 개정 때 드릴 것이 「전체 합본 재생성」(→`if not exists`가
  건너뛰어 **조용한 미적용** · §0이 죽이려던 바로 그것)이거나 「새 파일 1개만」(→사람이 기억해야 하므로 ⑤ 위반)
  둘뿐이다. **§0·§1이 내건 목적이 정확히 여기서 산다.**
  - **⑦과의 양립 형태**(2R 제시): 한 파일 안에서 `begin` → 이력 테이블 확보 → 버전 존재 검사 → **미적용일 때만**
    본체 → 버전 기록 → `commit`. ⚠ SQL Editor용 파일이므로 `psql \if` 같은 **클라이언트 지시자는 쓸 수 없다.**
  - 🔴 **부트스트랩 규칙을 정한다** — **낮은 판(c3·c4)이 이미 선 DB에는 이력 행이 없다.** 그래서 「버전 없음」이
    **빈 DB인지 기존 판인지** 가릴 규칙이 필요하다(예: `engine` 스키마 존재 여부로 가른다). 안 정하면 **기존 DB를
    빈 DB로 오인해** 본체를 부었다가 `if not exists`에 전부 막히고, 이력에는 「적용됨」만 남는다 — 가장 나쁜 조합이다.
  - 🔴 **확인 쿼리 기대값을 다시 정의한다** — 이력 테이블이 생기면 기준선 파일의 꼬리 확인이 세는 **테이블 수가
    깨진다.** 본체와 이력을 나눠 세거나 기대값을 함께 올린다. **안 고치면 정상 적용이 ❌로 나온다**(§2-1과 같은
    형태의 사고다). 🔴 **고친 값은 기준선 파일에만 적는다** — 이 문서에 숫자를 복사하면 그게 다음 사고다.

### 3-2. 검증 5종 — **실행 층**에서 (필수)

지금 회귀 8건은 전부 **SQL 텍스트를 읽는** 검사다. 파일이 문법적으로 맞는지도, 진짜 DB에 서는지도 모른다.
아래는 실제로 돌려서 확인한다. **운영 후보 프로젝트에서는 하지 않는다.**
⚠ 어디서 돌릴지는 열려 있지 않다 — **아래 「실행 층이 지금 없다」를 먼저 읽어라.**

| # | 항목 | 통과 기준 |
|---|---|---|
| ① | **빈 DB 적용** | 아무것도 없는 DB에서 끝까지 완주 · 확인 쿼리 `판정` 칸 = `✅ 전부 통과` |
| ② | **재실행** | 같은 것을 다시 돌려 에러 0 · 데이터·구조 변화 0 |
| ③ | **중간 실패** | 임의 지점에서 끊었을 때 **반쪽 상태가 남는지** 확인하고, 남으면 그 사실을 문서화(트랜잭션 경계) |
| ④ | **롤백** | 세운 것을 되돌리는 경로가 실재하는지 — 실행해서 확인. 없으면 그것도 결론이다(「전진 수정만 가능」) |
| ⑤ | **RLS** | 학생 토큰으로 **남의 행이 안 보이고**, 학생이 **쓰기를 못 하며**, `anon`·`authenticated`에 `engine` 권한 0 |
| ⑥ | **기존 스키마** | 낮은 판(c3·c4)이 이미 선 DB를 재현해 헤더 ⚠·문서 §9-4의 `alter` 경로로 현행 버전까지 올린다 · 확인 ④가 **현행 버전 접미사만** 낸다(옛 접미사가 하나라도 남으면 미적용) |

⑤는 문서가 이미 정한 계약이다(L0 §4-3 · C0 §1). **정책 파일을 읽어 통과라고 하지 말고 실제 토큰으로 조회한다** —
정책은 있는데 안 먹는 형태가 이 저장소가 여러 번 데인 자리다.

⑥은 분업 §8-4가 요구하는 「기존 데이터」 자리다. **「빈 프로젝트」는 전제일 뿐 확인된 적이 없다** — `C0 §9`와
`supabase/L0_스키마.sql` 헤더 ⚠가 둘 다 「이미 c3가 선 DB」를 살아 있는 가능성으로 다룬다. 유호님이 예전에
c3 판을 한 번 Run했다면 합본을 붙여넣어도 **전부 건너뛰고 초록 Success**가 나고 확인 쿼리만 ❌를 낸다.
그 상태에서의 복구 경로(`alter` 3쌍)를 **아무도 실행해 본 적이 없다.**

#### ⚠ 실행 층이 지금 없다 — 발주 시점 실측 (2026-08-06 · 이 발주의 최대 차단자)

유호님 PC에 **`docker`·`psql`·`pg_ctl`·`supabase` CLI가 전부 없다**(4종 모두 `MISSING` 실측). 그리고 A 확정(§6)이라
AI는 Supabase 자격증명을 갖지 않으므로 **「임시 프로젝트」 경로도 AI 단독으로는 막힌다.** 즉 위 5종을 돌릴 자리가
**현재 존재하지 않는다.** 착수하면 바로 여기서 멈춘다 — **먼저 고르고, 고른 뒤에 움직인다.**

✅ **Codex 1라운드 회신 = (라) 선택** (2026-08-06) — **CI에서 Supabase 로컬 스택을 띄운다.** 순수 postgres가
아니라 Auth 역할·`auth.uid()`·JWT를 포함한 스택이라 아래 (라) 함정이 대부분 닫힌다. 남는 잔여 위험은
**적용 후 실프로젝트에서 ⑤(RLS)만 유호님이 1회 재확인**해 닫는다. 유호님 PC 무변경 · 자격증명 0 · 검증이 회귀로 남는다.
아래 (가)~(다)는 **기각이 아니라 안 고른 것**이므로 근거를 남겨 둔다(선택이 뒤집힐 때 다시 읽는다).

- **(가) 로컬에 Postgres를 세운다** — AI 쪽 도구이므로 §3-1 ③ 위반이 아니다. 🔴 **단 유호님 PC에 무언가를 설치하는
  것은 유호님 승인 사항이다** — 무엇을·용량·되돌리는 법을 적어 클로드를 거쳐 올린다. 임의 설치는 그 자체가 결함.
- **(나) 유호님이 개발용 프로젝트에서 검증까지 실행** — 자격증명이 0으로 유지되는 대신 왕복이 늘고, 붙여넣기가
  5종만큼 반복돼 **§3-1 ⑤와 정면으로 부딪힌다.** 채택하려면 ⑤를 어떻게 지키는지 같이 낸다.
- **(다) 검증 층을 줄인다** — 🔴 **클로드 판정 사항이다.** 의미 층 경계(§5)라 Codex가 단독으로 줄이지 않는다.
- **(라) 넷째 길** — 예: **CI 러너의 Postgres 서비스에서 돌린다.** 유호님 PC를 안 건드리고 자격증명도 안 쓰며,
  검증이 **회귀로 남는다**(§4-2가 요구하는 것과 같은 자리). `.github/workflows/ci.yml`의 `verify` 잡은
  `ubuntu-latest`에서 돌아 서비스 컨테이너를 붙일 자리가 있다(클로드 실측) — **읽어서 직접 확인해라.**
  ⚠ **함정**: Supabase의 RLS는 `auth.uid()`와 `anon`·`authenticated` 역할에 기대는데 **순수 postgres 컨테이너엔
  그게 없다.** 스텁을 만들어 넣으면 ⑤가 돌긴 하나 「진짜 Supabase에서도 같은가」가 미검증으로 남는다 —
  (라)를 고르면 **그 잔여 위험을 무엇으로 덮는지 함께** 낸다(예: 적용 후 실프로젝트에서 ⑤만 유호님이 1회 재확인).

⚠ **함정 2 — ③(중간 실패)의 답은 SQL 텍스트가 아니라 「어떻게 먹였나」가 정한다.** `psql -f`는 문장별
autocommit이라 **앞 문장이 커밋된 채 남고**, 한 덩어리로 보내면 Postgres가 암묵 트랜잭션 1개로 묶어 **전부
롤백된다** — 같은 파일로 정반대 결과가 나온다. 어느 층에서 재든 **유호님이 실제로 밟는 형태**(편집창에 통째로
붙여넣고 Run)와 같게 먹였음을 함께 증명한다. 증명이 없으면 ③도, 그 위에 얹힌 ⑦도 미검증이다.
(§3-1 ⑦의 `begin;/commit;`을 명시하면 이 층 의존성 자체가 사라진다 — 그쪽이 싸다.)

⚠ **함정 3 — SQL Editor가 무엇을 어떻게 보내는지 우리는 모른다.** 공식 문서로 확인되는 것은 **1분 타임아웃**
하나뿐이고, 「편집창 전체를 보내는가 선택 영역만 보내는가」·「다중 문장에서 어느 결과셋을 보여주는가」는
**미확인**이다. ⑦이 「화면과 무관하게 확인 쿼리 1회」로 통일한 이유가 이것이다 — **모르는 층 위에 사람의 판단을
얹지 않는다.** 실측 항목: 빈 입력·부분 선택 실행 · 다중 문장 전체 전송 여부 · 마지막 결과셋 표시 ·
`commit` 뒤 지연으로 타임아웃을 만든 뒤 이력 확인 · 실행 직후 네트워크 차단 후 재확인.

넷 중 아무것도 못 고르면 **그것이 반려다**(§7 ④) — 그때 유호님께 올라간다.

### 3-3. 기록 6종 (L0 §8 — 하나라도 빠지면 미완)

적용 커밋·마이그레이션 버전 / Supabase 프로젝트와 **개발·운영 구분**(§0-1 판정) /
**실행 전 상태**(`supabase/확인_적용전상태.sql`의 판정 칸 — 붓기 전에 받는다) / 실행 결과 /
적용 후 테이블·제약·RLS 검증 결과 / 실패 시 롤백·전진 수정 경로.

🔴 「Supabase 프로젝트」 칸은 **기억으로 적지 않는다** — 유호님이 Run한 화면 **주소창의 `project/` 뒤 문자열**을
그대로 복사해 붙인다. AI가 못 보는 층이라 이것이 유일한 물증이고, `current_database()`는 전 프로젝트가
`postgres`라 SQL 안에서는 구별되지 않는다.

**기계 가드가 싸다** — 합본 머리에 「이미 학습 데이터가 있으면 트랜잭션째 멈추는」 한 덩어리를 넣는 것을 검토한다.
빈 개발 DB에서는 무해하고, 잘못된 프로젝트에 붙여넣으면 거기서 선다. 넣을지는 Codex가 정한다.

## 4. 완료 기준 — 테스트로 판정한다

1. 확인 쿼리 `판정` 칸이 **`✅ 전부 통과`** — ⚠ 기대값은 ⑧(이력 테이블)을 반영해 **재정의한 것**을 쓴다.
   이력 테이블을 안 세는 옛 기대값을 그대로 쓰면 **정상 적용이 ❌로 나온다.**
2. `tests/L0스키마.test.js` 초록 + **실행 층 검증 5+1종을 회귀로 남긴 것** 초록.
3. 계약(현행 버전)과 DDL 값목록이 **파생 관계**로 묶여 있다 — 계약을 고치면 테스트가 빨개진다.
4. **⑧이 실제로 동작한다** — 같은 합본을 두 번 돌려 두 번째가 **자기를 건너뛰고**, 확인 쿼리가 **현재 적용 버전**을
   낸다. §3-2 ②(재실행)와 **같은 실행에서** 잰다(따로 재면 두 번째 실행이 다른 조건이 된다).
5. **⑦의 「결과별 후속 판정표」**가 L0 §8 절차에 실려 있다 — **재실행 허용 조건 포함.**
6. 원격 CI 초록(로컬 초록은 CI 초록이 아니다).

## 5. 경계 — 이 발주에서 하지 않는 것

- **운영 프로젝트 적용** — 개발용 하나만. 운영은 별도 발주.
- **Edge Function 실물**(payload Zod 검증 · L0 §7-6) · **로그인 코드 발급 도구** — 기준선이 선 뒤.
- **`Settings → API → Exposed schemas` 변경** — `engine`은 노출하지 않는다(L0 §4-3).
- **계약 값·필드 뜻 변경** — 의미 층은 클로드 펜이다. 문제가 보이면 고치지 말고 반려.
- **DB 비밀번호·`service_role` 키를 대화·repo·로그에 남기기** — 어떤 형태로도.

## 6. 적용 주체 — ✅ 유호님 확정 **A** (2026-08-06)

**A. 유호님이 실행한다.** Supabase SQL Editor에 붙여넣고 `Run`, 확인 쿼리 `판정` 칸만 확인한다.
**이 발주 범위에서 AI는 Supabase 자격증명을 갖지 않는다.** 이 확정이 §3-1 ⑤⑥⑦⑧을 만든다.
(범위 한정이다 — 분업·`docs/배포_경로.md`가 정한 「유호님 승인이 붙는 AI 실행 경로」를 소급 무효화하지 않는다.)

**B(AI 원격 실행)는 기각이 아니라 보류**다 — 유호님 2026-08-06 「원격 관련은 차차」.
재판단 때 **셋을 같이 본다**: **비용** = 개발 전용 자격증명 분리가 그 자체로 발주 1건 · **이득** = 유호님 손이
승인 1회로 줄고 **§3-2 검증 층 문제가 통째로 사라진다** · **리스크 상한** = 운영과 분리된 개발 전용 자격증명이라
**유출돼도 개발 DB만 영향**. (이득·상한을 지워두면 다음 세션이 비용 한 줄만 읽고 「차차」를 「안 함」으로 굳힌다.)
🔴 **이 발주 안에서 B를 전제한 설계·배선을 미리 하지 않는다** — 안 쓸지도 모르는 자동화 경로가 남으면
「어느 쪽으로 적용됐는지」가 흐려진다.

🔑 **유호님 확인(2026-08-06): 「슈파베이스 구축 과정은 니가 해주면 될 것 같아」** — A 안에서 **설계·SQL·검증·
절차는 전부 AI 몫**이고 유호님은 **붙여넣기와 판정 회신만** 한다는 뜻으로 읽는다(B로의 전환이 아니다 — 같은 날
「원격 관련은 차차」와 함께 온 말이다). 그래서 **유호님 손 횟수를 줄이는 것 자체가 이 발주의 품질 기준**이고,
§3-1 ⑤가 그 기준의 기계적 형태다.
⛔ **A·B와 무관하게 AI가 못 하는 것 둘**: ①Supabase 로그인(자격증명) ②DB 비밀번호 취급. 절차로 우회하지 않는다 —
프로젝트 생성·비밀번호 설정이 필요한 순간은 **언제나 유호님 손**이다.

유호님 손이 드는 지점은 **최소 3회**다: ①실행 전 상태 조회 ②마이그레이션 Run ③확인 쿼리 Run.
여기에 이 발주를 Codex에 넘기는 1회, §3-2 갈래에 따라 추가가 붙는다. **정확한 횟수는 산출물이 확정되면
L0 §8 절차에 실수로 적는다** — 확정 전에 숫자를 박지 않는다(「클릭 1회」 프레임이 폐기된 것과 같은 이유다).

## 7. 반려 사유 (Codex → 클로드)

발주 검수 4문(분업 §4)에 하나라도 걸리면 구현 전에 반려한다:
①입출력이 구체적인가 ②빈 값·중복·네트워크 실패가 정의됐는가 ③완료 기준을 테스트로 판정할 수 있는가
④**구현 불가능하거나 모순된 요구가 없는가**(§3-1 ③ 「유호님께 CLI를 요구하지 않는다」와 ⑤ 「붙여넣기 1개」가
여기 걸린다면 그것도 반려다 — 대안을 제시하고 클로드가 판정한다. 단 **적용 주체 A 자체는 유호님 확정이라
반려 대상이 아니다** — 바꾸려면 클로드를 거쳐 유호님께 올린다).

## 9. 착수 계획 — Codex 3R 제출 · 클로드 인수 (2026-08-06)

여기까지가 **발주 단계의 종점**이다. 아래는 Codex가 정한 물리 층 설계이므로 **클로드는 의미 층 위반만 본다**(분업 §8-1).

| 항목 | 확정 |
|---|---|
| 조각 | `supabase/migrations/YYYYMMDDHHMMSS_<영역>_<계약버전>.sql` — **파일명 정렬이 곧 실행 순서**(①) |
| 합본 | `supabase/L0_스키마.sql` — **생성물**이다. 손으로 고치지 않는다(⑤·⑥의 「구 파일 처분」이 여기서 해결된다) |
| 생성기·회귀 | `tools/마이그레이션_합본.js` + `tests/마이그레이션_합본.test.js`(바이트 동일성 · 1바이트 변이로 빨개짐 실증) |
| 이력(⑧) | `engine.schema_migrations` = `version`(PK)·`name`·`checksum`·`applied_at`. **버전+checksum 일치면 건너뛰고, 같은 버전에 checksum이 다르면 중단**. RLS 켜고 정책 0 |
| 부트스트랩(⑧) | **빈 DB** = `engine` 없고 public·계정 0 → 현행 버전 전체 실행 / **기존 낮은 판**(c3·c4) = 그 판의 본체 테이블과 접미사 제약이 **전부** 확인될 때만 §9-4 `alter` 경로 → 이력 기록 / **부분·혼합·불명** = 트랜잭션 중단, 이력 기록 금지 |
| 확인 기대값 | 🔴 **기준선 파일(`supabase/L0_스키마.sql`) 꼬리 확인이 정본** — 이력 테이블이 느는 만큼 **테이블·RLS 기대를 함께 올린 값**을 쓴다. 🔴**여기에 숫자를 적지 않는다**(세 번 낡았고 증상은 매번 「정상 적용이 ❌」였다 · §2-1). 사후 쿼리는 **현재 버전·checksum도 함께** 낸다 |
| 확인 쿼리 | 사전 = `supabase/확인_적용전상태.sql`(기존) / 사후 = `supabase/확인_적용후상태.sql`(신설) — **합본 밖**(⑤ 철회 조항) |
| CI(라) | `verify` 잡은 그대로 두고 **별도 `supabase` 잡 신설** · `build`는 둘 다 통과해야 실행. Supabase CLI는 **CI 구동에만** 쓴다(유호님 경로는 계속 SQL Editor — ③) |
| 검증 순서 | ①빈 DB ②재실행(이력·구조·데이터 불변) ③`commit` 전 실패 주입→전부 롤백 ④reset 복원(원격 개발 DB는 전진 수정만) ⑤두 Auth 사용자로 자기 행만·쓰기 차단·권한 0 ⑥**낮은 판(c3·c4) 픽스처→부트스트랩 경로**. ②와 ⑧은 **같은 DB의 연속 실행**으로 잰다 |
| 유호님 손 | **정상 경로 3회**(사전 확인 · 본체 · 사후 확인) + 실프로젝트 RLS 재확인 1회 = **총 4회.** 표가 허용한 재실행이 나면 2회 추가 |
| 남은 왕복 | **1회** — Codex 구현·CI 결과를 클로드가 통합 판정한다. **발주 재검수 4R은 없다** |

### 9-1. ⑦ 결과별 후속 판정표 (초안 — L0 §8 절차에 실린다)

| 확인 결과 | 재실행 | 유호님 행동 |
|---|---|---|
| 버전 있음 + checksum 일치 | 안 함 | 종료 · 판정 회신 |
| 버전 없음 + 사전 상태 = 완전 빈 DB | 사전 상태와 결과가 **모두** 일치할 때만 | 합본 1회 |
| 버전 없음 + 정확한 낮은 판 상태 | 그 판의 접미사 제약이 **빠짐없이** 확인될 때만 | 부트스트랩 합본 1회 |
| 부분 상태 | 🔴 금지 | 결과·주소를 보내고 전진 수정 대기 |
| 버전 불일치 · 같은 버전 checksum 불일치 | 🔴 금지 | 새 forward migration을 만든다 |
| 빨간 화면 · 초록 `❌` · 빈 화면 · 타임아웃 | 🔴 즉시 재실행 금지 | **사후 확인 쿼리 1회** 후 위 표로 |

### 9-2. 남은 미지 — 반려가 아니라 실측 항목
