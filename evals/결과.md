# 교정 엔진 평가 (2026-08-03)

프롬프트 `prompts/교정.md` · 픽스처 `evals/픽스처.json`(**합성 100문항** — 2026-08-08 확장, 이전 26)

## 🔴 지금 상태 (2026-08-08) — 시험지는 100문항인데 재진 것은 26문항이다

유호님 지시로 시험지를 26 → **100문항(오류 60 + 정상 40)**으로 늘렸다. **새 74문항의 출력은 아직 없다.**
아래 v1 점수는 **옛 26문항짜리**이고, 채점기가 그 사실을 스스로 말한다:

```
판정불가  74건  — 출력없음 74(모델을 안 돌렸다) · 근거없음 0(강사 교정을 더 받아야 한다)
⚠ 시험지 100문항 중 74문항은 출력이 없어 **안 재졌다** — 위 점수는 26문항짜리다.
```

**왜 늘렸나**: 정상 문장이 5개뿐이라 **과교정을 잴 힘이 없었다.** 0/5 무오류가 보증하는 상한은 60%다 — 실제 과교정률이 절반이어도 0이 나올 수 있는 표본이다. 그런데 문헌이 실측한 LLM 교정의 주된 실패 모드가 바로 과교정(맞는 문장에 부사·형용사를 덧붙이는 것)이다. 정상 40개면 상한이 **약 7.5%**로 내려간다.

**같이 메운 구멍**: 통제 어휘 23종 중 **8종이 시험지에 아예 없었다**(`조사:접속`·`조사:기타`·`어미:종결`·`어휘:없는말`·`맞춤법:기타`·`어순`·`누락:필수성분`·`화용:공손성`). 그 태그를 한 번도 못 붙여도 초록이었다. 이제 23종 전부 **단일 오류로 2개 이상**이다.

**채점기도 같이 고쳤다**: 확장하자 옛 출력에 없는 74건이 전부 「거짓양성 — 맞는 문장을 고쳤다」로 찍혔다. 거짓양성은 이 채점기의 최우선 축이라, **응답을 빠뜨린 모델이 「과교정이 심한 모델」로 보인다** — 모델 선발 판정이 그대로 뒤집히는 자리다. 출력 자체가 없으면 판정불가로 빼고, 사유를 `출력없음`/`근거없음`으로 갈랐다(처방이 정반대다: 모델을 돌려라 / 강사 교정을 받아라). 회귀 = `tests/계약.test.js`.

## v1 — 옛 26문항 기준 (2026-08-03)

**유호님 결정 반영: 「학생이 묻지 않은 오류까지 고친다」.** 규칙 2가 「최소로 고친다」에서 「틀린 것은 전부 고친다」로 바뀌었고, 그 방침을 재기 위해 복합 오류 6문장(`M01~M06`, 오류 2~3개짜리)을 픽스처에 넣었다.

```
거짓양성  0/5    (맞는 문장을 고친 건수 — 0이어야 한다)
교정 정확  21/21  100%
태그 정확  21/21  100%
전체 통과  26/26
```

재현: `npm run eval`

### 방침을 바꿀 때 채점기도 함께 바꿔야 했다

기대 태그 대조가 `some()`(하나라도 맞으면 통과)이었다. 그대로 뒀다면 **오류 3개 중 1개만 잡아도 만점**이라, 방침을 바꾼 것이 채점에 하나도 반영되지 않는다. `every()`로 바꿨다 — 「전부 고친다」의 기계적 표현이다.

### 규칙 1을 지키기 위해 규칙 3을 새로 세웠다

「전부 고친다」를 그냥 두면 규칙 1(맞는 문장은 고치지 않는다)을 잡아먹는다. 그래서 선을 명시했다 — **「틀림」과 「덜 자연스러움」은 다르다.** 문법·맞춤법·높임이 어긋난 것은 고치고, 틀리지 않았는데 원어민이면 다르게 말할 법한 것은 오류가 아니므로 두 방침 어디에도 해당하지 않는다. 정상 문장 5개의 거짓양성이 여전히 0인 것이 이 선이 유지됐다는 증거다.

## 🔴 이 수치가 말하지 않는 것 — 먼저 읽을 것

**100%는 상한이지 실측이 아니다.** 픽스처를 만든 주체와 출력을 만든 주체가 같다(둘 다 이 세션의 Claude). 정답을 아는 채로 답을 썼으니, 이 점수로 교정 품질을 주장할 수 없다.

구체적으로 세 가지가 아직 안 재졌다.

1. **실제 엔진 경로가 아니다.** 제품에서는 API가 `prompts/교정_v0.md`만 보고 답한다. 여기서는 대화 세션의 모델이 픽스처 설계 의도까지 아는 상태로 답했다. **이 차이가 결과를 바꿀 수 있다** — API로 같은 프롬프트를 돌리면 점수는 내려가는 쪽이 정상이다.
2. **오류 분포를 모른다.** 유형별로 1개씩 균등하게 만들었지만, 실제 몽골 학생은 특정 유형에서 압도적으로 많이 틀린다. 어디에 힘을 쏟을지는 실학생 문장으로만 알 수 있다.
3. **거짓양성 0은 「내가 예상한 함정을 피했다」는 뜻**이다(옛 5개 → 지금 40개로 넓혔지만 성질은 같다). 진짜 위험은 설계자가 예상하지 못한 함정이고, 그건 실학생 문장으로만 나온다.

## 그래서 실제로 증명된 것

- **하네스가 돈다** — 픽스처 → 출력 → 기계 채점 → 종료코드. 프롬프트를 고칠 때마다, **그리고 새 모델이 나올 때마다** 같은 100문항으로 이전과 비교할 수 있다. 이게 이번 작업의 진짜 산출물이다.
- **태그 어휘가 수집층과 붙는다** — 23종을 SYNK-appsscript `HW_ERROR_TAGS`에서 그대로 가져왔다. 갈라졌다면 2년치 집계가 깨진다. **그리고 이제 23종을 전부 시험한다**(전에는 8종이 시험지 밖이라, 그 태그를 한 번도 못 붙이는 모델도 만점이었다).
- **채점을 세 축으로 나눈 것이 값을 했다** — 합산 점수 하나였다면 거짓양성이 탐지율에 묻힌다. 제품에서 더 나쁜 실패는 「맞게 쓴 학생 문장을 고치는 것」이다. 학생이 자기가 뭘 아는지 모르게 되고 첨삭을 믿지 않게 된다.

## 관찰 1건 — 최소 수정과 교육적 교정이 부딪힌다

`E12` "우리 선생님은 한국어를 잘 배워요"에서 프롬프트 규칙 2(**최소로 고친다**)를 따르면 `가르쳐요`가 맞다. 그런데 실제 교사는 `가르치세요`로 고친다 — 선생님이 주어일 때의 주체 높임이 한국어에서 중요한 교육 지점이기 때문이다. 출력은 후자를 골랐고 태그가 하나 늘었다(`높임:주체` 추가).

**어느 쪽이 옳은지는 교육 방침의 문제이지 엔진의 문제가 아니다.** v1에서 프롬프트에 명시해야 할 첫 항목으로 남긴다 — 「학생이 묻지 않은 오류까지 고칠 것인가」.
